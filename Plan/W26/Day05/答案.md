# W26 · Day05 答案与资产盘点指引

## 一、自测题标准答案
1. **唯一改位置入口/谁只读**：片的物理位置是全设备最敏感的单一事实，一旦允许多处直接改，并发取放下必然出现双占、丢片、守恒被破坏且无法定位。SubstrateTracker 集中 expectedFrom 校验、加锁、快照、改后断言、失败回滚，把三不变式（唯一位置/容量/守恒）封死在一个入口。E40（PJ 路线）、E94（CJ 编排）、Cell（流水线）、Ept/Ram/Oee（度量）都只能**只读查询或读投影**（LocationOf/AllWaferIds/快照），需要移动时调用 Tracker 的 Move/Pick/Place/Transfer，绝不自行改位置。
2. **度量层为何不能反向写域**：Ept/Ram/Oee 是"观察者/消费者"，它们的存在依赖域事实（状态段、作业、片），如果反向修改 E40/E94 就形成依赖环，且会让"度量"反过来改变"被度量对象"，破坏因果与可测试性（算个 OEE 却改了作业状态是灾难）。正确方向是域发出领域事件、度量层订阅并维护自己的时间账/指标（只读投影），依赖箭头永远从度量指向域、不回头。这也保证同一批事件同源驱动作业与度量（W22/W24）。
3. **依赖环的问题/编译期禁止**：环依赖导致无法独立编译/单测（A 改了 B 也要重编、无法用桩替换）、层次职责腐化（谁都能调谁）、复用困难（想单独拿出 E90 却拖入整串）、变更影响不可控。用独立项目（csproj）+ 单向 ProjectReference，编译器在出现 A→B→A 时直接报循环引用错误，从构建期物理禁止；配合架构测试（反射检查程序集依赖关系、禁止下层引用上层命名空间）做持续守门。
4. **泛型 StateMachine 复用/一致语义**：W10 的 `StateMachine<TState,TTrigger>` 被 E30 控制态、E87 Carrier、E40 JobStateMachine、E94 CjStateMachine 等全部 FSM 复用。它统一保证：迁移必须显式 Configure/Permit 合法边、PermitIf 走 Guard 裁决、Fire 加锁原子、非法触发零副作用（不产生半迁移）、OnEntry/OnExit 回调一致、终态无出边。复用同一内核使所有状态机行为语义一致、不会每个模块各写一套有不同 bug 的迁移逻辑，也让"外部命令只是触发、必须经合法边+Guard、不直接赋值"这一铁律在全栈统一落地。
5. **build 过/test 挂 vs test 绿/架构有环**：build 过只证明语法与类型正确、能编译，test 挂说明行为不符合预期（逻辑错、边界没处理），是"能跑但跑得不对"，必须修到绿才算功能正确。test 绿但架构有环说明当前行为碰巧对、但结构已腐化：短期功能正常，长期无法独立演进/复用、改动牵一发动全身、技术债累积，属于"现在能用、将来难改"。两者是不同维度——test 守行为正确性，架构走查守可演进性，专家两者都要，不能用测试绿掩盖结构问题。
6. **新增停机原因码并进 OEE 的改动顺序**：自底向上、单向不回改。①E10/Ept：在原因码体系登记新码，E10StateClassifier 确认它归到哪个 E10 状态（SchDown/UnschDown/Standby）；②EptCollector 订阅对应领域事件、设置正确信号位，时间账能切出该段并带原因；③上报层 EptReporting 视需要加 VID/CEID 让 Host 收到；④Ram：若属故障确认是否计入 N_f/MTBF·MDT（计划类不计故障）；⑤Oee：在损失瀑布把它归到 A（停机）或 P（小停顿），OeeCalculator 无需改公式、只靠分类自动汇总；⑥测试：补该原因的采集/归类/指标 xUnit，build+test 回归。全程域→度量单向，不改既有状态机内核。
7. **证明可演进**：①分层+单向依赖，新增标准（如 EDA/E132、新 E116 原因）只需新增项目/模块并引用既有 Domain，不改动下层；②通信可替换——SECS2/HSMS 在 E5 层封装，替换传输（如换商业栈/Interface-A）不影响 E90/E40/E94 域逻辑；③泛型 StateMachine、Tracker、Scheduler 等稳定内核复用，新业务只配置不重写；④域与度量分离、事件驱动，加新订阅者（FDC/YMS/看板）不动发布方；⑤每个命名空间可独立单测、可用教学桩替换，证明解耦；⑥一套全绿测试作为重构安全网。能做到"加功能主要靠扩展而非修改既有核心"，就是可演进资产。

## 二、build / test 命令（PowerShell，解决方案根目录）
```powershell
# 一次构建(Release 也跑一遍)
dotnet build EapLab.sln -c Debug
dotnet build EapLab.sln -c Release
# 全部测试 + 收集结果
dotnet test EapLab.sln -c Debug --logger "console;verbosity=normal"
# 列测试用例数(不执行)
dotnet test EapLab.sln --list-tests
```

## 三、架构走查清单（逐条打勾）
- [ ] 项目引用方向：Domain 不引用任何业务层；E5/E30/E39 不引用 E40+；E90 不引用 E40/E94；Ept/Ram/Oee 不反向引用 E40/E94/Cell。
- [ ] 无循环 ProjectReference（编译器 0 循环引用错误）。
- [ ] 全栈改位置只出现在 E90 SubstrateTracker；grep 不到其他层直接写位置集合。
- [ ] 所有 FSM 均由泛型 StateMachine 派生，无自写第二套迁移内核。
- [ ] 状态迁移一律经合法边+Guard，无外部直接赋状态；受理≠生效处都以迁移后事件为准。
- [ ] 事件同源：作业 FSM 与 EptCollector 订阅同一领域事件、同一时钟。
- [ ] Spool/对账只在 Cell/Host 层，域层不掺通信重发逻辑。
- [ ] 无跨层"上层状态被下层直接修改"，跨层只走事件/只读查询。
- [ ] 每个命名空间有对应测试文件夹，关键不变量都有断言（守恒/合法边/指标自洽）。

## 五、今日易错点
1. 图省事在 E40/Cell 直接改片位置（破坏唯一入口与守恒）。
2. 度量层反向写作业域，形成因果倒置与依赖环。
3. 每个模块自写一套状态迁移，语义不一致、重复 bug。
4. 只看 build 过就交付，不跑全测试；或测试绿就无视架构环。
5. 项目引用随手加，形成环直到编译报错才回头拆。
6. 新增原因码只改上报不改 Classifier/指标归类，时间账与 OEE 对不上。
7. 通信层与域逻辑耦合，换传输/加 EDA 时要动核心。
8. 不写架构守门，靠人记忆保证分层，时间一长必然腐化。
