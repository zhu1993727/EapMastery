# W25 · Day01 答案与参考实现

## 一、自测题标准答案
1. **一次故障/反复报警计数**：故障是设备丧失规定功能、进入不可生产状态（UnscheduledDown）的事件；一次"可生产→不可生产"的状态进入计一次故障。同一根因在未修复期间的反复报警、抖动、连带告警不重复计数（它们属于同一次停机事件内部）；修复恢复可生产之后再次发生故障，才计为新的一次。计数对象是"进入不可用状态的次数（故障段数）"，不是报警条数，避免一次故障被报警次数放大。
2. **MTTR vs MDT / 等备件归属**：MTTR（Mean Time To Repair）是平均**实际修复**时间，只含工程师动手排查、换件、调试到修复的主动维修时间；MDT（Mean Down Time）是平均**停机**时间，从故障发生到恢复可用的整段，除修复外还含等待备件、等待人员、等待批准、后勤行政时间。等待备件属于 MDT 但不属于 MTTR（设备在等、没人在修）。现场常把两者混用，必须用原因码把故障段细分为"修复中/等待备件/等待人员"才能分别计算，否则 MTTR 会被等待时间虚高。
3. **公式**：MTBF=T_op/N_f（统计期累计运行时间/故障次数，平均故障间隔）；MTTR=T_cm/N_f（累计主动修复时间/故障次数）；Inherent Availability A_i=MTBF/(MTBF+MTTR)（只含主动修复、无等待后勤与计划停，反映固有可靠性）。补充：MTTF=T_op/失效数（不可修复对象平均到失效）；MDT=总停机时长/停机次数（含修复+等待后勤）。
4. **三种可用度差异**：差异全在分母包含什么。Inherent A_i=MTBF/(MTBF+MTTR)，只算主动修复，最"理想"、数值最高，衡量设计固有可靠性；Achieved A_a=MTBM/(MTBM+M̄)，把预防性维修 PM 也纳入维修间隔与停机（MTBM 含纠正+预防维修），体现实际维修策略影响；Operational/运行可用度=Uptime/(Uptime+非计划停机+等待/后勤+...)，按真实日历、含等待后勤等管理损失，口径最宽、数值最低，也最贴近 OEE 的 Availability。计划停机/未排产是否进分母必须逐口径声明。
5. **为何不能用日历时间当 T_op**：MTBF 度量"运行多久会出一次故障"，分母必须是设备真正处于可运行/运行状态的时间 T_op。日历总时间里混着未排产、计划 PM、等料待机、等待后勤——这些时间设备根本没在运行、没有"暴露在故障风险下"，算进分母会把 MTBF 虚高（显得很可靠，实际是很多时间没开机），且无法横向比较不同排班的机台。正确做法是从时间账取 Uptime/Operating 段累计为 T_op，停机/未排产剔除（按口径）。
6. **PM 计入故障吗 / 进哪个可用度**：PM 是计划内预防维修，不是故障，不计入 N_f、不拉低 MTBF（MTBF 只统计非计划故障）。它进入 Achieved Availability（通过 MTBM/M̄ 把预防维修作为维修活动纳入），也在 Operational 口径/时间账里作为 ScheduledDown 影响生产利用率；但不进 Inherent Availability（固有可用度只看故障与主动修复）。即 PM 是"计划维修活动"而非"失效"，归属计划停机口径。
7. **只有 Down 总时长能否算 MTTR**：不能严格算 MTTR，只能算 MDT（或 MTTR 的上界近似）。因为 MTTR 要剔除等待备件/人员/后勤，只留主动修复时间，而未细分的 UnscheduledDown 总时长把这些都包含在内。表述时应明确："因未细分修复与等待，现算得的是平均停机时间 MDT=总 Down/故障次数；MTTR≤MDT，需在原因码中补充修复中/等待分类后才能精确计算"，不能把 MDT 直接标成 MTTR，更不能臆造一个修复时间。

## 二、参考实现（net8.0）

```csharp
namespace EapLab.Ram;
public enum DownKind{ Repair, WaitPart, WaitStaff, WaitApproval, Logistics }
public sealed record FailureRec(double Start,double End,DownKind Kind,string Reason)
{ public double Dur=>End-Start; }

public sealed class RamMetrics
{
    public double OperatingTime{get;private set;} public int FailureCount{get;private set;}
    private readonly List<FailureRec> _f=new();
    public void AddOperating(double sec){OperatingTime+=sec;}
    public void AddFailure(FailureRec r){_f.Add(r);FailureCount++;}

    double Sum(Func<FailureRec,bool> where)=>_f.Where(where).Sum(x=>x.Dur);
    public double TotalDown=>_f.Sum(x=>x.Dur);
    public double RepairTime=>Sum(x=>x.Kind==DownKind.Repair);
    public double WaitTime=>Sum(x=>x.Kind!=DownKind.Repair);

    public double Mtbf=>FailureCount==0?double.PositiveInfinity:OperatingTime/FailureCount;
    public double Mttr=>FailureCount==0?0:RepairTime/FailureCount;
    public double Mdt=>FailureCount==0?0:TotalDown/FailureCount;
    public double FailureRate=>OperatingTime==0?0:FailureCount/OperatingTime; // λ

    // 固有可用度: 只含主动修复
    public double InherentAvailability=>
        double.IsPositiveInfinity(Mtbf)?1:Mtbf/(Mtbf+Mttr);
    // 运行可用度: 运行/(运行+全部非计划停机含等待后勤)
    public double OperationalAvailability=>
        OperatingTime+TotalDown==0?0:OperatingTime/(OperatingTime+TotalDown);
    // 达成可用度: 再纳入PM时间
    public double AchievedAvailability(double pmTime)
    { double up=OperatingTime, down=TotalDown+pmTime; return up+down==0?0:up/(up+down); }
}
```

public class RamTests

    static RamMetrics Build()

## 三、RAM 时间与公式（手绘参考）
```
时间轴: [运行T_op][故障: 等待备件 | 修复Repair ][运行]...[PM计划]...
计数: 每次"可生产→不可生产"=1次故障; 同因未修复内重复报警不重复计
MTBF=T_op/故障数(只运行时间, 剔除未排产/PM/待机)
MTTR=主动修复时间/故障数 ; MDT=(修复+等待备件/人员/后勤)/故障数 ; MTTR≤MDT
MTTF=运行/失效数(不可修复对象); λ=故障数/T_op≈1/MTBF
可用度族(分母决定口径):
 Inherent  =MTBF/(MTBF+MTTR)  (理想,只主动修复,最高)
 Achieved  =运行/(运行+非计划停+PM) (含预防维修)
 Operational=运行/(运行+非计划停+等待后勤) (真实日历,最宽最低,≈OEE-A)
来源: 全部取自EPT状态段+原因码(Repair/WaitPart/...); 未细分只能算MDT并注明
```

## 四、今日易错点
1. 把报警条数当故障次数（一次进入不可用=一次，同因未修复不重复计）。
2. MTTR 与 MDT 混（等备件/人员属 MDT 不属 MTTR）。
3. 用日历时间当 T_op（混入未排产/待机，MTBF 虚高）。
4. PM 当故障拉低 MTBF（PM 是计划维修，进 Achieved 不进 Inherent/故障数）。
5. 不声明可用度分母，三种口径数字混用不可比。
6. 没细分修复/等待却报 MTTR（只能报 MDT 并注明限制）。
7. MTBF/MTTF 不分（可修复用 MTBF，不可修复寿命用 MTTF）。
8. 以为可用度越高越好而选最宽/最窄口径（口径服务分析目的，须固定一致）。
