# W25 · Day06 答案与参考实现

## 一、基线计算（工具核算，8h=28800s）
- PPT=28800（NonScheduled=0）；Downtime=故障900+换型1200=2100；RunTime=26700。
- Availability=26700/28800=**92.71%**
- Performance=100×240/26700=24000/26700=**89.89%**
- Quality(FPY)=231/240=**96.25%**
- OEE=A×P×Q=化简式 100×231/28800=23100/28800=**80.21%**；TEEP=OEE=80.21%（无未排产）。
- 自洽：A×P=24000/28800=83.33%，×Q=80.21%，与化简式一致。

## 二、自测题标准答案
1. **计算过程**：见上。先由状态段定 PPT/RunTime 得 A=92.71%；由理想节拍 100s、总产 240、RunTime 得 P=89.89%；由一次合格 231/已判 240 得 Q=96.25%；三者相乘（等价于良品理想时间 23100s/PPT 28800s）得 OEE=80.21%。
2. **Standby/Engineering 处理**：经典 OEE 的 Downtime（从 PPT 扣到 RunTime）只取让设备"不能生产"的故障与换型；Standby（等料/短暂待机）与 Engineering（工程活动）设备本身可用、未离开运行，因此不进 Availability 的停机扣除，而是进入 RunTime——它们通过"占用运行时间却没产出/没量产"拉低 Performance（实际产出相对理想变少）。区别：故障/换型是设备确实停了（扣 A），等料/工程是设备没停但没在有效量产（扣 P/管理利用），这与 W24"等料是 Standby 不是故障"一脉相承。
3. **最大损失层/责任**：从时间瀑布看，Availability 损失 2100s（换型 1200+故障 900）最大，其中换型 Setup 属可通过 SMED 改善的设备/工程项、故障属设备可靠性（真空等子系统）；Performance 侧小停顿 300+降速 500=800s（设备稳定性/工艺/瓶颈）；Quality 损失 9 片（废品 5+一次未过 4）属工艺控制。综合最大可行动杠杆是换型+故障（时间最大），其中换型 1200s 为单项最大，责任以设备/工程为主；等料类 Standby 属外部物流，不在本基线 Downtime 内。
4. **分别提 A/P/Q / 乘法含义**：OEE 是三要素相乘，改善任一要素（其余不变）OEE 按比例提升，但**关键是改善要转化为有效产出**。见下方三组实验：只提 A 但不把释放时间用于生产时，A 升、P 同比例降，OEE 不变（化简式分子 Good 没变）；只有把释放/追回的时间真正变成更多良品，OEE 才上升。乘法结构说明：三要素是"串联短板"，OEE 被最低效的环节限制，且任何改善最终要落到 Good Count 或有效时间利用上。
5. **为何高 Q 再提空间小（边际）**：乘法下某要素越接近 1，把它再提高的绝对收益越小。若 Q 已 99.5%，提到 100% 只增加 0.5% 相对量、对 OEE 绝对拉动很小；而本例 Q=96.25% 尚有 3.75pt 空间，提到 100% 使 OEE 80.21%→83.33%（+3.13pt），反而比某些时间改善更直接，因为良率提升不额外占用时间、直接增加 Good。决策应比较各要素"到理想的差距×可改善性"，优先攻差距大且可落地的要素（帕累托/边际），而非无脑优化已经接近满分的项。
6. **返工 4 片（3 救回）体现**：FPY 口径下这 4 片第一次未过、不计入一次 Good，Q=231/240（含这 4 片为非一次合格）；最终良率=(231+3)/240=234/240=97.5%（3 片返工后救回，1 片报废归入废品 5 之内或单列，本例废品 5 含最终报废），高于 FPY。OEE 用 FPY=96.25%，返工救回不回补 Q；返工多跑的设备时间落在 RunTime、由 P 承担。即质量账看到 FPY96.25% 与最终 97.5% 的差=返工救回率，时间账看到返工占用的额外产能。
7. **非瓶颈设备提 OEE 不增整线产出（TOC）**：整线产出由瓶颈工序节拍决定（W18/W23）。若该设备不是瓶颈、前后有在制品缓冲或瓶颈在别处，它效率再高也只能多生产在制品堆在瓶颈前，整线产出节奏不变，甚至增加 WIP 与等待。因此局部 OEE 最大化不等于整线最优：非瓶颈设备适当待机有时是合理的（避免过量生产），改善应优先投向约束瓶颈（瓶颈的 OEE/可用率提升才直接放大整线产出）。这也是为什么设备端 OEE 要结合 W23 资源利用率/瓶颈定位一起看，避免局部优化、全局无效。

## 三、改善对比实验（工具核算）
| 方案 | 关键变化 | Total/Good | OEE | 相对基线 |
|---|---|---|---|---|
| 基线 | — | 240/231 | 80.21% | — |
| 治故障并转化产出 | 故障900清零，释放时间按当前P净增约8片 | 248/239 | 82.99% | +2.78pt |
| 只消故障不增产 | 释放900s变待机，Good不变 | 240/231 | 80.21% | **0（A升P降抵消）** |
| 治降速 | 追回500s多产5片 | 245/236 | 81.94% | +1.74pt |
| Q→100% | 消除9片质量损失、不增时间 | 240/240 | 83.33% | +3.13pt |

核心结论：**可用性/性能的时间改善必须转化为有效产出才提升 OEE**（否则 A 升 P 降、化简式不变）；良率提升直接增加 Good、不占时间，在 Q 有空间时杠杆很高；最终按"差距×可改善性×是否瓶颈"排优先级。

## 四、参考实现（net8.0）

```csharp
namespace EapLab.Oee.Lab;
public sealed class ShiftOeeLab
{
    static ShiftData Base()=>new(28800,0,900,1200,300,500,100,240,231,0,
        Enumerable.Range(1,240).Select(i=>"W"+i).ToHashSet(),
        Enumerable.Range(1,240).Select(i=>"W"+i).ToHashSet());
    readonly OeeCalculator _calc=new();
    public OeeResult Baseline()=>_calc.Compute(Base());

    public OeeResult FixFaultButNoGain() // 释放时间变待机: PPT不变,RunTime增,产出不变
    { var d=Base() with{FaultDown=0};return _calc.Compute(d); } // Good仍231→化简式不变
    public OeeResult FixFaultAndProduce() // 释放900s按P转化≈8片, Q不变
    { var d=Base() with{FaultDown=0,TotalCount=248,GoodFirstPass=239,
        ProcessedIds=Enumerable.Range(1,248).Select(i=>"W"+i).ToHashSet(),
        QualityIds=Enumerable.Range(1,248).Select(i=>"W"+i).ToHashSet()};return _calc.Compute(d); }
    public OeeResult FixSlowSpeed()=>_calc.Compute(Base() with{SlowLossTime=0,TotalCount=245,GoodFirstPass=236,
        ProcessedIds=Enumerable.Range(1,245).Select(i=>"W"+i).ToHashSet(),
        QualityIds=Enumerable.Range(1,245).Select(i=>"W"+i).ToHashSet()});
    public OeeResult PerfectQuality()=>_calc.Compute(Base() with{GoodFirstPass=240});
}
```

## 六、今日易错点
1. 以为消除停机就自动提 OEE（不增产则 A 升 P 降抵消，必须转化为 Good）。
2. Standby/Engineering 错扣到 Availability（应进 RunTime 影响 P/利用）。
3. 用最终良率代替 FPY，返工损失隐身。
4. 改善不做基线对比、不量化 OEE 变化。
5. 只看本机 OEE 忽视 TOC（非瓶颈提效不增整线产出、徒增 WIP）。
6. 三要素改善不同步考虑"差距×可改善性"，去优化已近满分项。
7. 返工片重复计数破坏 Total/守恒。
8. 报告不给责任归属与可行动建议，只堆数字。
