# W30 · Day05 答案与参考实现

## 一、自测题标准答案
1. **处理流水线**：①接收 EDA Packet（周期 Rows + 事件 Events + 时间戳/质量）；②先处理 Events——遇 StepChanged/JobStart 更新当前上下文（Job/Step/Recipe/Lot）、加载该段 RuleSet、Reset 全部有状态规则与告警态；③再按时间顺序逐行处理 Rows，按 Tag 找到当前段对应规则；④质量门控——非 Good 点不参与工艺判定（转数据质量处理）；⑤规则流式求值得到当前是否越限；⑥边沿管理——与该规则上一态比较，仅在 正常→报警 发 Raised、报警→正常 发 Cleared，激活期不重复；⑦抑制检查——被屏蔽状态直接跳过；⑧Raised 送分类器匹配指纹得 FaultId/严重度，critical 产出 Hold 建议对象（只建议，回控走 EAP→GEM）。
2. **先事件后周期点**：同一时间窗里事件 marker 声明"从此刻起进入哪个 Step/Recipe"，周期点是该 Step 下的数据。必须先处理事件、完成规则集切换与 Reset，再用**新段**规则判本窗数据；若先判点后切段，会用上一 Step（如升温段）的规则/状态去判新段（稳态）第一拍数据，在切换边界产生跨段误报或漏报，并把旧段窗口残留带入新段。顺序原则：上下文先行，数据判定在后。
3. **边沿管理/何时发**：解决"一条持续故障在每个采样点都重复告警、刷屏且下游重复处理"的问题。为每条规则维护激活态：仅当状态从 false→true 的跳变发一次 Raised（带规则/当前值/阈值/Step/Lot/时间/证据），持续越限期间不再发；当从 true→false（越过回差并满足恢复条件）发一次 Cleared，形成成对的告警生命周期。下游按 Raised/Cleared 计算当前活跃故障、持续时长，避免重复 Hold 建议。
4. **分段/结束清引擎告警态**：规则 Reset 只清规则内部窗口（rate 上一点、stuck 队列、去抖计数），但引擎还维护"哪些规则当前处于告警激活"的状态。若不清理，上一 Step/Job 遗留的激活态会被带进下一段：新段规则刚运行就被认为"已激活"从而漏发 Raised，或上一 Job 的告警悬挂不闭合（没有对应 Cleared），导致活跃故障表错误、持续时长统计跨 Job 串联。因此切段/作业结束要同时 Reset 规则并清空告警激活态（或为未闭合告警强制按上下文结束出 Cleared/Aborted）。
5. **抑制处理/不乱发 Cleared**：抑制（维护、换气、非 Scheduled 等）状态下，被屏蔽规则不执行判定、不产生 Raised；同时也不能因为"这期间没判/值正常了"就自动发 Cleared——因为抑制期根本没有有效判定，若据此发恢复，会把一个抑制期后仍存在的真实故障错误关闭。正确做法：抑制期冻结该规则状态（既不 Raised 也不 Cleared），抑制解除后重新基于有效数据判定（必要时重置窗口再确认），状态变化只由真实 Good 数据驱动。
6. **Bad/Gap/长期 Bad**：Bad/Uncertain/Gap 点不进入工艺限界/趋势判定（否则把采集坏点当真故障误报），变化率/stuck 窗口在 Gap 后重置（Day03）。但"数据长期 Bad/长时间无 Good 点"本身是一类独立的**数据质量/采集故障**（传感器掉线、EDA 断流），应单独产生数据质量告警（区别于工艺故障），因为 FDC 无法检测等于该量失去监控，对安全关键量属于危险状态，需要提示检查传感器/链路，甚至按策略建议安全处置。
7. **设备端为何精通 FDC**：FDC 是设备 EDA 数据的第一大消费者，它的能力边界直接规定设备端数据出口的要求——要哪些点/WKN/单位、多高采样与多快 flush（检测延迟预算）、必须有哪些 Step/Job/Lot/Hold/Alarm marker、点序与时间对齐、质量码/Gap、事件先于数据。不懂 FDC 怎么消费，就无法把 EDA 接口、事件、频率、上下文做对，会出现"数据都给了但 FDC 无法分段/漏检/误报"。设备端精通 FDC 内部逻辑，才能主导接口契约（Day04）、联调定位（是数据问题还是规则问题）、并正确实现回控闭环，这正是 EAP 专家与"只会发 SECS 消息"的区别。

## 二、参考实现（net8.0）：流式 FDC 引擎

```csharp
namespace EapLab.Fdc.Engine;
public enum AlarmEdge{Raised,Cleared}
public sealed record FdcAlarm(AlarmEdge Edge,string Rule,double At,double Value,string Step,string? FaultId,Severity? Sev,bool RecommendHold);

public sealed class RuleSet{
    public string Step{get;}public Dictionary<string,Rule> Rules{get;}=new();
    public HashSet<string> Suppressed{get;}=new();
    public RuleSet(string step){Step=step;}
    public RuleSet Add(Rule r){Rules[r.Tag]=r;return this;} }

public sealed class FdcEngine
{
    RuleSet? _cur;readonly Dictionary<string,bool> _active=new();readonly FaultClassifier _clf;
    public string Context{get;private set;}="";
    public FdcEngine(FaultClassifier clf){_clf=clf;}

    public void LoadSet(RuleSet rs){ _cur=rs;Context=rs.Step;
        foreach(var r in rs.Rules.Values)r.Reset();_active.Clear(); } // 切段: 规则+告警态全清

    public IEnumerable<FdcAlarm> Process(Packet pk)
    { var outA=new List<FdcAlarm>();
        // 1 事件优先(教学: 事件名即Step切换则外部已LoadSet; 这里处理作业/控制marker记录上下文)
        foreach(var e in pk.Events)Context=$"{Context}@ev{e.At:F3}";
        if(_cur is null)return outA;
        // 2 周期点按序判定
        foreach(var p in pk.Rows)
        { if(!_cur.Rules.TryGetValue(TagOf(p),out var rule))continue;
            if(_cur.Suppressed.Contains(rule.Tag))continue;          // 抑制: 冻结, 不Raise不Clear
            bool now=rule.Eval(p);bool prev=_active.GetValueOrDefault(rule.Tag);
            if(now&&!prev){ _active[rule.Tag]=true;
                var sym=new List<Symptom>{new(rule.Tag,"High")};
                var cr=_clf.Classify(sym);
                outA.Add(new(AlarmEdge.Raised,rule.Tag,p.At,p.V,Context,cr?.FaultId,cr?.Sev,
                    cr is not null&&cr.Sev==Severity.Critical)); }
            else if(!now&&prev){ _active[rule.Tag]=false;
                outA.Add(new(AlarmEdge.Cleared,rule.Tag,p.At,p.V,Context,null,null,false)); } }
        return outA; }
    static string TagOf(Pt p)=>"T"; // 教学: 真实按列映射
}
```

## 三、FDC 引擎数据流（手绘参考）
```
EDA Packet{Rows周期点, Events marker, 质量, 统一时钟}
  ①事件优先: StepChanged/JobStart→LoadSet(新RuleSet)+规则Reset+清告警态
  ②Rows按时间序: Tag→当前段规则; 抑制则冻结(不Raise不Clear)
  ③质量门控: 非Good不判工艺(长期Bad单列数据质量告警), Gap后窗口重置
  ④规则流式求值(Limit/Rate/Stuck: 去抖/回差/持续)
  ⑤边沿管理: false→true发Raised一次; true→false发Cleared; 激活期不刷
  ⑥Raised→分类器指纹→FaultId/Severity; Critical→Hold建议(仅建议)
  ⑦回控: 建议→EAP策略→GEM S2F41→S6F11生效(Day04), 引擎本身不写设备
扩展: 按腔分实例/规则索引/版本热加载(ECN); PCA/ML作为另一类规则挂同一流水线
```

## 四、今日易错点
1. 先判周期点后处理 marker，切换边界跨段误报。
2. 不做边沿管理，持续故障每点重复告警、重复 Hold 建议。
3. 切段只 Reset 规则、不清引擎激活态，旧告警悬挂/漏 Raised。
4. 抑制期根据"没判/值正常"误发 Cleared（应冻结状态）。
5. 对 Bad/Gap 点判工艺限界，把采集坏点当工艺故障。
6. 数据长期 Bad 不单独告警，安全量失去监控却无感知。
7. 引擎直接下发 Hold（应只产建议，回控走 EAP→GEM）。
8. 多 Tag 点乱序判，变化率依赖相邻点顺序被打乱。
