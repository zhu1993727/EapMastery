# W30 · Day02（周二）FDC 原理：故障检测（Detection）与故障分类（Classification）

> 建议时长：90 分钟。今天深入 FDC 两大核心动作：先"检测"出过程偏离/异常，再"分类"出是什么故障、可能根因。理解单变量/多变量/模型三类检测方法、故障指纹与分级、检测延迟与采样率关系，为 Day03 规则体系和 Day05 规则引擎打底。

## 一、今日目标
1. 分清 Detection 与 Classification：一个回答"是否异常/何时异常"，一个回答"是什么故障/根因"。
2. 掌握检测方法谱系：单变量限界/趋势、统计过程方法、多变量模型（PCA/T²/SPE 概念）、基于模型/AI。
3. 理解故障分类：故障库、症状-故障指纹、规则/模型分类、严重度分级与处置映射。

## 二、背景知识（先读，40 分钟）

### 1. Detection：怎么知道"不正常"
- **单变量规则（univariate）**：对单个传感器做上下限、变化率、卡死(无变化)、毛刺、死区、持续时间等判定，简单可解释，是现场主力（Day03 细做）。
- **统计/多变量（multivariate）**：变量间相关关系在高维空间是否偏离，常见 **PCA**（主成分分析）降维，**T² 统计量**（主成分空间内偏离）与 **SPE/Q 统计量**（残差，模型没能解释的部分）；适合单看每个量都正常、组合起来异常的故障。
- **基于模型**：物理/机理模型残差、回归/机器学习/深度学习（含 VM 预测残差）检测异常。
- 方法演进不是替代而是分层：简单规则兜底可解释，多变量/模型抓复杂耦合异常。

### 2. Classification：异常"是什么"
- 检测只给"异常了"，分类要给故障类型/根因（如 MFC 漂移、真空泄漏、RF 失配、温控异常、传感器断线）。
- **故障库（fault library）**：预定义故障、其症状指纹（哪些变量、什么方向/组合/时序模式）、可能根因、建议处置。
- 分类手段：规则（症状布尔组合/决策表）、模式匹配、机器学习分类模型；输出故障 id、名称、置信度、严重度。
- 分级：提示(warning)/严重(major)/危急(critical)，映射到不同处置（记录/通知/建议 Hold/立即停机建议）——处置仍经控制面（Day01 铁律）。

### 3. 检测延迟与采样率（设备端必须懂）
- 检测延迟=故障发生到被检出的时间，受采样率、规则持续时间窗口、上报 flush 周期、FDC 计算周期共同决定。
- 奈奎斯特直觉：要可靠捕捉一个时间尺度 T 的异常，采样周期应远小于 T（经验至少 5–10 倍密度）；采样太慢会把短时毛刺漏掉（alias）。
- 这直接反推设备端 EDA 该给多高频率、flush 多快（W28/W29 的采样/上报设计要满足 FDC 检测延迟预算）。

### 4. 误报与漏报（Day06 治理，先建概念）
- 误报(false alarm)：正常却报故障，造成不必要 Hold、损失产能；漏报(miss)：故障没报出，流到良率/安全。两者此消彼长，阈值/模型要按工艺窗口与代价平衡；抑制、去抖、工况区分是常用手段。

### 5. FDC 与 GEM Alarm(S5F1) 的关系（澄清旧知识）
- GEM S5F1 Alarm 是**设备自己**产生的离散报警通知（设备已知的明确故障，受控使能 S5F3）；FDC 是**上层基于过程数据**检测出的异常，可能比设备报警更早、更细（设备没报警但趋势已坏），也可能把多个 S5F1 + trace 综合分类。
- 二者都不是"执行方"：都只报告/建议，Hold 由设备 FSM 执行（你之前已厘清，今天从 FDC 视角再确认）。

### 6. 上下文依赖（呼应 W29 marker）
- 正常窗口随 Step/Recipe/产品而变（升温段温度快速上升是正常，稳态段同斜率就是异常），检测必须结合 Step/Recipe/Lot 上下文分段，这需要设备端提供事件 marker。
