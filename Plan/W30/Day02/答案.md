# W30 · Day02 答案与参考实现

## 一、自测题标准答案
1. **检测/分类/顺序**：Detection 回答"现在是否异常、从何时开始、哪些量偏离"，输出异常触发事实（触发规则/统计量、时间、偏离值）；Classification 回答"这是什么故障、根因可能是什么、多严重、建议怎么办"，输出故障 id/类型/置信度/严重度/处置建议。顺序上必须先检测后分类——分类需要以检测到的异常症状（哪些变量、什么方向/模式）为输入，没有可靠检测就无从分类；实践中也可边检测边把症状送分类器，但逻辑上"发现异常"先于"判定故障种类"。
2. **三类检测/场景**：①单变量规则——对单个传感器做限界/变化率/卡死/毛刺/持续时长，简单、可解释、易部署，适合有明确工艺窗口的量，是现场主力；②统计/多变量——捕捉变量间相关性破坏，每个量单独都在界内但组合异常（如温度与功率关系失衡），适合强耦合、多变量协同的工艺；③基于模型——用机理残差或 ML/DL/VM 模型预测并看残差，适合复杂、难用固定阈值描述的过程，能抓更隐蔽异常但可解释性弱、需建模维护。三者分层互补：规则兜底可解释，多变量/模型抓复杂异常，不是替代关系。
3. **T²/SPE 抓什么**：PCA 先把高维相关变量投影到主成分子空间。T²（Hotelling's T²）度量样本在主成分子空间内离正常中心多远（正常相关模式内部的大幅度偏离）；SPE/Q（Squared Prediction Error，残差）度量样本到主成分子空间的距离，即正常相关模型"解释不了"的部分（相关性结构被破坏）。它们能抓单变量限界抓不到的异常：每个变量都没超各自上下限，但变量之间的协同关系被破坏（例如压力正常、流量正常，但二者配比关系偏离训练的正常流形），单变量全绿而 T²/SPE 报警。
4. **症状指纹/输出字段**：症状指纹是某类故障在多变量上的特征模式——哪些变量、偏离方向（高/低/波动/卡死）、组合关系与时序先后（如"RF 反射功率升高 + 正向功率下降 + 腔压波动"→匹配网络/等离子异常）。分类器把实时症状与故障库指纹匹配。输出字段：故障 id/名称、匹配的症状、置信度(0–1)、严重度（warning/major/critical）、可能根因、建议处置、起止时间、关联 Lot/Job/Step 上下文。
5. **1 秒异常的采样密度**：依据"采样密度要显著高于异常时间尺度"（奈奎斯特思想：采样率须大于信号最高频率 2 倍，工程上为可靠刻画波形取 5–10 倍以上）。持续约 1s 的异常，若周期 1s 可能只采到 1 点甚至恰好漏掉，至少用 100–200ms 采样（5–10 点）较稳妥，要刻画其波形/变化率建议 50–100ms；同时规则持续窗口、EDA flush 周期、FDC 计算周期都要计入检测延迟预算，使"采样+上报+计算"总延迟远小于异常发展时间和允许响应时间，否则检出时故障已造成后果。
6. **FDC vs S5F1/谁 Hold**：S5F1 是设备自身产生的离散报警（设备已明确判定的故障，需 S5F3 使能，带 ALID/类别）；FDC 是上层基于连续 trace（可能结合多个 S5F1）做的检测分类，能在设备尚未报警时从趋势/多变量相关性提前发现、并做更细根因分类。联系：FDC 可把 S5F1 作为输入特征/事件，统一到时间线。两者都只是报告/建议方，不是执行方；Hold 的执行方永远是设备控制状态机（决策方可来自设备联锁/EAP 经 S2F41/FDC 经 EAP 建议，谁设谁解）。
7. **为何结合上下文/不结合后果**：工艺窗口随 Step/Recipe/产品变化——升温/抽真空过渡段，温度快速上升、压力快速下降本就是正常过程，若用稳态段阈值会大量误报；不同 Recipe/产品设定点不同，同一绝对值在 A 工艺正常、B 工艺异常。不结合 Step/Recipe/Lot 上下文就只能用一套全局阈值，必然在过渡段误报、在具体工艺段漏报，也无法把异常归因到具体工步/片。必须靠设备端事件 marker（StepChanged/JobStart 等，W29）把 trace 分段，按段加载对应规则/模型基线。

## 二、参考实现（net8.0）：检测结果 + 指纹分类器

```csharp
namespace EapLab.Fdc;
public enum Severity{ Info,Warning,Major,Critical }
public sealed record Symptom(string Tag,string Mode); // Mode: High/Low/Stuck/Drift/Wave
public sealed record Detection(double At,string Rule,string Tag,bool Triggered,double Value);
public sealed record FaultDef(string Id,string Name,HashSet<Symptom> Fingerprint,Severity Sev,string RootCause,string Action);
public sealed record ClassResult(string FaultId,double Confidence,Severity Sev,string Action);

public sealed class FaultClassifier
{
    readonly List<FaultDef> _lib=new();
    public FaultClassifier Add(FaultDef f){_lib.Add(f);return this;}
    // 用当前症状集合匹配指纹: 命中指纹症状比例为置信度, 全中=1
    public ClassResult? Classify(IEnumerable<Symptom> live)
    { var set=live.ToHashSet();ClassResult? best=null;
        foreach(var f in _lib)
        { int hit=f.Fingerprint.Count(set.Contains);double conf=(double)hit/f.Fingerprint.Count;
            if(hit>0&&(best is null||conf>best.Confidence))best=new ClassResult(f.Id,conf,f.Sev,f.Action); }
        return best; }
    // 处置建议只产出, 不直接控制(决策≠执行); Critical才建议回控Hold
    public bool RecommendHold(ClassResult r)=>r.Sev==Severity.Critical;
}
```

public class ClassifyTests

## 三、检测-分类-回控链路（手绘参考）
```
EDA trace+事件marker ─分段(Step/Recipe)─▶ 检测层
  单变量(限界/变化率/卡死/毛刺/持续) ; 多变量(PCA: T²主成分内偏离, SPE/Q残差相关性破坏) ; 模型残差
        │ 触发的症状集合(Tag,Mode,At)
        ▼
分类层: 症状指纹匹配故障库 → FaultId/置信度/严重度/根因/建议
        │ 分级 Info/Warning/Major/Critical
        ▼
建议层: 记录/通知 ; Critical→Hold建议(只产出建议, 不直写设备)
        ▼ 经EAP/Host决策 → GEM S2F41 → 设备FSM执行(谁设谁解) → S6F11/S5F1回告
延迟链: 采样周期+规则窗口+flush+FDC计算 << 异常发展时间(密度5~10倍以上)
对照: S5F1=设备自报离散报警; FDC=上层数据检测, 可更早更细; 都非执行方
```

## 四、今日易错点
1. 把检测和分类混为一谈（先检出异常、再判故障种类）。
2. 只懂单变量限界，不知道多变量相关性异常（T²/SPE）。
3. 以为每个量都在界内就一定正常（相关性破坏照样故障）。
4. 指纹匹配不给置信度/严重度，无法排序与决策。
5. 忽视检测延迟预算，采样/flush 太慢漏掉短时异常。
6. 把 FDC 异常等同 S5F1（前者上层数据检测、后者设备自报，可互补）。
7. 不按 Step/Recipe 分段，用全局阈值导致过渡段误报。
8. 让 FDC 分类结果直接停机（只建议，回控必须经 GEM 控制面）。
