# W24 · Day05 答案与参考实现

## 一、自测题标准答案
1. **包含关系**：总时间 = Scheduled Time（已排产）+ Non-Scheduled（未排产）。Scheduled = Uptime + Downtime。Uptime = Productive + Standby + Engineering（设备可生产）。Downtime = Scheduled Down + Unscheduled Down（设备不能生产）。即 Productive ⊂ Uptime ⊂ Scheduled；两类 Down 合为 Downtime ⊂ Scheduled；Non-Scheduled 在 Scheduled 之外、不进可用率分母。
2. **Availability vs Production Utilization**：可用率 Availability=Uptime/Scheduled Time（在该生产的时间里设备能不能生产，扣减的是 Downtime，主要是 Unscheduled Down）；生产利用率 Production Utilization=Productive/Scheduled Time（真正增值加工占排产时间比例）。差异来自 Uptime 里不增值的 Standby（等料/等指令）与 Engineering（工程活动）——设备明明是好的（计入可用），却没在量产（不计入 Productive），所以通常 Production Utilization ≤ Availability，差值正好暴露"设备没坏却没产出"的浪费。
3. **为何显式声明口径 / Scheduled Down 例**：同一批时间段用不同分母/归属会得出不同指标，不声明口径数字无法比较、容易互相矛盾。典型 Scheduled Down（PM/换型）：一种口径（设备综合视角）把它计入 Downtime、从可用率扣除，因为这段确实没产出；另一种口径（固有可用度/剔除计划停机）把 Scheduled Down 与 Non-Scheduled 一样排除在分母外，只让 Unscheduled Down 拉低可用率，用于衡量"纯故障可靠性"。两种都常见，报告必须写明分母是 Scheduled Time 还是 Scheduled−ScheduledDown，否则 PM 多的机台可用率不可比。
4. **六大损失映射**：①故障停机→Unscheduled Down 段；②换型/Setup 调整→Scheduled Down 段（时间账直接覆盖①②）；③空转小停顿→短暂 Standby/Idle 段（可生产但瞬时等待，时间账覆盖）；④降速损失→需要实际加工节拍对比理想节拍（W23 beat/工艺时长），处于 Productive 但单位产出变慢，光看状态段不够、要结合产出速率；⑤废品/缺陷、⑥启动返工降等→需要良率/分档与 Rework 数据（W23 Binning/Rework），属质量损失。即 EPT 时间账直接给①②③，④要节拍数据，⑤⑥要质量数据，三者合起来才是完整 OEE。
5. **Standby 是否瓶颈导致**：把 Standby 段的原因码/关联资源与 W23 全局资源日历对齐：若大量 Standby 是"等待某腔/某锁/机械手"，且该资源在资源日历上利用率接近 100%、其他资源在等它，则 Standby 是瓶颈拥塞传导的排队（瓶颈节拍决定整机，上游只能等）；若 Standby 主要是"无载具/等 AMHS/等 Host 指令"，则是外部物流/调度原因而非设备瓶颈。用资源利用率交叉验证：等待时间高度集中在最高利用率资源前后，即瓶颈导致；分散且与外部事件相关，则非瓶颈。
6. **MTBF/MTTR / 数据来源**：MTBF（Mean Time Between Failures，平均无故障时间）度量相邻故障之间设备正常运行的平均时长，=统计期内累计运行(Uptime/Productive)时长 / 故障次数（Unscheduled Down 段数）；MTTR（Mean Time To Repair，平均修复时间）度量一次故障平均多久修好，=Unscheduled Down 段总时长 / 故障次数。数据全部来自时间账：UnscheduledDown 段给修复时长与次数，相邻故障间的 Uptime 段给无故障间隔；段上的原因码还可按子系统分别统计 MTBF/MTTR（E58 完整口径 W25）。
7. **区分设备可控/外部**：帕累托按原因码时长排序找最大损失项后，要区分责任与可改善性：设备可控（故障、降速、设备内部小停顿、可优化的换型）由设备/工程团队通过可靠性、维护、控制优化改善；外部损失（等料/等 AMHS/等 Host 派工/未排产）要靠物流、调度、生产计划改善，设备团队单方面改不了。混在一起会让设备团队为"没料"背指标、或让厂务忽视真正的外部瓶颈；分类后各认领最大项，改善才落到能行动的一方。

## 二、参考实现（net8.0）

```csharp
namespace EapLab.Ept.Metrics;
public sealed class TimeBook
{
    public Dictionary<E10State,double> ByState{get;}=Enum.GetValues<E10State>().ToDictionary(s=>s,_=>0.0);
    public Dictionary<string,double> DownByReason{get;}=new();   // 原因码下钻
    public int FaultCount;
    public void Add(Segment s)
    { ByState[s.State]+=s.Dur;
      if(s.State==E10State.UnscheduledDown){DownByReason[s.Reason]=DownByReason.GetValueOrDefault(s.Reason)+s.Dur;FaultCount++;} }
    public double Scheduled=>ByState.Sum(kv=>kv.Value)-ByState[E10State.NonScheduled];
    public double Uptime=>ByState[E10State.Productive]+ByState[E10State.Standby]+ByState[E10State.Engineering];
    public double Downtime=>ByState[E10State.ScheduledDown]+ByState[E10State.UnscheduledDown];
}

public sealed class EptMetrics
{
    readonly bool _excludeScheduledDown;   // 口径显式声明
    public EptMetrics(bool excludeScheduledDown=false){_excludeScheduledDown=excludeScheduledDown;}
    double AvailabilityDenom(TimeBook b)=>_excludeScheduledDown?b.Scheduled-b.ByState[E10State.ScheduledDown]:b.Scheduled;
    public double Availability(TimeBook b)=>b.Uptime/AvailabilityDenom(b);
    public double ProductionUtilization(TimeBook b)=>b.ByState[E10State.Productive]/b.Scheduled;
    public double StateShare(TimeBook b,E10State s)=>b.ByState[s]/b.Scheduled;

    public double Mtbf(TimeBook b)=> // 无故障运行时长/故障次数
        b.FaultCount==0?double.PositiveInfinity:b.Uptime/b.FaultCount;
    public double Mttr(TimeBook b)=>
        b.FaultCount==0?0:b.ByState[E10State.UnscheduledDown]/b.FaultCount;

    // 损失帕累托(原因码降序)
    public List<(string reason,double dur,double share)> LossPareto(TimeBook b)
    { double tot=b.Downtime+b.ByState[E10State.Standby]+b.ByState[E10State.Engineering];
      return b.DownByReason.Concat(new Dictionary<string,double>
        { ["STANDBY_WAIT"]=b.ByState[E10State.Standby],["ENGINEERING"]=b.ByState[E10State.Engineering] })
        .OrderByDescending(kv=>kv.Value)
        .Select(kv=>(kv.Key,kv.Value,tot>0?kv.Value/tot:0)).ToList(); }
}
```

### 损失-瓶颈关联
```csharp
public sealed record WaitSlice(double At,double Dur,string WaitingFor);
public sealed class BottleneckCorrelation
{   // Standby等待按所等资源聚合, 与资源利用率对照
    public Dictionary<string,double> WaitByResource(IEnumerable<WaitSlice> ws)
    =>ws.Aggregate(new Dictionary<string,double>(),(m,x)=>{m[x.WaitingFor]=m.GetValueOrDefault(x.WaitingFor)+x.Dur;return m;});
    public string? BottleneckResource(Dictionary<string,double> waitByRes,Dictionary<string,double> utilization)
    =>waitByRes.Keys.OrderByDescending(r=>waitByRes[r]*(utilization.GetValueOrDefault(r))).FirstOrDefault();
}
```

## 三、时间→指标（手绘参考）
```
总时间 = NonScheduled + Scheduled
Scheduled = Uptime(Productive+Standby+Engineering) + Downtime(SchDown+UnschDown)
Availability=Uptime/Scheduled(口径: 是否剔除SchDown需声明)
ProductionUtilization=Productive/Scheduled (≤Availability, 差=Standby+Engineering浪费)
六大损失: ①故障→UnschDown ②换型→SchDown ③小停顿→Standby
         ④降速→实际vs理想节拍(W23) ⑤废品⑥返工→良率/Binning/Rework(W25)
下钻: 段原因码聚合时长/次数; MTBF=运行/故障次数 MTTR=故障时长/次数
瓶颈: Standby"等资源"×资源利用率→集中在≈100%资源即瓶颈; 等料/等指令属外部
帕累托: 最大损失先攻, 区分设备可控 vs 外部
```

## 四、今日易错点
1. 混淆 Availability 与 Production Utilization（差在 Standby/Engineering）。
2. 不声明分母口径，Scheduled Down 归属前后不一致。
3. 把 Non-Scheduled 算进可用率损失（未排产不进 Scheduled）。
4. 以为时间账能覆盖全部六大损失（降速要节拍、废品返工要良率）。
5. MTBF/MTTR 概念混（一个是正常间隔、一个是修复时长）。
6. Standby 一律当设备问题（要区分瓶颈排队 vs 外部等料）。
7. 损失不按原因码下钻，只给总停机时长（无法定位子系统/责任）。
8. 改善不做帕累托、不区分设备可控与外部，行动落不到责任方。
