## 二、自测题标准答案
1. **处理链**：班次领域事件（作业/载具/故障/维护/工程/排产，含断线窗口）→EptCollector 改信号位、E10StateClassifier 算唯一状态、EquipmentTimeModel 切段（同源同戳）→EptReporting 把每次切段经统一出口出 S6F11/S16F1（断线进 Spool，重连先快照对账再按序补）→班末 Close 闭合时间账→TimeBook 汇总各态时长与原因→EptMetrics 算可用率/利用率/MTBF/MTTR/帕累托/瓶颈→生成复盘报告。
2. **闭合断言项**：①互斥——逐时刻只有一个活动段（相邻段状态不同才切）；②完备——相邻段前一段 end==后一段 start，无缝隙无重叠；③时间守恒——所有段时长之和=班次时长 28800；④分类完整——每段都有合法 E10 状态与原因码；⑤上报一致——Host 侧重建的段与设备侧段逐段相同（经 Spool 补发后仍一致）。任一不过时间账不可信。
3. **断线内切换为何 Host 仍完整**：断线期间状态切换不依赖连接，EptCollector 照常切段、本地时间账连续推进，该切换事件带序号进 Spool 缓存而非丢弃；重连后先发"当前状态+各态累计"权威快照让 Host 对账，再按序补发 Spool 内事件，Host 按序号去重、顺序应用、ACK 后删除。于是断线 300s 内的那次切换既没丢（在 Spool）也没乱（按序+快照校验），Host 重建出的状态段与设备本地完全一致、时间账仍闭合。
4. **最大损失/归因/建议**：按时长，Standby 合计 3000s 最大（开班+等料 600+班末 1800+其他），其次 SETUP 1200、Engineering 900、故障 900。其中 WAIT_MAT 与开班/班末待料属外部（物流/排产/计划衔接），建议由生产调度/AMHS 物流改善（提前备料、错峰换型、班末排料优化），设备团队配合暴露等待原因；真正设备可控的是 VAC_FAULT 900s（真空子系统可靠性、预防性维护）与换型时间（SMED 快速换型）。注意：Standby 总量大但多为边界/外部，应再按原因码拆分，避免误判为设备故障。
5. **SETUP 在两口径下**：含计划停机口径（分母=Scheduled=28800），SETUP 1200 计入 Downtime、拉低 Availability；剔除计划停机口径（分母=28800−1200=27600），SETUP 不扣可用率（视为计划安排），只影响 Production Utilization（它不是 Productive）。本场景两口径 Availability 分别为 92.71% 与 96.74%，报告必须声明用哪个口径。
6. **Engineering 两指标差异**：Engineering 属于 Uptime（设备健康可用），所以不降低 Availability；但它不是批量增值生产，不计入 Productive，因此会拉低 Production Utilization。本场景 900s Engineering：可用率把它当"可用"，生产利用率把它当"没在量产"，这正是两者差值来源之一，说明"设备好着但在做工程"是一种需要单独管理的时间占用。
7. **消最大损失后的结构效应**：把损失时间转为生产时间后，不仅生产时间增加，各状态占比的分母结构也变化——原 Standby 3000 若全部转为 Productive，Productive 变为 25800，Production Utilization 从 79.17% 升到 89.58%；同时其他状态（如故障、换型）占比因生产占比上升而相对下降（结构重排）。所以改善一项会同时改变分子与相对结构，指标要重算而非简单加减；这也说明抓最大损失项（帕累托）杠杆最大。

## 三、指标结果（工具核算）
- Availability（含 ScheduledDown）=26700/28800=**92.71%**
- Availability（剔除 ScheduledDown）=26700/27600=**96.74%**
- Production Utilization=22800/28800=**79.17%**
- 各态占比：Productive 79.17% / Standby 10.42% / Engineering 3.13% / ScheduledDown 4.17% / UnscheduledDown 3.13%
- MTTR=900/1 次=900s；MTBF=26700/1=26700s（单故障教学值）
- 损失帕累托：Standby 3000 > SETUP 1200 > Engineering 900 = VAC_FAULT 900
- 改善对照：消 Standby 3000→Productive，Utilization 89.58%（+10.41pt）

## 四、参考实现（net8.0）：班次复盘

```csharp
namespace EapLab.Ept.Lab;
public sealed class ShiftReplay
{
    public (TimeBook book,EptReporting rep) Run()
    {
        var col=new EptCollector(); var rep=new EptReporting();
        void E(DomainEventKind k,double t,string r="")=>col.Handle(new DomainEvent(k,t,r));
        E(DomainEventKind.ShiftStart,0);
        E(DomainEventKind.CarrierLoaded,300); E(DomainEventKind.JobStart,600);
        E(DomainEventKind.FaultBegin,7200,"VAC_FAULT"); E(DomainEventKind.FaultClear,8100);
        E(DomainEventKind.JobStart,8100); E(DomainEventKind.JobFinish,12000);
        E(DomainEventKind.JobStart,12600);                                   // 12000-12600 WAIT_MAT
        E(DomainEventKind.JobFinish,16000); E(DomainEventKind.PmBegin,16000,"SETUP");
        E(DomainEventKind.PmEnd,17200); E(DomainEventKind.JobStart,17200);
        E(DomainEventKind.JobFinish,19000); E(DomainEventKind.EngageEngineering,19000);
        E(DomainEventKind.ExitEngineering,19900); E(DomainEventKind.JobStart,19900);
        E(DomainEventKind.InfoAlarm,23000);                                 // 不切段
        E(DomainEventKind.JobFinish,27000); E(DomainEventKind.ShiftEnd,28800);
        col.EndShift(28800);
        var book=new TimeBook(); foreach(var s in col.Segments)book.Add(s);
        return(book,rep);
    }
}
```

## 六、今日易错点
1. 时间账不校验闭合（段和必须=班次时长、相邻首尾相接）。
2. 提示报警/加工中动作误切段，破坏真实生产时长。
3. 可用率不声明是否剔除 ScheduledDown，数字不可比。
4. 把 Availability 当 Production Utilization（忽略 Standby/Engineering 浪费）。
5. Standby 总量大就误判设备差（要按原因码拆外部 vs 设备可控）。
6. 断线切换事件丢弃（Spool+快照对账才完整）。
7. 改善只做绝对加减、忽略占比结构效应（要整体重算）。
8. MTBF/MTTR 用错分子（运行时长/故障次数、故障时长/故障次数）。
