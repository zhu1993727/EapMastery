## 二、背景知识（先读，25 分钟）

### 1. 6 类异常场景

#### 场景1：消息格式错误
- **表现**：Host 发的消息 body 格式不符合预期（如 S2F41 body 不是 L,2、参数不是 L,2[A,值]、类型不匹配）。
- **检测**：解析 body 时检查类型、长度、嵌套结构。
- **处理**：回 S9 错误（S9F7=非法数据、S9F9=数据太长），或回对应 reply 带 ACKC 非 0（如 S2F42 ACKC10=3 参数错误）。
- **原则**：不崩溃、不抛出未捕获异常、记录详细日志（收到的原始 hex + 错误原因）。

#### 场景2：通信超时
- **表现**：Host 发消息后设备没回 reply（T3 超时），或设备发消息后 Host 没回确认（S6F12/S5F2 超时）。
- **检测**：发送消息时启动 T3 定时器，超时未收到 reply/确认则触发超时处理。
- **处理**：
  - Host 发消息超时：重发（最多 N 次），或记录错误并通知上层。
  - 设备发 S6F11/S5F1 超时：重发（最多 N 次），超过后进入 Spool 缓存（如果通信中断）。
- **原则**：不无限重发、不阻塞其他消息、记录超时日志。

#### 场景3：连接断开/重连
- **表现**：TCP 连接断开、HSMS Select 丢失、网络中断。
- **检测**：TCP 连接的 Receive/Send 报错、HSMS 心跳（Linktest）超时、Select 状态变化。
- **处理**：
  1. 标记通信状态为 OFF-LINE，触发 Spool 模式（开始缓存事件/报警）。
  2. 停止发送新消息（除 S1 通信相关消息）。
  3. 启动重连机制（指数退避：1s、2s、4s、8s...，最大间隔 30s）。
  4. 重连成功后，重新建立 Select、S1F13 建立通信、S1F17 请求在线。
  5. 通信恢复后，重发 Spool 缓存的事件/报警。
- **原则**：不崩溃、自动重连、重连后恢复状态、Spool 保证数据不丢。

#### 场景4：状态不一致
- **表现**：Host 和设备的状态不一致（如 Host 认为通信 ON-LINE 但设备认为 OFF-LINE、Host 认为命令在执行但设备认为已完成）。
- **检测**：
  - 定期查询设备状态（S1F11 查询通信状态/控制状态 SV）。
  - 收到意外的消息（如 OFF-LINE 时收到 S6F11）。
  - 状态转换时校验合法性（如从 OFF-LINE 直接到 EXECUTING 是非法的）。
- **处理**：
  - 重新同步状态（发 S1F13 重新建立通信、S1F17 请求在线）。
  - 查询设备当前状态（S1F11），以设备状态为准。
  - 记录状态不一致日志，告警。
- **原则**：以设备状态为准（设备是状态的权威来源），不盲目信任 Host 缓存的状态。

#### 场景5：非法状态转换
- **表现**：收到导致非法状态转换的消息（如 OFF-LINE 时收到 S2F41、EQUIPMENT OFF-LINE 时收到 S2F41、命令已完成时又收到完成事件）。
- **检测**：状态机的 CanTransition 方法校验合法边，非法转换拦截。
- **处理**：
  - 拒绝消息（回 ACKC 非 0 或 S9 错误）。
  - 记录非法转换日志（当前状态、请求的转换、消息内容）。
  - 不改变状态（保持当前状态）。
- **原则**：状态机是唯一的状态管理者，所有状态变化必须经过状态机校验，不允许绕过状态机直接改状态。

#### 场景6：资源耗尽
- **表现**：内存不足、队列满、线程池耗尽、文件句柄耗尽。
- **检测**：
  - 内存：定期检查 GC.GetTotalMemory，超过阈值告警。
  - 队列：检查队列长度，超过阈值拒绝新元素。
  - 线程池：检查 ThreadPool.GetAvailableThreads，不足时告警。
- **处理**：
  - 队列满：拒绝新消息（回 ACKC 非 0），不丢弃已有消息。
  - 内存不足：触发 GC、清理缓存（如 Spool 中最旧的记录）、告警。
  - 线程池耗尽：限流（降低消息处理速率）、告警。
- **原则**：优雅降级（拒绝新请求而不是崩溃）、告警通知、自动恢复（资源释放后恢复正常）。

### 2. S9 错误回执的正确用法
- S9 是"设备端错误"消息，用于设备无法处理收到的消息时通知 Host。
- 常见 S9 消息：
  - S9F1：未定义的 Stream（Stream 不认识）
  - S9F3：未定义的 Function（Function 不支持）
  - S9F5：非法的消息（消息格式非法，如 W 位错误）
  - S9F7：非法的数据（body 数据格式错误）
  - S9F9：数据太长（body 超过设备支持的最大长度）
  - S9F11：转换超时（设备处理超时）
- **使用原则**：
  - S9 用于"消息本身不支持/无法处理"（如 Stream 不认识、Function 不支持、数据格式错误）。
  - 如果消息支持但当前条件不满足（如 OFF-LINE 时发 S2F41），应该回对应 reply 带 ACKC 非 0，而不是 S9。
  - S9 是 W=0（不需要 Host 再回），设备发完即止。
  - 发 S9 时记录详细日志（收到的原始消息 hex + 错误原因）。

### 3. 异常处理框架设计
```
全局异常捕获（GlobalExceptionHandler）
  ├─ 消息处理异常 → 回 S9 错误 + 记录日志
  ├─ 状态机异常 → 拒绝转换 + 记录日志 + 状态一致性检查
  ├─ 通信异常 → 标记 OFF-LINE + 触发 Spool + 启动重连
  ├─ 超时异常 → 重发（有限次）+ 记录日志
  ├─ 资源耗尽 → 优雅降级 + 告警
  └─ 未知异常 → 记录详细日志 + 尝试恢复（不崩溃）
```
- 所有线程的入口都要有 try/catch，不允许未捕获异常导致进程崩溃。
- 异常日志要包含：异常类型、消息、堆栈、上下文（当前状态、收到的消息 hex）。
- 异常处理后要尝试恢复（如重连、重试、状态同步），而不是只记录日志就放弃。
