# W08 · Day05 答案与参考实现

## 一、自测题标准答案
1. **6 类异常场景 / 检测方法 / 处理策略**：
   ①**消息格式错误**：检测=解析 body 时检查类型/长度/嵌套；处理=回 S9F7（非法数据）或对应 reply 带 ACKC 非 0，记录原始 hex 日志。
   ②**通信超时**：检测=发送消息时启动 T3 定时器，超时未收到 reply/确认；处理=有限次重发（最多 3 次），超过后记录错误，设备端进入 Spool 缓存。
   ③**连接断开/重连**：检测=TCP Receive/Send 报错、Linktest 超时、Select 状态变化；处理=标记 OFF-LINE→触发 Spool→指数退避重连→重连后重新建链→重发 Spool 缓存。
   ④**状态不一致**：检测=定期查询设备状态（S1F11）、收到意外消息、非法状态转换拦截；处理=以设备状态为准，重新同步（S1F13/S1F17），记录告警。
   ⑤**非法状态转换**：检测=状态机 CanTransition 校验合法边；处理=拒绝消息（ACKC 非 0 或 S9），不改变状态，记录非法转换日志。
   ⑥**资源耗尽**：检测=定期检查内存/队列长度/线程池；处理=优雅降级（拒绝新请求、限流、清理缓存），告警，资源释放后自动恢复。

2. **S9 错误 vs ACKC 非 0 / 使用场景**：**S9 错误**表示"消息本身不支持/无法处理"——Stream 不认识(S9F1)、Function 不支持(S9F3)、消息格式非法(S9F5)、数据格式错误(S9F7)、数据太长(S9F9)、转换超时(S9F11)。设备无法理解这条消息，回 S9 通知对端。**ACKC 非 0**表示"消息支持但当前条件不满足"——设备理解这条消息，但因为状态不对(OFF-LINE)、参数错、设备忙等原因拒绝执行，回对应 reply 带 ACKC 非 0。简单说：S9="我听不懂你说什么"，ACKC 非 0="我听懂了但现在不能做"。使用原则：消息本身不支持（Stream/Function 不认识、格式非法）用 S9；消息支持但条件不满足（状态不对、参数错、设备忙）用 ACKC 非 0。

3. **通信断开后设备怎么处理 / 重连后怎么恢复**：通信断开后：①标记通信状态 OFF-LINE，控制状态自动回 OFF-LINE；②触发 Spool 模式，事件/报警写入缓存（不发给 Host）；③停止发送新消息（除 S1 通信相关）；④正在执行的命令继续执行（不中断，因为通信不影响设备内部运行）；⑤启动指数退避重连（1s、2s、4s、8s...最大 30s）。重连后：①重新建立 TCP 连接和 HSMS Select；②发 S1F13 重新建立通信，S1F17 请求在线；③通信 ON-LINE 后，重发 Spool 缓存的事件/报警（按时间顺序，限速）；④Host 回确认后从缓存删除；⑤全部重发完成后，Spool 清空，切回正常上报模式；⑥重新同步状态（查询设备当前状态、命令执行状态）。关键：Spool 保证通信中断期间的数据不丢失，重连后补收。

4. **状态不一致时以谁为准 / 怎么重新同步**：以**设备的状态为准**——设备是状态的权威来源，Host 缓存的状态可能因为消息丢失、延迟、异常而不准确。重新同步的方法：①Host 发 S1F11 查询设备的通信状态、控制状态、运行状态等 SV；②Host 用查询到的设备状态更新自己的缓存状态；③如果发现通信状态不一致（Host 认为 ON-LINE 但设备是 OFF-LINE），重新发 S1F13/S1F17 建立通信；④如果发现命令状态不一致（Host 认为命令在执行但设备已完成），查询命令相关的 SV 或等待命令完成事件；⑤记录状态不一致告警，包含 Host 缓存状态和设备实际状态的对比，便于排查根因。原则：定期（如每 30 秒）做状态一致性检查，不要只在异常时才检查。

5. **非法状态转换时设备怎么处理 / 状态机作用**：非法状态转换时：①状态机的 CanTransition 方法返回 false（当前状态不允许这个转换）；②设备拒绝导致转换的消息，回 ACKC 非 0（如 OFF-LINE 时发 S2F41 回 ACKC10=4）或 S9 错误；③设备**不改变状态**（保持当前状态，不进入非法状态）；④记录非法转换日志，包含当前状态、请求的转换、消息内容（hex），便于排查。状态机的作用：①**唯一的状态管理者**——所有状态变化必须经过状态机，不允许绕过状态机直接改状态；②**合法边校验**——只允许预定义的状态转换，非法转换被拦截；③**副作用触发**——状态转换成功后触发副作用（事件、日志、通知上层）；④**可测试性**——状态机可以独立测试，验证所有合法边和非法边；⑤**可预测性**——系统行为可预测，不会进入未知状态。状态机是 GEM 内核稳定性的基石。

6. **资源耗尽时优雅降级是什么意思 / 为什么不能直接崩溃**：**优雅降级**（Graceful Degradation）是指系统在资源不足时，不崩溃，而是降低服务质量（如拒绝新请求、限流、关闭非核心功能），保证核心功能继续运行，等资源释放后自动恢复正常。例如：①队列满时拒绝新命令（回 ACKC10=5），但已入队的命令继续执行；②内存不足时清理 Spool 中最旧的记录、触发 GC，但不停止消息处理；③线程池不足时限流（降低消息处理速率），但不崩溃。为什么不能直接崩溃：①GEM 内核运行在 FAB 生产环境，崩溃会导致生产中断、晶圆报废、经济损失；②设备可能正在执行工艺，崩溃可能导致设备进入未知状态（如腔体未清洗、气路未关闭），有安全风险；③崩溃后恢复需要人工干预（重启软件、重新建链、重新配置），恢复时间长，影响生产；④优雅降级可以在资源释放后自动恢复，无需人工干预，提高系统可用性。原则：**永远不崩溃，永远尝试恢复**，即使资源耗尽也要保证核心功能（通信、状态管理、命令执行）继续运行。

## 二、参考实现（异常处理框架）

### GlobalExceptionHandler.cs
```csharp
using EapLab.Secs2;
using EapLab.Transport.Logging;

namespace EapLab.Gem.ExceptionHandling;

/// <summary>全局异常处理器：捕获所有异常，根据类型分发处理。</summary>
public sealed class GlobalExceptionHandler
{
    private readonly ILogSink _log;
    private readonly S9ErrorSender _s9Sender;
    private readonly IStateResync _stateResync;
    private readonly IReconnector _reconnector;

    public GlobalExceptionHandler(ILogSink log, S9ErrorSender s9Sender,
                                    IStateResync stateResync, IReconnector reconnector)
    {
        _log = log;
        _s9Sender = s9Sender;
        _stateResync = stateResync;
        _reconnector = reconnector;
    }

    /// <summary>消息处理异常入口。</summary>
    public void HandleMessageException(Exception ex, HsmsHeader header, SecsItem? body, byte[] rawBytes)
    {
        try
        {
            _log.Log(LogDir.ERR, $"Message exception: S{header.Stream}F{header.Function} - {ex.Message}");
            _log.Log(LogDir.ERR, $"Raw hex: {BitConverter.ToString(rawBytes).Replace("-", " ")}");
            _log.Log(LogDir.ERR, $"Stack trace: {ex.StackTrace}");

            switch (ex)
            {
                case SecsFormatException formatEx:
                    // 消息格式错误 → 回 S9F7
                    _s9Sender.SendS9F7(header, formatEx.Message);
                    break;
                case SecsTooLongException tooLongEx:
                    // 数据太长 → 回 S9F9
                    _s9Sender.SendS9F9(header, tooLongEx.Message);
                    break;
                case TimeoutException timeoutEx:
                    // 超时 → 记录日志，上层负责重发
                    _log.Log(LogDir.WARN, $"Timeout: {timeoutEx.Message}");
                    break;
                case CommunicationException commEx:
                    // 通信异常 → 触发重连
                    _log.Log(LogDir.ERR, $"Communication error: {commEx.Message}");
                    _reconnector.TriggerReconnect();
                    break;
                case InvalidStateException stateEx:
                    // 非法状态 → 拒绝转换 + 状态同步
                    _log.Log(LogDir.ERR, $"Invalid state: {stateEx.Message}");
                    _stateResync.RequestResync();
                    break;
                default:
                    // 未知异常 → 记录详细日志，尝试恢复
                    _log.Log(LogDir.ERR, $"Unexpected exception: {ex.GetType().Name} - {ex.Message}");
                    // 不崩溃，继续运行
                    break;
            }
        }
        catch (Exception handlerEx)
        {
            // 异常处理器本身也不能崩溃
            _log.Log(LogDir.ERR, $"Exception handler failed: {handlerEx.Message}");
        }
    }

    /// <summary>后台线程异常入口（防止未捕获异常导致进程崩溃）。</summary>
    public void HandleBackgroundException(Exception ex, string threadName)
    {
        _log.Log(LogDir.ERR, $"Background exception in '{threadName}': {ex.Message}");
        _log.Log(LogDir.ERR, $"Stack trace: {ex.StackTrace}");
        // 不崩溃，尝试恢复（如重启后台线程）
    }
}

// 自定义异常类型
public class SecsFormatException : Exception { public SecsFormatException(string msg) : base(msg) { } }
public class SecsTooLongException : Exception { public SecsTooLongException(string msg) : base(msg) { } }
public class CommunicationException : Exception { public CommunicationException(string msg) : base(msg) { } }
public class InvalidStateException : Exception { public InvalidStateException(string msg) : base(msg) { } }

public interface IStateResync { void RequestResync(); }
public interface IReconnector { void TriggerReconnect(); }
```

### S9ErrorSender.cs
```csharp
namespace EapLab.Gem.ExceptionHandling;

/// <summary>S9 错误发送器。</summary>
public sealed class S9ErrorSender
{
    private readonly HsmsConnection _conn;
    private readonly ILogSink _log;

    public S9ErrorSender(HsmsConnection conn, ILogSink log)
    {
        _conn = conn;
        _log = log;
    }

    /// <summary>S9F3: 未定义的 Stream。</summary>
    public void SendS9F3(HsmsHeader header, string reason)
        => SendS9(3, header, reason);

    /// <summary>S9F5: 未定义的 Function。</summary>
    public void SendS9F5(HsmsHeader header, string reason)
        => SendS9(5, header, reason);

    /// <summary>S9F7: 非法的数据。</summary>
    public void SendS9F7(HsmsHeader header, string reason)
        => SendS9(7, header, reason);

    /// <summary>S9F9: 数据太长。</summary>
    public void SendS9F9(HsmsHeader header, string reason)
        => SendS9(9, header, reason);

    private void SendS9(byte function, HsmsHeader header, string reason)
    {
        _log.Log(LogDir.WARN, $"S9F{function}: S{header.Stream}F{header.Function} - {reason}");
        // S9 body 通常包含原始消息的 header（10 字节），用于 Host 定位是哪条消息出错
        var body = SecsItem.B(header.Encode(0)); // 简化：原始消息 header 作为 body
        _conn.SendPrimaryAsync(9, function, body); // S9 是 W=0，不需要 Host 回
    }
}
```

### StateConsistencyChecker.cs
```csharp
namespace EapLab.Gem.ExceptionHandling;

/// <summary>状态一致性检查器：定期查询设备状态，对比 Host 缓存，不一致时重新同步。</summary>
public sealed class StateConsistencyChecker : IStateResync
{
    private readonly GemStateMachine _gemState;
    private readonly HsmsConnection _conn;
    private readonly ILogSink _log;
    private readonly TimeSpan _checkInterval = TimeSpan.FromSeconds(30);
    private CancellationTokenSource? _cts;
    private bool _resyncRequested;

    public StateConsistencyChecker(GemStateMachine gemState, HsmsConnection conn, ILogSink log)
    {
        _gemState = gemState;
        _conn = conn;
        _log = log;
    }

    public void Start()
    {
        _cts = new CancellationTokenSource();
        _ = Task.Run(() => RunAsync(_cts.Token));
    }

    public void Stop() => _cts?.Cancel();

    public void RequestResync() => _resyncRequested = true;

    private async Task RunAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            try
            {
                await Task.Delay(_checkInterval, ct);
                if (_resyncRequested || _gemState.CommState == GemCommState.Online)
                {
                    await CheckAndResyncAsync();
                    _resyncRequested = false;
                }
            }
            catch (OperationCanceledException) { break; }
            catch (Exception ex)
            {
                _log.Log(LogDir.ERR, $"State consistency check failed: {ex.Message}");
            }
        }
    }

    private async Task CheckAndResyncAsync()
    {
        // 查询设备通信状态（简化：用 S1F1 心跳判断）
        try
        {
            // 实际应查询通信状态/控制状态 SV
            // 这里简化：如果连接断开，标记 OFF-LINE
            if (!_conn.IsConnected)
            {
                if (_gemState.CommState == GemCommState.Online)
                {
                    _log.Log(LogDir.WARN, "State inconsistency: Host thinks ONLINE but connection is down");
                    _gemState.RequestOffline(); // 同步为 OFF-LINE
                }
            }
        }
        catch (Exception ex)
        {
            _log.Log(LogDir.WARN, $"State check failed, will retry: {ex.Message}");
        }
    }
}
```

## 三、异常处理速查表
| 异常类型 | 检测方法 | 处理策略 | 恢复机制 |
|---|---|---|---|
| 消息格式错误 | 解析时类型/长度检查 | 回 S9F7/S9F9 或 ACKC 非 0 | 记录日志，等待 Host 重发正确消息 |
| 通信超时 | T3 定时器 | 有限次重发（最多 3 次）| 超过后记录错误，设备端进入 Spool |
| 连接断开 | TCP/Linktest 检测 | 标记 OFF-LINE + Spool + 重连 | 指数退避重连，重连后重新建链+重发 Spool |
| 状态不一致 | 定期查询设备状态 | 以设备状态为准，重新同步 | S1F13/S1F17 重新建链，查询 SV 更新状态 |
| 非法状态转换 | 状态机 CanTransition | 拒绝消息，不改变状态 | 记录日志，等待合法转换 |
| 资源耗尽 | 定期检查内存/队列/线程池 | 优雅降级（拒绝/限流/清理）| 资源释放后自动恢复正常 |

## 四、今日易错点
1. 消息格式错误时抛出未捕获异常（应该捕获并回 S9 或 ACKC 非 0，不崩溃）。
2. 通信断开后停止执行命令（通信不影响设备内部运行，命令继续执行，只是不通知 Host）。
3. 状态不一致时以 Host 缓存为准（应该以设备状态为准，设备是权威来源）。
4. 非法状态转换时改变状态（应该拒绝转换，保持当前状态，状态机是唯一管理者）。
5. 资源耗尽时崩溃（应该优雅降级，拒绝新请求而不是崩溃）。
6. S9 和 ACKC 非 0 混用（S9=消息不支持，ACKC=消息支持但条件不满足）。
7. 重连后不重发 Spool 缓存（应该重发，保证数据不丢失）。
8. 异常日志不包含原始消息 hex（应该包含，便于排查）。
9. 后台线程没有全局异常捕获（应该有，防止未捕获异常导致进程崩溃）。
10. 异常处理后不尝试恢复（应该尝试恢复，如重连、重试、状态同步，而不是只记录日志）。
