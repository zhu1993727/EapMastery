## 二、背景知识（先读，20 分钟）

### 1. 为什么需要压力测试
- GEM 内核运行在 FAB 生产环境，必须 7×24 小时稳定运行。
- 极端场景下（如多台设备同时上报、工艺执行中高频事件、报警风暴），GEM 内核可能出现：
  - 消息积压（队列满，新消息被丢弃）
  - 延迟增大（事件上报延迟从毫秒级变秒级）
  - 内存泄漏（长时间运行后内存持续增长）
  - CPU 占用过高（编码/解码消耗大量 CPU）
  - 死锁/竞态（多线程访问共享资源）
- 压力测试的目的是在上线前发现这些问题，保证生产环境的稳定性。

### 2. 5 个压力测试场景

#### 场景1：高频事件上报
- **测试方法**：模拟设备以 1000 条/秒的频率触发事件（S6F11），持续 60 秒，共 60000 条事件。
- **验证指标**：
  - 吞吐量：实际能处理多少条/秒
  - 延迟：从事件触发到 Host 收到 S6F11 的平均延迟、P99 延迟
  - 错误率：有多少条事件被丢弃或发送失败
  - 内存/CPU：测试前后的内存变化、CPU 峰值
- **预期**：吞吐量 ≥ 500 条/秒，平均延迟 ≤ 100ms，错误率 ≤ 1%。

#### 场景2：命令队列满
- **测试方法**：快速发送 100 条 START 命令（超过队列最大长度 10），验证队列满时的行为。
- **验证指标**：
  - 前 10 条命令被接受（ACKC10=0），后续命令被拒绝（ACKC10=5 设备忙）
  - 队列中的命令按顺序执行，不丢失、不重复
  - 队列满时不崩溃、不死锁
- **预期**：队列满时新命令被正确拒绝，已入队的命令正常执行。

#### 场景3：报警风暴
- **测试方法**：模拟设备在 1 秒内触发 100 个不同的报警（S5F1），验证报警上报和使能/禁用机制。
- **验证指标**：
  - 所有报警都被正确设置（状态 SET）
  - 所有报警都通过 S5F1 上报（如果使能）
  - 报警风暴时不影响命令执行和事件上报
  - 报警去重：同一个报警重复触发时不重复上报（如果已 SET）
- **预期**：100 个报警都正确设置和上报，不影响其他功能。

#### 场景4：Spool 容量满
- **测试方法**：通信中断后，触发 15000 条事件（超过 Spool 最大容量 10000），验证容量满时的行为。
- **验证指标**：
  - 前 10000 条事件被缓存，后续 5000 条被丢弃（FIFO 策略）
  - Spool 内存占用不超过上限
  - 通信恢复后，缓存的 10000 条事件被正确重发
  - 重发完成后 Spool 清空，内存释放
- **预期**：容量满时按 FIFO 丢弃最旧的，不崩溃，恢复后正确重发。

#### 场景5：HSMS 连接压力
- **测试方法**：模拟 Host 频繁断开/重连（每 2 秒一次，共 50 次），验证重连机制和状态恢复。
- **验证指标**：
  - 每次重连都能成功建立 Select 状态
  - 重连后通信状态正确恢复（ON-LINE/OFF-LINE）
  - 重连过程中不崩溃、不内存泄漏
  - 重连后 Spool 中的事件被正确重发
- **预期**：50 次重连全部成功，状态正确恢复，无内存泄漏。

### 3. 性能指标采集方法
- **吞吐量**：记录单位时间内成功处理的消息数（条/秒）。
- **延迟**：在消息中嵌入时间戳，计算从发送到接收的时间差（ms）。
- **内存占用**：测试前后用 `GC.GetTotalMemory(true)` 或任务管理器记录进程内存（MB）。
- **CPU 占用**：用任务管理器或性能计数器记录 CPU 峰值（%）。
- **错误率**：失败消息数 / 总消息数 × 100%。
- 测试环境：.NET 8、Release 模式、无调试器附加、关闭其他占用资源的程序。
