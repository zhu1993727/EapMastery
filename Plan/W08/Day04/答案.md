# W08 · Day04 答案与参考实现

## 一、自测题标准答案
1. **为什么需要压力测试 / 生产环境可能遇到哪些极端场景**：GEM 内核运行在 FAB 生产环境，必须 7×24 小时稳定运行，任何故障都可能导致生产中断、晶圆报废、经济损失。压力测试在上线前模拟极端场景，发现性能瓶颈和稳定性问题，保证生产环境的可靠性。生产环境可能遇到的极端场景：①**高频事件上报**——多腔体设备同时加工，每秒几十上百条 S6F11；②**命令队列满**——MES 批量下发命令，设备来不及执行；③**报警风暴**——设备故障导致短时间内大量报警；④**Spool 容量满**——Host 长时间断开（如 Host 重启、网络故障），设备缓存大量事件；⑤**HSMS 连接压力**——网络不稳定导致频繁断开/重连；⑥**大配方传输**——几 MB 的配方通过多块消息传输；⑦**长时间运行**——连续运行几个月不重启，内存泄漏和资源耗尽。
2. **高频事件上报可能的瓶颈 / 怎么优化**：可能的瓶颈：①**消息编码慢**——每条 S6F11 都要编码 SECS-II Item，频繁创建对象导致 GC 压力；②**队列锁竞争**——EventReportEngine 和发送线程共享队列，高频入队/出队导致锁竞争；③**网络发送慢**——TCP 发送缓冲区满，发送线程阻塞；④**Host 处理慢**——Host 回 S6F12 慢，导致待确认队列积压；⑤**日志 I/O 慢**——每条消息都写日志，磁盘 I/O 成为瓶颈。优化方法：①**对象池**——复用 SecsItem 对象，减少 GC；②**无锁队列**——用 ConcurrentQueue 或 Disruptor 模式减少锁竞争；③**批量发送**——合并多条小消息为一次 TCP 发送（Nagle 算法或应用层批量）；④**异步日志**——用异步日志框架（如 Serilog），日志写入队列，后台线程批量写磁盘；⑤**编码缓存**——缓存重复的消息头和固定字段，只编码变化部分；⑥**背压机制**——队列满时通知上游降速，而不是丢弃。
3. **命令队列满时怎么处理 / 拒绝新命令还是丢弃旧命令**：命令队列满时，应该**拒绝新命令**（回 ACKC10=5 设备忙），而不是丢弃旧命令。原因：①旧命令已经被 Host 接受（ACKC10=0），Host 期望它被执行，丢弃旧命令会导致 Host 永远等不到执行结果（命令丢失）；②拒绝新命令时，Host 收到 ACKC10=5，知道设备忙，可以稍后重试或排队到 MES 层；③旧命令是按顺序入队的，丢弃旧命令会破坏命令执行顺序（FIFO 语义）。这是队列的标准设计——队列满时拒绝入队，而不是覆盖已有元素。部分设备实现可能支持"高优先级命令抢占"（如 STOP/ABORT 可以中断正在执行的命令，而不是排队），但普通命令应该被拒绝。
4. **Spool 容量满时 FIFO 丢弃最旧 vs 拒绝新记录，哪种更好 / 为什么**：取决于业务场景，但**FIFO 丢弃最旧（保留最新）**通常更适合 GEM 场景。原因：①FAB 中，最新的事件/报警更重要——Host 恢复连接后，最关心的是设备当前状态和最近发生的事件，最旧的事件（如几小时前的 Wafer Start）可能已经不重要了；②拒绝新记录会导致最新的事件/报警丢失，而 Host 恢复后最需要的就是最新的状态；③FIFO 丢弃最旧是环形缓冲区的标准设计，实现简单，内存占用可控。但也有例外：如果业务要求"所有事件都不能丢失"（如合规要求），则应该拒绝新记录并告警（通知操作员 Spool 满，需要尽快恢复通信），而不是丢弃。专家实践：默认 FIFO 丢弃最旧，同时配置告警阈值（如 Spool 使用率超过 80% 时告警），在容量满之前通知操作员恢复通信。
5. **报警风暴时怎么保证不丢失、不重复、不影响其他功能**：①**不丢失**：报警设置时先写入 AlarmStore（状态 SET），再尝试发送 S5F1；如果通信中断，Spool 缓存报警，恢复后重发；AlarmStore 是持久化的（内存+Flash），断电不丢。②**不重复**：AlarmStore.Set 方法检查当前状态，如果已经是 SET，不重复触发 OnAlarmChanged 事件（不重复发 S5F1）；Host 端根据 ALID+时间戳去重，重复的 S5F1 不重复处理。③**不影响其他功能**：报警上报是异步的（独立线程或线程池），不阻塞命令执行和事件上报；报警风暴时限流（如每秒最多发 100 条 S5F1），超出的进入 Spool 缓存，避免网络和 Host 过载；AlarmStore 用 ConcurrentDictionary，无锁读取，不影响其他线程访问。④**报警合并**：短时间内多个相关报警可以合并为一条"报警组"上报（如温度过高和温度过高预警合并），减少消息数量。
6. **压力测试发现内存泄漏怎么定位和修复**：定位方法：①**对比测试前后内存**——用 `GC.GetTotalMemory(true)` 或任务管理器记录测试前后的进程内存，如果持续增长不释放，可能有泄漏；②**内存快照**——用 Visual Studio 内存探查器或 dotMemory 抓取测试前后的内存快照，对比对象数量增长，定位哪种对象泄漏；③**GC 根分析**——对泄漏的对象做 GC 根分析，找到是谁持有引用不释放（如事件订阅未取消、静态集合未清理、定时器未释放、Dispose 未调用）；④**长时间运行测试**——运行几小时甚至几天，观察内存增长趋势。修复方法：①**取消事件订阅**——对象销毁时取消所有事件订阅（-=）；②**清理静态集合**——定期清理静态字典/队列中的过期对象；③**释放定时器**——Timer/CancellationTokenSource 用完后 Dispose；④**using 模式**——实现 IDisposable 的对象用 using 或 try/finally 确保 Dispose；⑤**对象池**——频繁创建销毁的对象用对象池复用，减少 GC 压力；⑥**弱引用**——缓存用 WeakReference，允许 GC 回收。

### PressureTestBase.cs
```csharp
using System.Diagnostics;

namespace EapLab.Tests.Pressure;

/// <summary>压力测试基类：记录吞吐量、延迟、内存、CPU。</summary>
public abstract class PressureTestBase
{
    public string Name { get; }
    protected readonly ILogSink Log = new ConsoleLogSink();

    protected PressureTestBase(string name) => Name = name;

    public PressureTestResult Run(int durationSeconds = 60)
    {
        Console.WriteLine($"=== Pressure Test: {Name} ===");
        var sw = Stopwatch.StartNew();
        long totalMessages = 0;
        long totalErrors = 0;
        var latencies = new List<long>();
        var memBefore = GC.GetTotalMemory(true);
        var cpuBefore = Process.GetCurrentProcess().TotalProcessorTime;

        try
        {
            Execute(durationSeconds, ref totalMessages, ref totalErrors, latencies);
        }
        catch (Exception ex)
        {
            Console.WriteLine($"Test failed with exception: {ex.Message}");
            totalErrors++;
        }

        sw.Stop();
        var memAfter = GC.GetTotalMemory(true);
        var cpuAfter = Process.GetCurrentProcess().TotalProcessorTime;

        var result = new PressureTestResult
        {
            Name = Name,
            DurationMs = sw.ElapsedMilliseconds,
            TotalMessages = totalMessages,
            TotalErrors = totalErrors,
            Throughput = totalMessages / (sw.ElapsedMilliseconds / 1000.0),
            AvgLatencyMs = latencies.Count > 0 ? latencies.Average() : 0,
            P99LatencyMs = latencies.Count > 0 ? latencies.OrderBy(x => x).ElementAt((int)(latencies.Count * 0.99)) : 0,
            ErrorRate = totalMessages > 0 ? (double)totalErrors / totalMessages * 100 : 0,
            MemoryDeltaMB = (memAfter - memBefore) / (1024.0 * 1024.0),
            CpuTimeMs = (cpuAfter - cpuBefore).TotalMilliseconds
        };

        Console.WriteLine($"  Duration: {result.DurationMs}ms");
        Console.WriteLine($"  Total: {totalMessages} messages, {totalErrors} errors");
        Console.WriteLine($"  Throughput: {result.Throughput:F1} msg/s");
        Console.WriteLine($"  Avg latency: {result.AvgLatencyMs:F1}ms, P99: {result.P99LatencyMs:F1}ms");
        Console.WriteLine($"  Error rate: {result.ErrorRate:F2}%");
        Console.WriteLine($"  Memory delta: {result.MemoryDeltaMB:F2}MB");
        Console.WriteLine($"  CPU time: {result.CpuTimeMs:F0}ms");
        return result;
    }

    protected abstract void Execute(int durationSeconds, ref long totalMessages, ref long totalErrors, List<long> latencies);
}

public sealed class PressureTestResult
{
    public string Name { get; init; } = "";
    public long DurationMs { get; init; }
    public long TotalMessages { get; init; }
    public long TotalErrors { get; init; }
    public double Throughput { get; init; }
    public double AvgLatencyMs { get; init; }
    public double P99LatencyMs { get; init; }
    public double ErrorRate { get; init; }
    public double MemoryDeltaMB { get; init; }
    public double CpuTimeMs { get; init; }
}
```

### 场景1：高频事件上报
```csharp
public class HighFrequencyEventTest : PressureTestBase
{
    public HighFrequencyEventTest() : base("High Frequency Event Report") { }

    protected override void Execute(int durationSeconds, ref long totalMessages, ref long totalErrors, List<long> latencies)
    {
        var store = new ReportStore(new[] { 100, 101 });
        store.Define(1, new[] { 100, 101 });
        var linkStore = new EventReportLinkStore(new[] { 3001 }, store);
        linkStore.Link(3001, new[] { 1 });
        var varProvider = new FakeVariableProvider(new() { [100] = SecsItem.F4(25.5f), [101] = SecsItem.U2(100) });
        var conn = new MockHsmsConnection();
        var engine = new EventReportEngine(linkStore, store, varProvider, Log);

        var cts = new CancellationTokenSource(TimeSpan.FromSeconds(durationSeconds));
        var tasks = Enumerable.Range(0, 4).Select(_ => Task.Run(() =>
        {
            var sw = Stopwatch.StartNew();
            while (!cts.IsCancellationRequested)
            {
                sw.Restart();
                var body = engine.TriggerEvent(3001);
                if (body != null)
                {
                    conn.SendPrimaryAsync(6, 11, body);
                    latencies.Add(sw.ElapsedMilliseconds);
                    Interlocked.Increment(ref totalMessages);
                }
                else
                {
                    Interlocked.Increment(ref totalErrors);
                }
            }
        })).ToArray();
        Task.WaitAll(tasks);
    }
}
```

### 场景2：命令队列满
```csharp
public class CommandQueueFullTest : PressureTestBase
{
    public CommandQueueFullTest() : base("Command Queue Full") { }

    protected override void Execute(int durationSeconds, ref long totalMessages, ref long totalErrors, List<long> latencies)
    {
        var executor = new SlowExecutor(delayMs: 100); // 每条命令执行 100ms
        var engine = new RemoteCommandEngine(executor, Log);
        var defStore = new CommandDefinitionStore();
        defStore.RegisterStandardCommands();
        var handler = new S2F41Handler(defStore, engine, Log, () => true);

        int accepted = 0, rejected = 0;
        for (int i = 0; i < 100; i++) // 快速发 100 条命令
        {
            var body = SecsItem.L(
                SecsItem.A("START"),
                SecsItem.L(
                    SecsItem.L(SecsItem.A("LOTID"), SecsItem.A($"LOT{i:D3}")),
                    SecsItem.L(SecsItem.A("RECIPE"), SecsItem.A("RCP_A"))
                )
            );
            var reply = handler.Handle(body);
            var ackc10 = ((SecsU1)((SecsList)reply).Items[0]).Values[0];
            if (ackc10 == 0) accepted++;
            else rejected++;
            totalMessages++;
        }

        Console.WriteLine($"  Accepted: {accepted}, Rejected: {rejected}");
        // 等待队列中的命令执行完
        Thread.Sleep(2000);
    }
}
```

## 三、性能优化建议（常见瓶颈与解决方案）
| 瓶颈 | 现象 | 优化方案 |
|---|---|---|
| SECS-II 编码慢 | CPU 高，GC 频繁 | 对象池复用 SecsItem、编码缓存固定字段 |
| 队列锁竞争 | 吞吐量上不去，延迟抖动 | ConcurrentQueue、Disruptor 模式、分片队列 |
| 日志 I/O 慢 | 磁盘 I/O 高，延迟大 | 异步日志、批量写、降低日志级别 |
| 网络发送慢 | 发送线程阻塞，队列积压 | 批量发送、增大 TCP 缓冲区、背压机制 |
| 内存泄漏 | 长时间运行内存增长 | 内存快照分析、取消事件订阅、释放定时器 |
| 报警风暴 | 网络过载，Host 处理不过来 | 限流、报警合并、Spool 缓存 |
| Spool 重发风暴 | 通信恢复后瞬间大量消息 | 限速重发、优先级排序、增量重发 |

## 四、今日易错点
1. 压力测试在 Debug 模式下跑（结果不准，必须 Release 模式、无调试器）。
2. 只测吞吐量不测延迟（吞吐量高但延迟大也不行，必须同时测 P99 延迟）。
3. 测试前后不记录内存（无法发现内存泄漏）。
4. 命令队列满时丢弃旧命令（应该拒绝新命令，旧命令已被接受不能丢）。
5. Spool 容量满时拒绝新记录（默认应该 FIFO 丢弃最旧，保留最新）。
6. 报警风暴时同步发送（应该异步+限流，避免阻塞其他功能）。
7. 压力测试只跑几秒（应该跑至少 60 秒，最好几小时，才能发现内存泄漏和稳定性问题）。
8. 不做 GC 回收就测内存（测试前后应调用 GC.GetTotalMemory(true) 强制回收，得到准确的内存增量）。
