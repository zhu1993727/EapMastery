## 二、背景知识（先读，30 分钟）

### 1. Spool 是什么
- **Spool（Simultaneous Peripheral Operations On-Line，假脱机）**：在 GEM 中，Spool 是设备在通信中断时，把要发给 Host 的事件报告（S6F11）和报警（S5F1）缓存到本地存储（内存或 Flash），等通信恢复后再重发给 Host 的机制。
- **作用**：保证通信中断期间的事件/报警数据不丢失——Host 恢复连接后能收到中断期间的所有事件和报警，而不是只收到恢复后的。
- **为什么需要 Spool**：FAB 中设备可能因为网络故障、Host 重启、维护等原因短暂断开连接，如果没有 Spool，中断期间的工艺数据（如 Wafer Start/End、Lot End）和报警就丢失了，Host 无法追溯生产历史和异常。Spool 保证数据完整性。
- **Spool 是可选的 GEM 能力**：不是所有设备都支持 Spool，Host 建链后需要查询设备能力（S1F3 或设备手册）确认是否支持。支持 Spool 的设备通常有 Spool 状态变量（SV）和 Spool 控制消息（S2F43/S2F44）。

### 2. Spool 的触发条件
Spool 在以下情况被触发（设备开始缓存事件/报警）：
1. **通信 OFF-LINE**：Host 发 S1F15 请求离线，或设备主动离线（如急停、故障），通信状态从 ON-LINE→OFF-LINE。
2. **HSMS 断开**：TCP 连接断开、HSMS Select 丢失（Deselect 或超时），传输层连接中断。
3. **Host 不回确认**：设备发 S6F11/S5F1 后，Host 在 T3 时间内没回 S6F12/S5F2，设备可能认为通信异常，开始 Spool（取决于设备实现）。
- 触发 Spool 后，设备的事件/报警上报机制切换为"缓存模式"：事件/报警不再直接发给 Host，而是写入 Spool 缓存。

### 3. Spool 缓存的存储方式
- **存储位置**：
  - **内存（RAM）**：速度快，但断电丢失。适合短期缓存（分钟级）。
  - **非易失性存储（Flash/EEPROM/硬盘）**：断电不丢，适合长期缓存（小时级/天级）。
  - 具体以设备实现为准，先进设备通常用非易失性存储，保证断电不丢。
- **缓存内容**：每条缓存记录包含：
  - 消息类型（S6F11 事件报告 / S5F1 报警）
  - 完整的消息 body（S6F11 的 DATAID+CEID+报告列表，或 S5F1 的 ALID+ALTX）
  - 时间戳（事件/报警发生的时间，用于 Host 排序和追溯）
  - 序列号（用于去重和排序）
- **缓存格式**：设备自定义的二进制格式或序列化格式，Host 不需要解析缓存内容（设备重发时还原为标准的 S6F11/S5F1 消息）。

### 4. Spool 的容量管理
- **容量限制**：Spool 缓存有最大容量（如最多 10000 条记录，或最多 10MB 空间），由设备定义。
- **容量满时的策略**（取决于设备实现和配置）：
  1. **丢弃最旧的记录**（FIFO，先进先出，保留最新的）。
  2. **拒绝新的记录**（停止缓存，新事件/报警直接丢弃）。
  3. **覆盖最旧的记录**（循环写入，类似环形缓冲区）。
- **Host 应该监控 Spool 容量**：通过 S2F43 查询 Spool 状态（已用容量、剩余容量），在容量满之前恢复通信或清空 Spool。
- **Spool 容量是设备能力的一部分**：Host 建链后应该查询设备的 Spool 容量，评估通信中断的最大可容忍时间。

### 5. Spool 的恢复流程（必背）
```
通信恢复（ON-LINE + Select 重新建立）
    │
    ▼
1. 设备检测到通信恢复（通信状态 OFF-LINE→ON-LINE，或 Select 重新建立）
    │
    ▼
2. 设备查询 Spool 缓存：是否有未发送的记录？
    ├─ 无 → 切换回正常上报模式，事件/报警直接发给 Host
    └─ 有 → 继续
    │
    ▼
3. 设备按时间顺序（或序列号顺序）重发缓存的 S6F11/S5F1
    │
    ├─ 每条消息带原始的 body 和时间戳（可能带"Spool 重发"标志，取决于设备实现）
    ├─ Host 回 S6F12/S5F2 确认
    ├─ 设备收到确认后，从 Spool 缓存中删除该记录
    └─ 如果 Host 不回确认，设备可能重发或暂停（取决于设备实现）
    │
    ▼
4. 全部重发完成后，Spool 缓存清空
    │
    ▼
5. 设备切换回正常上报模式，新的事件/报警直接发给 Host
```
- **重发顺序**：通常按时间顺序（最早的先重发），保证 Host 收到的事件/报警按发生时间排序。
- **重发速率**：设备可能控制重发速率（如每秒 10 条），避免瞬间大量消息导致 Host 过载或网络拥塞。
- **去重机制**：Host 应该根据消息的序列号或时间戳+内容去重——如果设备重发了同一条消息（因为之前的确认丢失），Host 不应该重复处理。设备也可能在重发时带"Spool 重发"标志，Host 可以识别。

### 6. S2F43/S2F44（Spool 控制）
```
S2F43 Spooling Control Request (Host → Equipment, W=1)
body = L,2[
  U1 SPCTL,              // Spool 控制操作码（1=查询状态、2=清空、3=启用、4=禁用，具体以标准为准）
  <参数>                  // 操作参数（取决于操作码，查询时无参数，清空时无参数）
]

S2F44 Spooling Control Acknowledge (Equipment → Host, W=0)
body = L,2[
  U1 ACKC,               // 操作结果（0=成功，非0=失败）
  <Spool 状态>            // 查询操作时返回 Spool 状态（已用容量、剩余容量、记录数等）
]
```
- **S2F43/S2F44 是 Host 控制 Spool 的接口**：
  - **查询 Spool 状态**：Host 发 S2F43(SPCTL=1)，设备回 S2F44，返回 Spool 已用容量、剩余容量、记录数、是否启用等。
  - **清空 Spool**：Host 发 S2F43(SPCTL=2)，设备清空 Spool 缓存（删除所有未发送的记录），回 S2F44 确认。
  - **启用/禁用 Spool**：Host 发 S2F43(SPCTL=3/4)，设备启用或禁用 Spool 功能，回 S2F44 确认。
- **具体操作码和 body 格式以 E30 标准和设备实现为准**，不同设备可能有差异。今天讲概念和标准流程，具体实现看设备手册。
- **Host 建链后通常先查询 Spool 状态**（S2F43），如果有缓存记录，等待设备重发或主动请求重发；通信恢复后可以清空 Spool（S2F43）释放空间。

### 7. Spool 和正常上报的关系
- **正常模式**（通信 ON-LINE + Select 建立）：事件/报警直接发给 Host（S6F11/S5F1），不经过 Spool。
- **Spool 模式**（通信中断）：事件/报警写入 Spool 缓存，不发给 Host。
- **恢复模式**（通信刚恢复）：设备先重发 Spool 缓存中的记录，全部发完后切换回正常模式。
- **Spool 是透明的**：Host 不需要知道设备是否在 Spool——Host 收到的 S6F11/S5F1 格式是一样的，不管是实时上报还是 Spool 重发。Host 只需要根据时间戳和序列号去重。
- **Spool 不影响设备内部状态**：Spool 只缓存"要发给 Host 的消息"，不影响设备内部的事件/报警状态机、命令执行、工艺控制。设备在通信中断时仍然正常运行，只是不通知 Host。
