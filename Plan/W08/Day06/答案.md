# W08 · Day06 答案与参考实现

## 一、自测题标准答案
1. **各阶段用到的 W2-W8 能力**：
   - 阶段1（连接与建链）：W2 HSMS 连接/Select、W5 GEM 通信状态机（S1F13/S1F17/S1F18）
   - 阶段2（能力发现与配置）：W6 数据采集体系（S1F3/S1F5/S1F7/S2F33/S2F35）、W7 报警（S5F5/S5F3）、W7 配方（S7F3）
   - 阶段3（正常生产）：W5 控制状态/远程命令（S2F41/S2F42）、W6 事件上报（S6F11/S6F12）、W7 报警（S5F1/S5F2）
   - 阶段4（通信断开与 Spool）：W8 Spool 机制（通信中断触发 Spool、事件/报警入队缓存）
   - 阶段5（重连恢复与补收数据）：W5 通信状态机（重新建链）、W8 Spool 重发（按时间顺序重发、确认后删除）、W6 重新配置数据采集
   - 阶段6（继续生产与优雅断开）：W5 远程命令/通信状态（S2F41/S1F15/S1F16）、W2 HSMS Deselect/TCP 断开
   - 全程：W3 SECS-II 编码/解码、W4 事务模型（primary/reply/SystemBytes/W 位）、W8 异常处理（消息格式错误/超时/状态不一致）

2. **通信断开后命令执行和工艺控制会停止吗 / 为什么**：**不会停止**。通信断开只影响"设备和 Host 之间的通信"，不影响设备内部的命令执行、工艺控制、报警检测、事件触发。原因：①设备的运行不依赖 Host 的连接——设备是独立的物理设备，有自己的控制器（PLC/运动控制卡/工艺控制器），命令一旦被接受并开始执行，就由设备内部控制器驱动，不需要 Host 持续发送指令；②工艺控制是实时闭环（温度/压力/气体流量由设备内部 PID 控制），不依赖 Host；③报警检测是设备内部的硬件/软件检测，不依赖 Host；④事件触发是设备内部状态变化触发的，不依赖 Host。通信断开后，设备继续运行，只是这些事件和报警不发给 Host，而是写入 Spool 缓存，等通信恢复后补收。这是 GEM 设计的核心原则——**设备独立运行，Host 只是监控和管理方**。

3. **重连后为什么 Host 需要重新配置数据采集和报警 / 设备端配置会丢失吗**：取决于设备实现。①**易失性配置**（Volatile）：大部分设备的 S2F33 报告定义、S2F35 事件关联、S5F3 报警使能是**易失性的**——存在内存中，设备重启或通信断开后会丢失（或恢复为默认值）。所以重连后 Host 需要重新配置，否则设备不会上报事件/报警。②**非易失性配置**（Non-Volatile）：部分设备支持把配置保存到 Flash（通过 S2F43 或设备本地操作），重启后不丢失。但即使配置不丢失，Host 重连后也应该查询当前配置（S1F7 查询报告列表、S5F5 查询报警列表），确认配置是否一致，避免因为设备端配置被修改而导致数据采集异常。③**最佳实践**：Host 重连后，先查询设备当前配置（S1F7/S5F5），如果配置丢失或不一致，重新下发配置（S2F33/S2F35/S5F3），然后再开始生产。这是 FAB 中 MES/EAP 的标准重连流程。

4. **Spool 重发的消息和实时上报的消息格式一样吗 / Host 怎么区分**：**格式完全一样**。Spool 重发的 S6F11/S5F1 和实时上报的消息格式完全相同——Stream/Function/body 都一样，Host 无法从消息格式上区分是实时上报还是 Spool 重发。Host 区分的方法：①**时间戳**：S6F11 body 中通常包含事件触发时间（如果设备在报告中包含时间变量），Host 可以根据时间戳判断这是历史事件还是实时事件；②**序列号/顺序**：Host 维护已收到的事件序列号，如果收到的事件序列号比当前小，说明是 Spool 重发的历史事件；③**通信状态**：Host 知道自己什么时候断开/重连，重连后收到的第一批事件（在重连时间点之前的）就是 Spool 重发的；④**DATAID**：S6F11 的 DATAID 是 Host 配置报告时分配的，Spool 重发时 DATAID 不变，Host 可以根据 DATAID 匹配报告定义。关键：**Spool 对 Host 是透明的**——Host 不需要知道消息是实时还是重发，只需要正常处理（去重、按时间排序、更新状态）。Host 应该有去重机制（根据事件 ID+时间戳），避免 Spool 重发导致重复处理。

5. **报警中断命令后 Host 应该怎么处理**：Host 收到报警（S5F1）和命令失败事件（S6F11 CmdFail）后，应该：①**更新 Lot 状态**：把 Lot 状态从"生产中"改为"异常中断"，记录中断原因（报警代码、中断时的 Wafer 序号、工艺参数）；②**通知操作员**：通过 MES 界面、声光报警、短信/邮件通知操作员，说明设备报警和 Lot 中断情况；③**暂停派工**：暂停向该设备派新的 Lot，直到报警清除且设备恢复正常；④**触发维护流程**：如果是设备故障报警，触发 CMMS（计算机化维护管理系统）创建维护工单，通知工程师维修；⑤**数据采集**：保存报警时的工艺数据（FDC 数据），用于后续根因分析（RCA）；⑥**等待操作员处理**：操作员清除报警后，Host 收到报警清除事件（S5F1 ALCD=Clear 或 S6F11 AlarmClear），确认设备恢复正常；⑦**恢复派工**：设备恢复正常后，Host 重新派工（可以继续中断的 Lot，或派新 Lot）。这是 FAB 中标准的异常处理流程——报警→中断→通知→维护→恢复→继续。

6. **优雅断开为什么要按 S1F15→Deselect→TCP 顺序 / 直接 TCP 断开有什么问题**：优雅断开（Graceful Disconnect）按 S1F15→Deselect→TCP 顺序，是为了让双方都有机会清理状态、保存数据、避免数据丢失。①**S1F15（Request Off-line）**：Host 通知设备"我要断开了"，设备可以：停止接受新命令、完成当前正在执行的命令（或安全中断）、保存当前状态（Spool 中未发送的事件/报警）、触发通信 OFF-LINE 状态变化事件。设备回 S1F16（ACKC1=0）表示同意断开。②**HSMS Deselect**：Host 通知设备"我要取消 Select 了"，设备可以：清理 HSMS 会话状态、停止发送消息（除 S1 通信相关）、保存未确认的消息。设备回 Deselect.rsp 表示同意。③**TCP 断开**：最后才断开 TCP 连接，此时双方都已经清理完状态，没有未完成的事务。**直接 TCP 断开的问题**：①设备不知道 Host 是主动断开还是网络故障，会触发异常重连流程（指数退避重连），而不是优雅停止；②设备可能正在执行命令或发送消息，TCP 断开导致消息丢失（Spool 可能来不及缓存）；③设备状态可能不一致（如 Host 认为已断开但设备认为还在线）；④正在传输的大消息（如配方下载）会中断，导致配方不完整。优雅断开是"双方协商一致的断开"，直接 TCP 断开是"单方面强制断开"，生产环境应该用优雅断开。

## 四、今日易错点
1. 重连后不重新配置数据采集（设备配置可能丢失，导致事件不上报）。
2. Spool 重发后不等待 Host 确认就删除缓存（应等确认后删除，否则数据丢失）。
3. 通信断开后停止命令执行（通信不影响设备内部运行，命令继续执行）。
4. 报警中断后不通知操作员/不暂停派工（应触发完整异常处理流程）。
5. 直接 TCP 断开而不是优雅断开（应按 S1F15→Deselect→TCP 顺序，避免状态不一致和数据丢失）。
6. 重连后不查询设备当前配置就直接生产（应先查询配置，确认一致后再生产）。
7. Spool 重发不限速（瞬间大量消息可能导致 Host 过载，应限速重发）。
8. 报警清除事件不通过 Spool 缓存（通信断开时所有事件/报警都应缓存，包括报警清除）。
9. 命令失败时不记录失败原因（应在 S6F11 CmdFail 中包含失败原因，便于 Host 处理）。
10. 验收时不抓包验证（应抓包确认每条消息的 hex 和顺序，不能只看日志）。
