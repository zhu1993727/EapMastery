# W08 · Day07 答案与参考实现

## 一、GEM 内核阶段自测题（10 题）标准答案

### 1. GEM 内核 8 层架构
| 层 | 名称 | 作用 | 接口/消息 |
|---|---|---|---|
| L1 | 物理层 | TCP/IP 网络连接 | Socket |
| L2 | 传输层 | HSMS 连接、Select、心跳、超时 | HSMS 控制消息（SType 1-9） |
| L3 | 编码层 | SECS-II 消息编码/解码 | Item 模型（L/A/B/I/U/F/Boolean） |
| L4 | 事务层 | primary/reply 配对、SystemBytes、W 位、多块、S9 错误 | 所有 SECS-II 消息 |
| L5 | GEM 状态层 | 通信状态机、控制状态机、状态一致性 | S1F13/F14/F17/F18/F15/F16 |
| L6 | 业务层 | 数据采集、报警、远程命令、配方、Spool | S2F33/35、S6F11、S5F1/3、S2F41、S7F3、S2F43 |
| L7 | 应用层 | 业务流程编排（Lot 生产、异常处理、重连恢复） | 业务逻辑（调用 L6 组件） |
| L8 | CIM 对接层 | 与 MES/FDC/APC/YMS/RMS 等系统对接 | 北向接口（REST/消息队列/数据库） |

### 2. 通信状态 vs 控制状态
- **通信状态（Comm State）**：设备和 Host 之间的通信是否建立。状态：OFF-LINE（默认，未建立通信）→ ON-LINE（已建立通信）。转换：S1F13 建立通信→ON-LINE；S1F15 请求离线→OFF-LINE；通信断开→OFF-LINE。Host 可以通过 S1F17 请求在线（设备同意后 ON-LINE）。
- **控制状态（Control State）**：设备由谁控制。状态：EQUIPMENT OFF-LINE（本地控制，操作员操作）→ ON-LINE（远程控制，Host 发命令）。转换：操作员切本地→EQUIPMENT OFF-LINE；操作员切远程→ON-LINE。**Host 不能直接切换控制状态**，只能由设备本地操作员切换。
- 区别：通信状态是"能不能说话"，控制状态是"听谁的指挥"。通信 ON-LINE 但控制 EQUIPMENT OFF-LINE 时，Host 能查询状态但不能发命令；通信 OFF-LINE 时，控制状态无意义（Host 连不上）。

### 3. 数据采集三层模型
- **变量（Variable，VID）**：设备的状态变量，如温度=100、压力=101。是最小数据单元。S1F3/F4 查询变量列表。
- **报告（Report，RPTID）**：一组变量的集合，如"工艺数据报告"=温度+压力。S2F33/F34 定义报告（采集什么）。
- **事件（Event，CEID）**：设备状态变化的触发点，如 LotStart=3001。S2F35/F36 关联事件和报告（什么时候采集）。
- **上报（S6F11）**：事件触发时，设备采集关联报告中的变量值，通过 S6F11 上报给 Host。body=DATAID+CEID+报告列表。
- 流程：定义变量（设备固有）→ 定义报告（S2F33，选哪些变量）→ 关联事件（S2F35，事件触发时采集哪些报告）→ 事件触发→S6F11 上报。

### 4. 报警 vs 事件
- **报警（Alarm，ALID）**：设备异常状态的通知，有 SET/CLEAR 两个状态。S5F1 上报（ALID+ALCD+ALTX），需要 S5F3 使能才上报。报警是"异常"，需要操作员处理。
- **事件（Event，CEID）**：设备状态变化的通知，无状态（瞬时触发）。S6F11 上报（DATAID+CEID+报告列表），需要 S2F33/S2F35 配置才上报。事件是"正常状态变化"，不需要操作员处理。
- 区别：报警有状态（SET/CLEAR），事件无状态；报警用 S5F1，事件用 S6F11；报警需要 S5F3 使能，事件需要 S2F33/S2F35 配置；报警是异常，事件是正常变化。
- 联系：报警 SET/CLEAR 时也可以触发事件（如 AlarmSet=3201），通过 S6F11 上报，携带报警相关的变量值。

### 5. 远程命令异步执行机制
- Host 发 S2F41（RCMD+参数）→ 设备回 S2F42（ACKC10）。
- ACKC10=0 只表示"命令已接受"（格式正确、参数合法、当前状态允许），**不表示命令已执行**。
- 命令执行是异步的：设备把命令放入命令队列，按顺序执行（PENDING→EXECUTING→COMPLETE/FAILED）。
- 命令执行完成靠**事件通知**：命令开始时发 S6F11（CmdStart=3101），命令完成时发 S6F11（CmdComplete=3102），命令失败时发 S6F11（CmdFail=3103，含失败原因）。
- Host 不能通过 S2F42 判断命令是否完成，必须等待 S6F11 事件。这是 GEM 的异步设计——命令接受和执行分离。

### 6. Spool 完整流程
1. **触发**：通信 OFF-LINE（TCP 断开/HSMS Select 丢失/S1F15 离线）→ 设备切换到 Spooling 模式。
2. **缓存**：后续的 S6F11（事件）和 S5F1（报警）不发送给 Host，写入 Spool 缓存（按时间顺序，FIFO）。
3. **恢复**：通信 ON-LINE（TCP 重连/HSMS Select/S1F13 建链/S1F17 在线）→ 设备切换到 Resending 模式。
4. **重发**：按时间顺序重发 Spool 缓存中的 S6F11/S5F1，限速（如每 100ms 一条），避免 Host 过载。
5. **确认**：每条重发的消息，Host 回 S6F12/S5F2 确认后，设备从 Spool 缓存中删除该记录。
6. **清空**：所有缓存记录都重发并确认后，Spool 缓存清空，设备切换回 Normal 模式（正常上报）。
- 容量满时：FIFO 丢弃最旧的记录，保留最新的；超过阈值（如 80%）时告警。

### 7. S9 错误 vs ACKC 非 0
- **S9 错误**：消息本身不支持/无法处理。S9F1=未定义 Stream、S9F3=未定义 Function、S9F5=非法消息、S9F7=非法数据、S9F9=数据太长、S9F11=转换超时。设备"听不懂"这条消息，回 S9 通知对端。S9 是 W=0，不需要对端再回。
- **ACKC 非 0**：消息支持但当前条件不满足。如 S2F42 ACKC10=4（设备 OFF-LINE）、=5（设备忙）、=3（参数错误）。设备"听懂了"但"现在不能做"，回对应 reply 带 ACKC 非 0。
- 区别：S9="我听不懂你说什么"（消息层面），ACKC 非 0="我听懂了但现在不能做"（业务层面）。使用原则：Stream/Function 不认识、格式非法用 S9；状态不对、参数错、设备忙用 ACKC 非 0。

### 8. 通信断开后命令执行会停止吗
**不会停止**。通信断开只影响"设备和 Host 之间的通信"，不影响设备内部的命令执行、工艺控制、报警检测、事件触发。原因：①设备是独立的物理设备，有自己的控制器（PLC/运动控制卡/工艺控制器），命令一旦被接受并开始执行，就由设备内部控制器驱动，不需要 Host 持续发送指令；②工艺控制是实时闭环（温度/压力/气体流量由设备内部 PID 控制），不依赖 Host；③报警检测是设备内部的硬件/软件检测，不依赖 Host；④事件触发是设备内部状态变化触发的，不依赖 Host。通信断开后，设备继续运行，只是这些事件和报警不发给 Host，而是写入 Spool 缓存，等通信恢复后补收。这是 GEM 设计的核心原则——**设备独立运行，Host 只是监控和管理方**。

### 9. 重连后为什么需要重新配置数据采集和报警
取决于设备实现：①**易失性配置**（大部分设备）：S2F33 报告定义、S2F35 事件关联、S5F3 报警使能是易失性的——存在内存中，设备重启或通信断开后会丢失（或恢复为默认值）。所以重连后 Host 需要重新配置，否则设备不会上报事件/报警。②**非易失性配置**（部分设备）：支持把配置保存到 Flash，重启后不丢失。但即使配置不丢失，Host 重连后也应该查询当前配置（S1F7/S5F5），确认配置是否一致，避免因为设备端配置被修改而导致数据采集异常。③**最佳实践**：Host 重连后，先查询设备当前配置，如果配置丢失或不一致，重新下发配置，然后再开始生产。这是 FAB 中 MES/EAP 的标准重连流程。

### 10. 优雅断开的顺序 / 直接 TCP 断开的问题
- **优雅断开顺序**：S1F15（Request Off-line）→ 设备回 S1F16（ACKC1=0，同意离线）→ HSMS Deselect.req → 设备回 Deselect.rsp → TCP 断开。
- 每步的作用：①S1F15 通知设备"我要断开了"，设备可以停止接受新命令、完成当前命令、保存状态、触发 OFF-LINE 事件；②Deselect 通知设备"我要取消 Select 了"，设备清理 HSMS 会话状态、停止发送消息；③TCP 断开是最后一步，此时双方都已清理完状态。
- **直接 TCP 断开的问题**：①设备不知道 Host 是主动断开还是网络故障，会触发异常重连流程（指数退避重连），而不是优雅停止；②设备可能正在执行命令或发送消息，TCP 断开导致消息丢失（Spool 可能来不及缓存）；③设备状态可能不一致（Host 认为已断开但设备认为还在线）；④正在传输的大消息（如配方下载）会中断，导致配方不完整。优雅断开是"双方协商一致的断开"，生产环境应该用优雅断开。

## 二、W9 E39 OSS 预热补充

### OSS 对象模型类比（帮助理解）
| OSS 概念 | 面向对象编程类比 | GEM 类比 |
|---|---|---|
| Object Type（对象类型） | Class（类） | - |
| Object Instance（对象实例） | Object（对象） | - |
| Attribute（属性） | Field/Property（字段/属性） | SV（状态变量） |
| Method（方法） | Method（方法） | 远程命令（RCMD） |
| Event（事件） | Event（事件） | CEID（收集事件） |
| OBJSPEC（对象说明符） | 对象引用/指针 | - |
| S14（类型查询） | 反射（Reflection） | S1F3/F5/F7（查询列表） |
| S15（实例操作） | 调用对象方法 | S2F41（远程命令） |
| S16（事件通知） | 事件回调 | S6F11（事件上报） |

### OSS 的优势（为什么 GEM300 要用 OSS）
1. **结构化**：对象/属性/方法/事件是结构化的，Host 可以通过 S14 查询设备支持什么，不需要事先知道。
2. **可扩展**：新增对象类型不需要新增消息族，只需要在 S14 中注册新类型。
3. **一致性**：所有 GEM300 标准（E40/E87/E90/E94）都用同一套对象操作接口（S14/S15/S16），学习成本低。
4. **多实例**：设备可以有多个同类型对象（如多个 ProcessJob、多个 Carrier），每个对象有唯一 OBJSPEC，Host 可以分别操作。
5. **生命周期管理**：对象有创建/删除/状态变化，Host 可以跟踪对象的完整生命周期。

### W9 学习重点提醒
- W9 是从"消息级"到"对象级"的思维转变，第一天可能会不适应，多画对象关系图。
- S14/S15/S16 的消息格式比 GEM 消息复杂（嵌套 List 多），编码时要仔细。
- OSS 的核心是"对象类型定义"——先搞清楚设备支持哪些对象类型，每种类型有哪些属性/方法/事件，然后才能操作对象实例。
- E40（ProcessJob）、E87（Carrier）、E90（Substrate）、E94（ControlJob）都是基于 OSS 的对象类型，W9 打好基础，后面学这些标准会很快。

## 三、今日易错点
1. 通信状态和控制状态混淆（通信是"能不能说话"，控制是"听谁的"）。
2. 以为 ACKC10=0 表示命令已执行（只表示已接受，执行靠 S6F11 事件通知）。
3. 报警和事件混淆（报警有状态用 S5F1，事件无状态用 S6F11）。
4. 以为通信断开后命令会停止（不会，设备独立运行，只是不通知 Host）。
5. Spool 重发后不等确认就删除缓存（应等 Host 回 S6F12/S5F2 后再删除）。
6. S9 和 ACKC 非 0 混用（S9=消息不支持，ACKC=条件不满足）。
7. 重连后不重新配置数据采集（配置可能丢失，导致事件不上报）。
8. 直接 TCP 断开而不是优雅断开（应按 S1F15→Deselect→TCP 顺序）。
9. OSS 对象类型和对象实例混淆（类型是"类"，实例是"对象"，OBJSPEC 标识实例）。
10. 以为 OSS 替代 GEM（OSS 扩展 GEM，GEM 提供基础通信，OSS 提供对象级抽象）。
