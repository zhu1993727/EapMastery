## 二、背景知识（先读，45 分钟）

### 1. S7 在体系中的位置
- S7 是 SECS-II 定义的"过程程序（Process Program，即 recipe）传输"服务，跑在 HSMS 连接上（W02）；它负责把配方体在 Host(EAP/RMS) 与设备间搬运，不负责决定用哪个配方（MES）或工艺控制（R2R）。

### 2. 主要消息对（教学口径，精确字段以 SEMI E5/设备手册为准）
- **下载方向（Host→Equipment）**
  - S7F1 Process Program Load Inquire：Host 先问"我要下一个 PPID、长度多少，能否接收"；S7F2 设备回 ACKC7（0=可以）。
  - S7F3 Process Program Send（Load）：正式下发，结构 `L,3 [PPID(A), PPHEAD(L/A 头部属性), PPBODY(B 二进制配方体)]`；S7F4 设备回 ACKC7 确认结果。
- **上传方向（Equipment→Host）**
  - S7F5 Process Program Request：Host 请求设备上传某 PPID；S7F6 设备回 `L,3[PPID,PPHEAD,PPBODY]`。用于比对/备份设备本地副本。
- **删除**：S7F17 删除过程程序请求 / S7F18 确认。
- **目录**：S7F19 请求设备当前配方目录 / S7F20 返回 PPID 清单（用于盘点设备上到底有哪些配方、版本是否齐全）。

### 3. PPID / PPHEAD / PPBODY
- PPID：配方标识（A 字符串），配合版本唯一定位。
- PPHEAD：过程程序头部/属性（可含长度、创建时间、格式版本等元数据，具体依实现）。
- **PPBODY：配方体，类型是 B（二进制/字节串）**，不是可读 A——设备厂商私有编码格式，Host 通常不解析其内部、只做透明传输与完整性校验（checksum/长度）。这点和 S6 报告数据不同，务必记牢。

### 4. 标准下载握手时序（重点）
1. Host 发 S7F1（PPID+长度）询问；设备检查存储空间/状态/是否允许，回 S7F2 ACKC7=0。
2. 非 0：按原因码处理（空间不足先清理/删旧、状态不允许等空闲），不发 S7F3。
3. ACK=0 后 Host 发 S7F3 携带完整 PPBODY；设备写入本地存储、校验长度/checksum，回 S7F4 ACKC7。
4. S7F4=0 才算下载成功；随后可做 body 回读比对（Day03）。先 Inquire 再 Send 是为了避免盲目下发大文件失败、保证设备就绪。

### 5. ACKC7 原因码（教学常见值，精确以标准/手册为准）
- 0 接受；1 权限/不允许；2 PPID 不存在（上传/删除找不到）；3 PPID 已存在（重复下载，需确认覆盖）；4 PP 长度不符/空间不足；5 PPBODY 校验错（checksum/格式）；6 非允许的 PPID/参数；其他厂商自定义。
- 处理原则：可恢复错误（空间/状态）退避重试有上限；不可恢复（校验错/非法 PPID）上报告警、不重复硬发。

### 6. 大配方与健壮性
- 大 PPBODY 可能超单消息上限，部分实现按块分段传输（厂商扩展/分块协议），需保证按序拼接与整包 checksum；教学先做整包。
- 传输与 HSMS T 链路超时、Spool 的关系：控制类交互失败要可重试且幂等（同 PPID+版本重复下载结果一致），中断后以设备目录/回读校验真实状态，不凭"发过了"假设成功。

### 7. 与生命周期衔接
- 只有 Released 的 golden 才允许被 S7F3 下载（Day01 状态机）；下载校验一致后才进入 Distributed、可被 PP-Select（Day05）。
