# W33 · Day03（周三）黄金副本校验：Checksum、Body 比对与篡改检测

> 建议时长：95 分钟。下载成功不等于设备副本永远正确——本地可能被私改、掉电损坏、传输出错。今天讲配方一致性保障：校验和/哈希、长度与逐字节 body 比对、版本绑定、设备本地篡改/漂移检测、不一致的处置（禁选/隔离/重下/告警审计），以及生产前、换班、定期三种校验时机。代码实现 RecipeComparer/一致性审计器。

## 一、今日目标
1. 掌握完整性校验层次：长度、简单 checksum/累加和、CRC、加密哈希（SHA-256）的抗碰撞/检错差异。
2. 掌握 golden↔设备副本一致性判定：PPID+版本匹配、长度一致、checksum/hash 一致，必要时逐字节 body 比对。
3. 理解篡改检测：面板私改、本地编辑、掉电/存储损坏、版本错配的识别。
4. 掌握不一致处置链：禁止选择生产→隔离该配方/设备→自动重下→仍不一致告警→审计留痕。
5. 明确校验时机（下载后、PP-Select 前、换班/定期巡检）；用 C# 实现 RecipeComparer/ComplianceAuditor；xUnit。

## 二、背景知识（先读，40 分钟）

### 1. 为什么要持续校验
- S7F4=0 只保证下载那一刻写入成功；之后设备本地副本可能被工程师从面板手动编辑、被旧流程覆盖、存储掉电损坏、或下错版本。先进 FAB 要求"每次生产前都能证明设备上的配方 == 已批准 golden"。

### 2. 完整性校验层次
- 长度校验：最快，发现截断/多余，但同长度错误检不出。
- 累加和/checksum：把字节求和/异或，实现简单，能检出多数传输错，但可被刻意构造碰撞、检错能力弱。
- CRC（循环冗余校验）：检突发位错能力强，传输层常用。
- 加密哈希（SHA-256 等）：抗碰撞强，任何一字节变化哈希都不同，适合防"刻意篡改"与合规审计；FAB 配方一致性多用强哈希或厂商 CRC+哈希双保险。
- 教学用"长度+字节累加和"演示，工程上优先强哈希。

### 3. 一致性判定要素
- 身份一致：PPID 与版本号都对（同名不同版也算不一致）。
- 内容一致：长度相同且 checksum/hash 相同；高风险/仲裁场景 S7F5/F6 回读 body 逐字节比对。
- 元数据一致：适用设备/腔、参数范围、格式版本。
- 结论只有"一致/不一致"，不允许"差不多"。

### 4. 篡改/异常类型与识别
- 面板私改：PPID 版本名没变但 hash 变了——最危险，属违规变更，必须告警并追溯（谁、何时、哪台）。
- 版本错配：设备上是旧版/别的产品版本——按版本不符处理，禁止生产、下发正确版。
- 传输/存储损坏：hash/长度不符，重下；重下后仍不符怀疑设备存储/通信硬件。
- 缺失：目录里没有该 PPID（S7F19/F20 盘点发现），需下载。

### 5. 不一致处置链（闭环）
1. 判不一致→该配方立即置为不可选择（设备/ EAP 侧联锁，防止误生产）。
2. 自动从 RMS 重新 S7 下载（Day02），下载后再校验。
3. 重下后仍不一致→判设备异常，禁止该设备/腔接相关产品、上报告警、开维修/偏差单。
4. 全程审计：期望 hash、实际 hash、差异、时间、设备、处置结果；疑似人为私改要走质量/纪律流程。
- 与 E87/E94 门控思想一致：不满足前置条件（配方一致）就不放片。

### 6. 校验时机
- 下载后立即校验（进入 Distributed 的条件）。
- PP-Select 前强制校验（Day05，最后一道关）。
- 换班/换 Lot、定期巡检（S7F19 目录盘点 + 关键配方 hash 轮询）。
- 事件触发：设备重启/掉电恢复、配方被本地编辑告警（若设备支持编辑事件 S6F11）。

### 7. 与 R2R overlay 的区别（再强调）
- 一致性校验针对的是**主档 body**；R2R overlay 不写进主档 body、运行时叠加，因此不会造成"golden 与本地 body 不一致"；若实现错误地把 overlay 写回本地 recipe，反而会触发篡改告警——这也是 overlay 必须运行时叠加、不落主档的原因之一。
