# W19 · Day04 答案与参考实现

## 一、自测题标准答案
1. **三者各保证什么 / 缺一不可**：状态持久化（事件溯源+快照、WAL 先行）保证**设备本机任务进度不丢**——重启后知道每片做到哪个 Step、Job 到什么状态；三方对账保证**账实相符**——物理现实 P、设备逻辑账 L、Host 镜像 H 最终一致，纠正掉电期间被人工改动或滞后造成的偏差；Spool 保证**通信报文不丢**——断线期间待发事件缓存、重连按序补发。缺一不可：只持久化不对账，本机进度可能与被改动的物理现场、Host 视图不一致；只对账不持久化，重启没有可靠进度基准；前两者都有但无 Spool，重连后 Host 缺失过程事件、视图仍不一致。三者分别覆盖"本机进度、物理账实、上报链路"，共同构成端到端可靠。
2. **P/L/H / 差异性质**：P=物理现实（传感器、Mapper、读码读到的载具/片真实位置与状态）；L=设备逻辑账（E90/E40 依据持久化重建的位置与进度）；H=Host 镜像（FAB EAP/MES 侧认为的设备/片/Job 状态）。P≠L 是**设备内部账实不符**，最严重，可能是掉电期间人工动片、读码变化、位置错，必须以物理核查、身份存疑即人工；L≠H 多为**视图滞后**（断线期间设备继续变化、Host 没收到），设备 L 是权威，重连后把 L 同步给 H 即可。性质上 P-L 是"对不对"的安全问题，L-H 是"同步没同步"的通信问题。
3. **收敛顺序 / 反过来的风险**：必须先让 P-L 收敛（设备内部账与物理一致，得到权威 L），再做 L-H 同步（把权威 L 推给 Host）。反过来若先 L-H 同步，可能把尚未与物理核对、可能错误的中间态 L 报给 Host，甚至用滞后的 H 去覆盖/影响 L，导致 Host 锁定一个错误状态，之后即使 P-L 修正了还要再纠正 Host，造成三方反复不一致甚至按错误状态派工。先内后外保证对外同步的永远是已经与物理对齐的权威状态。
4. **物理优先 / 何时以 P 修 L、何时人工**：掉电期间物理可能被改变，L 是过时记录，P 是客观事实，所以以 P 为基准重建。当差异是**有无/位置类且身份明确**（读码确认片 ID 与记录一致，只是位置从臂变到某槽/锁）时，以 P 修 L（补登/修正位置）；当**身份或工艺完整性存疑**（读不到 ID、ID 与记录不符、守恒破坏找不到去向、无法判断某 Step 是否完成）时必须人工，绝不猜测身份或假定工艺完成。判据仍是"能否不猜测地确定这片是谁、处于什么可续状态"。
5. **Spool 为何在恢复后补发 / 边恢复边发的问题**：补发的事件必须反映恢复后的权威状态。若边恢复边发，可能把尚未与物理对齐的错误中间态、随后又被对账修正的位置/进度先发出去，Host 收到自相矛盾的事件序列；且恢复可能判定某些片需要人工/改派，过早发出的"加工中/完成"事件会误导 MES。正确顺序：先完成状态重建和 P-L 收敛得到权威 L，再按序补发 Spool（必要时用当前权威快照重发/纠正），保证 Host 一次性收到与最终事实一致、有序、可去重的事件流。
6. **至少一次为何要去重**：Spool 采用"发送—等确认—确认后删除"，未收到确认就可能重发（网络延迟/对端实际已收到但 ACK 丢失），因此对端可能**重复收到同一事件**，即"至少一次送达"。若对端不按事件序号去重，会把同一进度/完成/报警重复记账（如片被算完成两次、计数翻倍、重复触发下游）。对端按单调事件序号识别已处理事件、重复的直接丢弃（幂等消费），就能在"至少一次"传输上实现"恰好一次生效"。
7. **最终一致判据**：①每片物理位置==L 记录==H 镜像（三方位置一致）；②Job/载具状态三方一致；③事件序号连续无缺漏（缺段用快照补齐，重复已去重）；④三不变式（唯一/容量/守恒）在 P、L 侧都成立且 H 计数吻合；⑤无未决差异项、无未确认 Spool 报文。全部满足才算三方最终一致，可安全继续生产/下料。

## 二、参考实现（net8.0）

### 三方视图与对账
```csharp
namespace EapLab.Cell;
public sealed record View(string Wafer,string Location,JState JobState);
public enum DiffKind { PL_Mismatch, LH_Lag, IdentityDoubt }
public sealed record ReconDiff(string Wafer,DiffKind Kind,string P,string L,string H,string Action);
public sealed class Reconciler3
{
    private readonly Dictionary<string,View> _p,_l,_h;
    public Reconciler3(Dictionary<string,View> p,Dictionary<string,View> l,Dictionary<string,View> h){_p=p;_l=l;_h=h;}

    public List<ReconDiff> Reconcile(Func<string,bool> identityOk)
    {
        var diffs=new List<ReconDiff>();
        // 第一步: P-L 收敛(设备账实)
        foreach(var w in _p.Keys.Union(_l.Keys))
        { _p.TryGetValue(w,out var p); _l.TryGetValue(w,out var l);
          if(p is null || l is null || p.Location!=l.Location)
          { bool ok= p is not null&&l is not null&&identityOk(w);
            diffs.Add(new(w, ok?DiffKind.PL_Mismatch:DiffKind.IdentityDoubt,
                p?.Location??"?", l?.Location??"?", "", ok?"以P修L":"安全保持转人工")); } }
        // 第二步: L-H 同步(权威L推给Host)
        foreach(var w in _l.Keys.Union(_h.Keys))
        { _l.TryGetValue(w,out var l); _h.TryGetValue(w,out var h);
          if(l is null||h is null||l.Location!=h.Location||l.JobState!=h.JobState)
            diffs.Add(new(w,DiffKind.LH_Lag,"",l?.Location??"?",h?.Location??"?","以权威L同步H")); }
        return diffs;
    }
    public bool NeedManual(IEnumerable<ReconDiff> d)=>d.Any(x=>x.Kind==DiffKind.IdentityDoubt);
}
```

### Spool 顺序补发 + 对端去重
```csharp
public sealed record SpooledEvent(long Seq,string Body);
public sealed class SpoolQueue
{
    private readonly Queue<SpooledEvent> _q=new();
    public void Enqueue(long seq,string body)=>_q.Enqueue(new(seq,body));
    public IEnumerable<SpooledEvent> Pending=>_q;
    public void Ack(long seq){ if(_q.Count>0&&_q.Peek().Seq==seq)_q.Dequeue(); } // 确认后删
}
public sealed class HostReceiver   // 对端按序号幂等去重
{
    private readonly HashSet<long> _seen=new(); public List<string> Applied=new();
    public bool Receive(SpooledEvent e){ if(!_seen.Add(e.Seq))return false; Applied.Add(e.Body); return true; }
}
public sealed class RecoverySync
{
    public void ResyncAfterRecovery(SpoolQueue spool,HostReceiver host)
    { foreach(var e in spool.Pending.OrderBy(x=>x.Seq).ToList())  // 恢复后按序补发
        if(host.Receive(e)) spool.Ack(e.Seq); }                    // 对端去重, ACK后删
}
```

public class ReconSpoolTests

## 三、复合故障恢复时序（手绘参考）
```
并发执行 ─断电→ 内存失(快照/事件已落盘, 末两条事件在Spool未确认)
 重启 → 快照+事件重建L; E87扫口/E90读码重建P
 第一步 P-L对账: 身份明确位置差→以P修L; 身份/工艺存疑→安全保持人工
 恢复: Executing先安全挂起 → 确认安全点 → Resume
 重连 → 第二步 L-H: Spool按序补发(权威状态), Host按序号去重, ACK后删, L→H同步
 判据: 每片 P位置==L==H; Job状态三方一致; 序号连续; 守恒 → 续跑到完成
顺序铁律: 先恢复本机权威状态(P-L), 再对外同步(L-H/Spool)
```

## 四、今日易错点
1. 混淆三层可靠性（进度不丢/账实相符/报文不丢，各管一层、缺一不可）。
2. 把 L≠H 当严重错误（多为视图滞后，权威 L 同步 H 即可）。
3. 先 L-H 同步再 P-L 对账（可能把错误中间态报给 Host，必须先内后外）。
4. 身份存疑还以 P 自动改 L（身份/工艺不确定必须人工）。
5. 边恢复边补发事件（应恢复出权威状态后再按序补发）。
6. Spool 补发不保证顺序、对端不去重（至少一次送达+序号去重=恰好一次生效）。
7. 未确认事件提前删除（ACK 后才删，否则重连补发）。
8. Executing 重启直接自动跑（先安全挂起、对账一致再 Resume）。
9. 只比对位置不比对 Job 状态与事件序号连续性（最终一致要全维度）。
