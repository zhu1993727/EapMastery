# W29 · Day02 答案与参考实现

## 一、自测题标准答案
1. **双向/设备角色**：普通 REST 是客户端拉、服务端只应答；Freeze II 的 SOAP Web Services 是双向的——FDC/YMS 客户端除了向设备发请求（建会话/订阅），自己也暴露一个数据接收回调 Web Service（回调 URL）。设备在有数据时角色反转为 **HTTP 客户端**，主动调用各客户端的回报方法、把 XML 数据包 POST 过去。因此"设备是 EDA 服务端（接收订阅）"和"设备是上报时的 HTTP 客户端（推送数据）"两个角色并存。
2. **XML 段/为何带单位质量**：包含消息头（会话 id、计划 id、包序号、时间窗起止）、变量定义列表（路径/WKN/单位/类型）、周期采样行集合（每行时间戳+各变量值+质量码）、事件/异常快照段、Gap 丢点数与连续性标志。每点带单位/质量是因为客户端是通用、零硬编码的：不依赖外部点表就能解析数值物理含义（Pa 还是 mTorr）、判断该点是否可信（Good/Bad/Gap），否则跨厂商、跨版本无法正确解释数据，坏点还可能被当真值触发 FDC 误判。
3. **XML 开销/降内存**：主要开销是标签冗余导致报文体积大（每值都带开闭标签、路径/单位重复出现），以及 XML DOM 解析/字符串分配带来的 CPU 与 GC。降低内存：用 XmlWriter **流式**顺序写出（不构建整棵 XDocument/DOM、不字符串拼接），重复的变量定义只在头部列一次、行内按列顺序给值，复用 StringWriter/缓冲与 ArrayPool，避免对每个采样点装箱 ToString；必要时启用压缩。即便如此 XML 仍比 protobuf 重，这正是 Freeze III 的动因（Day03 量化对比）。
4. **成功判定/超时短于 flush**：客户端回调返回 2xx（200/202）视为接收成功；连接失败/超时/非 2xx 都算失败、累加 FailStreak，达阈值判会话死亡并级联撤销。发送超时要短于 flush 周期，否则一个慢/挂的目标会让发送循环长时间阻塞，后续数据包和其他客户端的发送被拖在后面，破坏上报节拍；短超时让它快速失败、走背压/隔离，发送循环保持流动，采样完全不受影响。
5. **独立 HttpClient/Factory**：每个目标客户端独立发送任务与连接，单点慢断只影响自己（故障隔离）。用 IHttpClientFactory 而非每次 new HttpClient，是因为频繁 new/Dispose HttpClient 会导致底层 socket 处于 TIME_WAIT 堆积、端口耗尽（经典 socket exhaustion），Factory 复用 HttpMessageHandler 连接池、统一配置超时/DNS/TLS，生命周期由框架管理；同时为不同回调目标命名不同 client、独立并发发送。
6. **抓包过滤/对比**：选 Npcap Loopback Adapter，过滤 `http` 或 `tcp.port==回调端口`；触发一次上报后找到 POST 行，Follow HTTP/TCP Stream 看完整请求头（POST 路径、Host、Content-Type: text/xml|application/soap+xml、Content-Length）与 Body 里的 XML 采样行，以及响应 200。与 W02 抓的 HSMS 帧对比：HSMS 是 4B 长度+10B 头+紧凑二进制 SECS-II（人不可读、面向控制事务），HTTP/XML 是明文文本、标签自描述、肉眼可读但冗长——直观看懂两通道编码与用途差异，并记录 XML 字节数供 Day03 对比 protobuf。
7. **时间/数值格式/后果**：时间用 ISO8601 UTC（如 2026-09-08T10:00:00.123Z），跨时区/系统无歧义、可与 MES/EDC 对齐；数值用 InvariantCulture 序列化（小数点固定 "."、不用本地化逗号）。错了会：本地文化用逗号小数点导致客户端 double.Parse 失败或数值错位；时间用本地不带时区导致跨系统对不齐、夏令时/时区错；质量枚举写成数字/本地词导致通用客户端无法识别。序列化规范是跨厂商互操作的底线。

## 二、参考实现（net8.0）：XML 编码器 + HTTP 回调传输

```csharp
using System.Globalization;using System.Text;using System.Xml;
namespace EapLab.Eda.Soap;
public sealed class SoapXmlEncoder
{
    public string Encode(Packet p,ModelMeta meta)
    { var sb=new StringBuilder();using(var w=XmlWriter.Create(sb,new(){OmitXmlDeclaration=true}))
      { w.WriteStartElement("DataCollectionPacket");
        w.WriteAttributeString("plan",p.PlanId);w.WriteAttributeString("seq",p.Seq.ToString(CultureInfo.InvariantCulture));
        w.WriteAttributeString("gap",p.Gap.ToString(CultureInfo.InvariantCulture));w.WriteAttributeString("continuous",p.Continuous?"true":"false");
        w.WriteStartElement("Rows");
        foreach(var pt in p.Rows)
        { w.WriteStartElement("s");w.WriteAttributeString("t",pt.At.ToString("F4",CultureInfo.InvariantCulture));
            w.WriteAttributeString("v",pt.V.ToString(CultureInfo.InvariantCulture));w.WriteAttributeString("q",pt.Q.ToString());w.WriteEndElement(); }
        w.WriteEndElement();
        w.WriteStartElement("Events");
        foreach(var e in p.Events){w.WriteStartElement("e");w.WriteAttributeString("t",e.At.ToString("F4",CultureInfo.InvariantCulture));w.WriteAttributeString("v",e.V.ToString(CultureInfo.InvariantCulture));w.WriteEndElement();}
        w.WriteEndElement();w.WriteEndElement(); }
      return sb.ToString(); }
}

// ITransport的HTTP版: 设备作为客户端向回调URL POST; 每目标独立, 短超时, 失败计数
public sealed class CallbackTransport
{ readonly HttpClient _http;public int FailStreak{get;private set;}public bool Ok=true;
    public CallbackTransport(HttpClient http){_http=http;_http.Timeout=TimeSpan.FromMilliseconds(500);}
    public async Task<bool> PostAsync(string url,string xml,CancellationToken ct=default)
    { try{ using var req=new HttpRequestMessage(HttpMethod.Post,url){Content=new StringContent(xml,Encoding.UTF8,"application/soap+xml")};
            var resp=await _http.SendAsync(req,ct);
            if(!resp.IsSuccessStatusCode){FailStreak++;return false;}FailStreak=0;Ok=true;return true; }
        catch{FailStreak++;Ok=false;return false;} } }
```

## 三、Freeze II 回报（手绘参考）
```
FDC: 暴露 POST http://fdc/receive 回调端点; 建会话时登记到设备
设备采集→Packet→SoapXmlEncoder流式写XML(头/变量单位WKN/Rows带质量/Events/Gap)
   →设备反转为HTTP Client(IHttpClientFactory, 每目标独立, 超时<flush周期)
   →POST application/soap+xml 到各回调URL → 2xx成功 / 非2xx或超时FailStreak++→达阈值判死级联
抓包: Npcap Loopback, http过滤, Follow Stream看明文XML; 对比HSMS二进制帧
规范: 时间ISO8601 UTC带Z; 数值InvariantCulture点小数点; 质量枚举标准串; 单位/WKN随字段
代价: 标签冗余报文大/DOM占CPU → 流式XmlWriter缓解, 根本优化看Day03 protobuf
```

## 四、今日易错点
1. 以为设备永远是服务端（上报时它是主动 POST 的 HTTP 客户端）。
2. 用 DOM/字符串拼接大 XML，高频下内存与 GC 爆炸（用 XmlWriter 流式）。
3. 每点重复带完整路径/单位，报文进一步膨胀（头部定义一次、行内按列给值）。
4. new HttpClient 频繁创建导致 socket/TIME_WAIT 耗尽（用 IHttpClientFactory）。
5. 发送超时设得比 flush 周期长，慢目标拖死整个发送循环。
6. 数值用本地文化（逗号小数点）、时间不带时区，客户端解析/对齐出错。
7. 数据点不带单位/质量，通用客户端无法解释与判可信。
8. 把文本 XML 报文和 HSMS 二进制帧混为一谈（用途与编码都不同）。
