# W10 · Day07 答案

## 一、W10 自测题（10 题）标准答案

### 1. 包含 vs 关联 / Substrate 归属
包含（Composition）是强生命周期关系，子有唯一直接父、父删除要级联处理子，用对象树 CompositionRule 管理（CJ→PJ、Carrier→Substrate）；关联（Association）是弱引用，双方生命周期独立，用对象属性存对方 OBJSPEC（PJ.SourceCarrier=Carrier:CAR01），级联不沿关联传播。Substrate 物理上唯一装在一个 Carrier 的 Slot 里、随载具上下料，物理归属唯一，故由 Carrier 包含；而 PJ 只是加工期引用 Substrate（取出加工再放回），同一片可能被多个 PJ 先后加工，PJ 结束 Substrate 仍在 Carrier 上，故 PJ 只关联不包含，避免违反唯一父、避免删 PJ 误删晶圆。这是物理归属与加工归属分离。

### 2. 嵌套 OBJSPEC 逐级解析与校验
按 `/` 分段、每段按首个 `:` 拆 Type:ID；从根段开始在 InstanceStore 定位并校验对象存在、Type 与段一致；下一段通过 ObjectTree.GetChildren 校验它确实是上一级的直接子（且父子类型符合 CompositionRule）；逐级向下直到目标。任一级"对象不存在/类型不符/非直接父子"即解析失败（实例不存在或层级非法）。这样路径必须真实反映对象树，不能靠拼字符串伪造归属。

### 3. 列举分页 / 读部分失败 vs 写整批原子
对象可能数百个，单条 SECS 消息有最大长度，全量返回会撑爆消息、增大延迟内存，故分页（StartIndex/Count，返回本页+Total+HasMore+NextCursor，结果稳定排序，Host 翻页到 HasMore=false）。批量查询是读操作、无副作用，一个对象查不到不影响其他对象，允许部分失败、逐项标注，可用性优先；批量写（创建/设置/删除）有副作用，部分成功会造成对象半更新、跨对象不一致且难补偿，因此两阶段——先整批校验全部通过、再统一提交，任一非法整批不变。

### 4. 订阅三粒度与优先级 / 空订阅策略
三粒度：按类型（某类型全部实例）、按实例（具体 OBJSPEC）、按 CEID（特定事件），一条订阅=(类型或实例范围)+CEID 白名单（空=全部）。判定：实例级先判（更具体），再类型级，任一命中即发（正向白名单并集）。空订阅策略："空=全发"兼容老 Host（控制通道常用，一旦建订阅即切白名单）；"空=不发"最省流最可控（EDA 高频通道用，但忘订阅会完全收不到）。按通道数据量和兼容性选型。

### 5. 状态机 Fire 流程与两个拦截点
加锁→按 CurrentState+Trigger 查转换表，找不到边则非法（拦截点1：无合法边）→找到边求值 Guard，false 则拒绝（拦截点2：守卫不满足）→执行源态 OnExit→更新 CurrentState→执行目标态 OnEntry（含自动 RaiseEvent）→记历史→触发 Transitioned 回调→解锁。两个拦截点任一失败则状态不变、零副作用（OnExit/OnEntry 都不执行）。

### 6. PermitIf 守卫 / Complete 守卫例子
Permit 是无条件边（状态匹配即可转），PermitIf 额外带 Guard 委托，运行时读取对象属性/子状态决定是否可转，同一(state,trigger)可多条 PermitIf 按配置顺序取首个满足的。ProcessJob Complete 守卫：`PermitIf(Complete, COMPLETED, () => ProcessedCount == PlannedCount)`——只有实际加工完的片数等于计划片数才允许转到 COMPLETED，片数不够时 CanFire(Complete)=false、Fire 抛异常、状态保持 EXECUTING，防止没做完却报完成。

### 7. 为什么只发 trigger / 终态为何无出边
业务只 Fire trigger 是为了让所有转换都经过状态机：合法性集中校验、进入/退出动作和事件自动一致执行、并发原子、状态图即代码可枚举测试可讲解；直接改字符串会绕过守卫、漏发 S16 事件、破坏不变式。终态（COMPLETED/ABORTED）代表生命周期结束、语义上不可再变，不配置任何出边，任何 trigger 都在查边环节拦截，防止"死而复生"、保证 Host 收到终态事件后可确定对象不再变化、安全统计清理删除。

### 8. 单一状态源+双适配器架构 / 依赖方向
底层内部领域模型（Domain，持状态机和真实数据）是唯一可写层，只有内部工艺回调和统一命令入口 AppService 能改它，变化时发布领域事件；其上 GEM 适配器（投影成 SV/S6F11、接 S2F41）和 OSS 适配器（投影成 Attribute/S16F1、接 S15F9）都是只读投影，写操作都转调 AppService。依赖方向单向：适配器依赖领域，领域不依赖任何通信协议（不引用 SECS/GEM 类型），从而可独立测试、协议可插拔、状态永不漂移。

### 9. GEM CEID 与 OSS CEID 关系
不是一套编号，是两个独立编号空间（GEM 设备级 CEID 如 3001，OSS 对象级 CEID 如 4101），粒度也可不同。关联靠领域事件映射表：同一个内部领域事件（如 Job 进入 Executing）同时映射到 GEM CEID 和 OSS CEID，两个适配器订阅同一领域事件各取各编号上报，是"一个领域事件→N 个协议事件编号"的一对多关系。SOFTREV 升级两套编号都要重新核对。

### 10. CJ 为何必须子 PJ 聚合、不能 Host 直接完成
ControlJob 是编排聚合对象，"完成"的客观含义是其下所有 ProcessJob 真正完成，这由子对象实际状态决定，不能由 Host 宣称。允许 Host 直接置 COMPLETED 会产生"CJ 完成但还有 PJ 在跑/失败"的矛盾，导致提前下料/误派工的生产事故。因此 CJ.Complete 不开放给 Host，只在聚合逻辑发现全部直接子 PJ=COMPLETED 时自动触发；任一 PJ ABORTED 且其余未完则 CJ 聚合为异常态。父状态永远是子状态的真实投影，这是 E94 级联状态机的根本原则。

## 四、E84 预热补充（为 W11 打底的关键概念）
1. **两套独立通道要分清**：HSMS/SECS/GEM/OSS 走 TCP 网口传软件报文（信息、状态、任务）；E84 LPT 走并行硬线 I/O 传电平信号（物理交接互锁）。两者物理介质、实时性、用途完全不同，不要混为一谈。
2. **E84 的安全哲学**：故障安全（fail-safe），信号丢失/断电/死机时回到安全态（停止动作、保持夹持），互锁不依赖软件和网络。
3. **两个交接方向**：Deposit=AMHS 把 FOUP 放到设备（上料），Pickup=AMHS 从设备取走 FOUP（下料），各有一套请求-就绪-执行-完成的握手时序，W11 Day03/04 闭卷手绘。
4. **三层配合**：E84 管物理硬握手、E87 管载具逻辑状态（走 SECS 上报 Host）、E90 管槽位/基板位置；自动上料=E84 放好→E87 转 LOADED 上报→E90 读 SlotMap→Host 建 PJ。
5. **常见信号先混个脸熟**（W11 精讲，不要求今天背）：设备侧 CS/ES/HO、搬运侧 SS/VR/TR_REQ、双方 VALID/ESTOP/BYPS、完成 COMPT/BUSY。重点是理解"双向并行信号、按节拍互锁"的握手思想。

## 五、W10 全周易错点汇总
1. 混淆包含与关联、让 Substrate 有两个父。
2. 嵌套路径只拼字符串不校验真实父子。
3. 列举不分页/不排序，批量读写原子性策略用反。
4. 订阅当"排除列表"用（实际是正向白名单并集）。
5. 业务绕过 FSM 直接改状态；终态配出边。
6. 守卫失败还执行了 OnExit/OnEntry（应零副作用）。
7. GEM/OSS 双份状态、双向同步（应单一领域源、单向投影）。
8. 两套 CEID 编号混用（靠领域事件映射表关联）。
9. 允许 Host 直接完成 CJ（必须子 PJ 聚合）。
10. 级联删除沿关联边误删 Carrier/Substrate、删对象不取消订阅。
