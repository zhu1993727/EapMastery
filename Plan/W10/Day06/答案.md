# W10 · Day06 答案与参考实现

## 一、自测题标准答案
1. **Substrate 为什么物理上归 Carrier 包含、PJ 只关联**：包含关系要求"一个子只有唯一直接父、父销毁则处理子"（强生命周期、唯一父）。Substrate 在物理上确定地装在一个 Carrier 的某个 Slot 里，随 Carrier 上料/下料移动，物理归属唯一且明确，所以包含树走 Carrier→Substrate，SlotMap 描述槽位。而 ProcessJob 只是"加工视角"在一段时间内引用这些 Substrate（把它们取出来加工再放回去），同一片 Substrate 可能被多个 PJ（不同工序）先后引用，PJ 结束后 Substrate 仍在 Carrier 上、生命周期不归 PJ 拥有，若让 PJ 也包含 Substrate 就违反"唯一父"，且删 PJ 会错误删掉晶圆记录。因此 PJ 用关联属性（SubstrateID/SourceSlot/TargetSlot 列表）引用 Substrate，不进包含树。这正是真实 GEM300 的建模：物理归属（Carrier/E90 位置跟踪）与加工归属（PJ/E40 处理顺序）分离，是后续 E90/E40 的核心思想。
2. **CJ 为什么不能 Host 直接 Complete、要子 PJ 聚合**：ControlJob 是聚合/编排对象，它的完成语义是"它编排的所有 ProcessJob 都真正完成"，这是一个由子对象实际状态决定的客观事实，不能由 Host 宣称——若允许 Host 直接把 CJ 置 COMPLETED，可能出现"CJ 已完成但还有 PJ 在执行/失败"的状态矛盾，Host 误判任务结束、提前下料或派工会造成生产事故。因此 CJ.Complete 不开放给 Host（方法不注册或守卫恒 false），只能由内部聚合逻辑在"全部直接子 PJ 处于 COMPLETED"时自动触发；同理任一 PJ ABORTED 且其余未完成时 CJ 聚合为异常态。这保证父状态是子状态的真实投影，状态不变式永远成立，也是 E94 级联状态机的根本原则（W21 详解）。
3. **CJ.Start 的父驱动子+子冒泡聚合链路**：①Host 对 CJ 调 Start（S15F9），CJ 方法执行器先校验自身状态（QUEUED 可启动）；②父驱动子：CJ 遍历对象树中直接子 PJ，按编排顺序对每个 PJ 调用其状态机 Fire(Start)，PJ 转 EXECUTING 并发 PJ Started 事件；③子状态变化通过 Transitioned/领域事件向上冒泡到 CJ 的聚合器；④聚合器读取所有直接子 PJ 当前状态，用聚合规则（任一执行中→EXECUTING、全 QUEUED→QUEUED、全 COMPLETED→COMPLETED、任一失败且其余未完→ABORTED/FAILED）算出 CJ 新状态；⑤若算出的状态与 CJ 当前不同，CJ 状态机 Fire 对应 trigger 转到新态，进入该态时发 CJ 的 S16 事件（5102 Started）；⑥之后每个 PJ 暂停/恢复/完成/中止都重复"子变化→冒泡→重算父→父转换并发事件"，一直聚合到 CJ 根。链路方向：命令自上而下（CJ→PJ），状态事件自下而上（PJ→CJ）。
4. **4101 被抑制、5102 发送，验证了什么**：订阅配置是"只订阅 ProcessJob 的 4102/4103 + ControlJob 全部事件"。PJ001 转 EXECUTING 发的是 ProcessJob.Started=4101，不在 PJ 的订阅白名单 {4102,4103} 内，也没有匹配的实例订阅，因此 SubscriptionTable.ShouldEmit 返回 false，事件被抑制（SuppressedCount+1，不发送）；而 CJ 聚合转 EXECUTING 发的是 ControlJob.Started=5102，ControlJob 订阅的 CEID 白名单为空（=全部事件），类型匹配命中，正常发送。这一步同时验证了三件事：①订阅过滤按"范围(类型/实例)+CEID 白名单"精确判定；②不同对象类型独立过滤（PJ 被抑制不影响 CJ）；③父状态聚合事件独立于子事件产生（即使子的细节事件被过滤，父级关键生命周期事件仍可达 Host），Host 可以只收粗粒度的 CJ 级事件来监控整体、按需再订阅 PJ 细节，体现订阅模型的流量裁剪价值。
5. **级联删除顺序 / Substrate 为何先解关联**：正确顺序（后序遍历）：①先把 PJ001 对 W01..W05 的加工关联解除（清空 PJ 的 SubstrateID/SourceSlot 引用列表），因为 Substrate 物理归属是 Carrier，删 PJ 不应删晶圆，只断开加工引用；②若 Substrate 是 CJ 子树的一部分则先删叶子（本骨架 Substrate 在 Carrier 下，不随 CJ 删，仅解关联）；③删除子 ProcessJob:PJ001（先确保其处于 COMPLETED/ABORTED 终态，执行中拒绝），同时取消其事件订阅；④最后删除 ControlJob:CJ001，取消订阅、移除父子关系。Substrate 先解关联是为了避免删除 PJ 后留下悬空引用（PJ 已不存在但 Substrate 的"被谁加工"指针还指向它），也避免误删物理晶圆对象；整体原则：先断关联引用→再从叶子到根沿包含边逐级删除→每级删除前校验终态→同步取消事件订阅防泄漏/幽灵事件。
6. **E40/E87/E90/E94 对应对象与问题地图**：①**E40 ProcessJob（加工任务，W16-W19）**——对应 ProcessJob 对象，解决"设备怎么执行一个加工任务"：PJ 结构（PPID 配方、加工顺序、基板列表）、PJ 状态机、多腔体并行/流水；②**E87 Carrier Management（载具管理，W12-W13）**——对应 Carrier 对象，解决"FOUP/载具的交接与状态管理"：载具状态机、预约/上料/下料、和 E84 并口自动交接配合；③**E90 Substrate Tracking（基板跟踪，W14-W15）**——对应 Substrate 对象和 SlotMap，解决"每片晶圆/基板现在在哪、从哪个槽来、到哪个槽去"：位置跟踪、槽位映射、交叉取片验证；④**E94 ControlJob（控制任务，W20-W23）**——对应 ControlJob 对象，解决"一个 Host 指令如何编排多个 PJ、跨载具/跨腔体调度"：CJ 结构、CJ-PJ 级联状态机、全链路调度与故障演练。四者通过 OSS 对象树组织：CJ 编排 PJ，PJ 引用 Substrate，Carrier 物理承载 Substrate，E84（W11）是载具自动交接的硬件并口协议。今天的迷你骨架就是这套体系的最小可运行雏形。

### CJ-PJ 级联编排器
```csharp
public sealed class CjPjOrchestrator
{
    private readonly ObjectRegistry _reg;
    private readonly ObjectTree _tree;
    public CjPjOrchestrator(ObjectRegistry reg, ObjectTree tree) { _reg = reg; _tree = tree; }

    /// <summary>父驱动子：CJ.Start 时启动其全部 PJ。</summary>
    public void StartControlJob(string cjSpec)
    {
        foreach (var pjSpec in _tree.GetChildren(cjSpec))
        {
            var pj = _reg.GetInstance(pjSpec);
            pj.InvokeMethod("Start", new(), Executor); // 内部 FSM 转 EXECUTING
        }
        Aggregate(cjSpec);
    }

    /// <summary>子冒泡：任一 PJ 状态变化后重算 CJ。</summary>
    public void Aggregate(string cjSpec)
    {
        var childStates = _tree.GetChildren(cjSpec).Select(s => _reg.GetInstance(s).State).ToList();
        string agg = StateAggregator.Aggregate(childStates); // Day01 聚合规则
        var cj = _reg.GetInstance(cjSpec);
        // 用 trigger 驱动 CJ FSM（映射 聚合态→trigger），不直接改状态
        switch (agg)
        {
            case "EXECUTING" when cj.State == "QUEUED": cj.InvokeMethod("Start", new(), Executor); break;
            case "COMPLETED": /* CJ 内部 Complete（不对外开放）*/ break;
            case "ABORTED": cj.InvokeMethod("Abort", new(), Executor); break;
        }
    }

    private static Dictionary<string, SecsItem> Executor(ObjectInstance inst, string method, Dictionary<string, SecsItem> p)
    {
        // 简化：方法名→trigger 映射，交给 Day04 FSM
        var trig = method switch
        { "Start" => PjTrigger.Start, "Pause" => PjTrigger.Pause, "Resume" => PjTrigger.Resume,
          "Abort" => PjTrigger.Abort, _ => throw new InvalidOperationException(method) };
        // inst 内部持有 FSM，这里示意调用
        // inst.As<PjFsmHolder>().Fsm.Fire(trig);
        return new();
    }
}
```

### 22 步剧本测试骨架
```csharp
public class MiniGem300ScenarioTests
{
    [Fact]
    public void 完整剧本_上料建任务加工级联下料清理()
    {
        var reg = new ObjectRegistry();
        foreach (var t in new[] { MiniGem300Types.ControlJob(), MiniGem300Types.ProcessJob(),
                                  MiniGem300Types.Carrier(), MiniGem300Types.Substrate() })
            reg.RegisterType(t);
        var tree = new ObjectTree(reg, MiniGem300Types.Rules());

        // 1-3 上料：建 CAR01，Load，建 W01..W05 挂 Carrier
        var car = reg.CreateInstance("Carrier", "CAR01", new(){ ["CarrierID"]=SecsItem.A("FOUP01") });
        // car.InvokeMethod("Load"...) → LOADED + 4201
        for (int i=1;i<=5;i++)
        {
            var w = reg.CreateInstance("Substrate", $"W0{i}", new(){ ["SubstrateID"]=SecsItem.A($"W0{i}"), ["Slot"]=SecsItem.U1((byte)i) });
            tree.AddChild(car.ObjSpec, w.ObjSpec); // Carrier 物理包含
        }
        // 4-7 建 CJ/PJ，PJ 挂 CJ（包含），PJ 关联 W（不挂树）
        var cj = reg.CreateInstance("ControlJob", "CJ001", new(){ ["ControlJobID"]=SecsItem.A("CJ001") });
        var pj = reg.CreateInstance("ProcessJob", "PJ001", new()
        { ["LotID"]=SecsItem.A("LOT_A"), ["RecipeID"]=SecsItem.A("RCP_A"),
          ["PlannedCount"]=SecsItem.U2(5), ["SourceCarrier"]=SecsItem.A(car.ObjSpec) });
        tree.AddChild(cj.ObjSpec, pj.ObjSpec);

        // 9 列举子树
        Assert.Single(tree.GetChildren(cj.ObjSpec));
        // 10 订阅（PJ 只要 4102/4103，CJ 全部）—— 用 SubscriptionTable
        // 11-17 Start→逐片→Pause/Resume→Complete→CJ 聚合 COMPLETED
        // 断言：PJ 4101 被抑制、CJ 5102 发送、最终 CJ/PJ 都 COMPLETED
        // 20-22 Unload、级联删除、列举为空、无残留订阅
        tree.DeleteTree(cj.ObjSpec, inst => { /* 终态校验 + Unsubscribe */ });
        Assert.Empty(reg.ListInstances("ControlJob"));
        Assert.Empty(reg.ListInstances("ProcessJob"));
        // Carrier/Substrate 仍在（物理归属独立）
        Assert.Single(reg.ListInstances("Carrier"));
        Assert.Equal(5, reg.ListInstances("Substrate").Count);
    }
}

## 三、总图（手绘参考：对象树+状态机+消息流）
```
 Host(EAP)
   │ S14 发现 4 类型        S15 操作(建/挂/调方法/列举/删)     S16 事件(订阅过滤)
   ▼
 ┌─────────────── OSS 层 ───────────────┐

   状态机：QUEUED→EXECUTING⇄PAUSED→COMPLETED / →ABORTED

## 四、今日易错点
1. 让 PJ 和 Carrier 都包含 Substrate（违反唯一父；物理归属 Carrier，PJ 只关联）。
2. 允许 Host 直接把 CJ 置 COMPLETED（必须子 PJ 全完成聚合触发）。
3. 父驱动子和子冒泡方向混淆（命令自上而下，状态事件自下而上）。
4. 级联删除误删 Carrier 下的 Substrate（删 CJ 子树只删 PJ，Substrate 解关联保留）。
5. 删除对象不取消订阅（幽灵事件、内存泄漏）。
6. 订阅过滤把父级聚合事件也抑制（类型独立过滤，CJ 订阅全部则 CJ 事件照发）。
7. PJ 完成守卫不看片数（应 ProcessedCount==PlannedCount 才允许 Complete）。
8. 对象树挂载不经 CompositionRule（非法层级要拦截）。
9. 状态聚合只算一次不递归（多层树要冒泡到根）。
