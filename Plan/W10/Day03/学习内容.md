## 二、背景知识（先读，20 分钟）

### 1. 为什么需要订阅过滤
- 设备对象多、事件频繁（几百片晶圆每片都有多个事件），Host 往往只关心：
  - 特定类型（如只关心 ProcessJob，不关心 Chamber 内部细节事件）；
  - 特定实例（如只关心当前在跑的 PJ001）；
  - 特定 CEID（如只要 Started/Completed 终态，不要中间状态变化）。
- 全发的问题：网络流量大、Host 处理负担重、无关事件干扰。订阅过滤让设备只发 Host 需要的事件。

### 2. 三个订阅粒度（可组合）
- **按类型订阅（Type-level）**：订阅某对象类型的所有实例事件，如 "ProcessJob 的所有事件"。
- **按实例订阅（Instance-level）**：订阅具体 OBJSPEC，如 "ProcessJob:PJ001 的事件"。
- **按事件订阅（CEID-level）**：订阅特定 CEID，如 "只要 CEID=4102 Completed"。
- 组合规则：一条订阅可指定 (类型或实例) + CEID 集合（空=该范围全部 CEID）。
- 匹配优先级：实例订阅 > 类型订阅；CEID 白名单为空表示全部。

### 3. 订阅表 SubscriptionTable
- 每条订阅记录：SubscriptionId、Scope（Type 名或 OBJSPEC）、ScopeKind（Type/Instance）、CeidSet（空=全部）。
- 核心方法：
  - Add/Remove：增删订阅
  - ShouldEmit(objSpec, typeName, ceid)：事件发生时判定是否应发送
    - 先查实例级订阅是否命中（OBJSPEC 完全匹配且 CEID 在集合内或集合空）
    - 再查类型级订阅（类型匹配且 CEID 命中）
    - 都不命中则抑制（不发）
- 默认策略：无任何订阅时是否全发？两种约定——"空订阅=全发"（向后兼容）或"空订阅=不发"（显式订阅才发，更省流），项目要明确，**教学采用"空订阅=全发"，一旦有订阅则按白名单过滤**。

### 4. S16F3/F4 订阅管理（教学约定）
- **S16F3（Host→设备）订阅/退订请求**：
  ```
  L,3
    [0] U1 Action        // 1=订阅(Add) 2=退订(Remove) 3=清空全部订阅(Clear)
    [1] U1 ScopeKind     // 1=类型 2=实例
    [2] L,n              // 订阅目标
          [i] L,2
                [0] A Scope       // 类型名 或 OBJSPEC
                [1] L,k [U4 CEID] // CEID 白名单，空 L,0=全部事件
  ```
- **S16F4（设备→Host）**：`L,2[U1 ACKC, L,n 生效的订阅摘要]`。
- 退订可以按 SubscriptionId 精确移除，或按 Scope 移除该范围全部。

### 5. 设备端过滤 vs Host 端过滤
| 维度 | 设备端过滤（订阅表在设备） | Host 端过滤（设备全发） |
|---|---|---|
| 网络流量 | 小（只发订阅事件） | 大（全发） |
| 设备复杂度 | 高（维护订阅表、匹配） | 低（事件全发） |
| Host 负担 | 小（收的都要） | 大（自己过滤） |
| 灵活性 | 改订阅即可，动态 | Host 自由过滤，不依赖设备 |
| 多 Host | 每 Host 独立订阅表 | 全发给所有连接方 |
| 适用 | 事件高频、带宽敏感（EDA/Interface-A 尤其明显） | 事件少、设备算力弱、快速实现 |
- 专家实践：SECS/GEM 控制通道常用设备端订阅过滤；EDA（Interface-A，后续 M7）更是强制订阅模型（Data Collection Plan）。本教学实现设备端过滤。

### 6. 订阅的易失性与重连重建
- 订阅表存在内存，连接断开/设备重启后丢失（和 S2F33/S2F35 报告事件关联、S5F3 报警使能一样是易失配置）。
- Host 重连、重新建链（S1F13/S1F17）后，必须重新下发订阅（S16F3），否则设备按"空订阅"策略运行（教学=全发，显式订阅模式=不发）。
- Host 应把订阅集成本地持久化，SOFTREV 变化时重新评估订阅是否仍有效（CEID 可能变化）。
