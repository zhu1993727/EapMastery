## 二、背景知识（先读，40 分钟）

### 1. E164 EDA Common Metadata
- 解决"跨厂商、跨标准语义统一"：定义公共元数据表示与约定——标准命名（Well-Known Names）、单位与量纲、数据类型、枚举语义、公共对象/属性结构。
- **Well-Known Names（WKN）**：为通用物理量/状态定义标准路径与语义（如腔体温度、RF 正向功率、压力、载具状态、作业状态），设备把私有变量映射到 WKN，客户端用 WKN 即可跨设备统一取数（Day03 已建立印象，今天落地映射）。
- Freeze III 里 E164 还承担"公共 Protocol Buffers 元素的集中定义"，避免各标准重复定义、保证互操作。

### 2. 辅助标准角色
- **E128 / E138**：XML Semiconductor Common Components——Freeze II 用 XML 表达时的公共组件/Schema 构件（类型、结构、命名空间约定），让各标准 XML 一致。
- **E179**：与数据表示/互操作相关的辅助标准（具体主题以 SEMI 原文为准，理解为 Freeze 套件的支撑件）。
- **E147**：Guide for EDA，是**指南**（Guide，非强制规范），给实施方法与最佳实践，不定义强制接口。
- 记忆主线：E120 模型、E125 自描述、E132 授权会话、E134 采集计划、E164 公共元数据/WKN 是五大主标准；其余为辅助与指南。

### 3. 为什么有 Freeze（冻结版本）
- 各标准独立演进、版本不同步会导致互操作问题（设备支持 A 版本、客户端按 B 版本解析就出错）。SEMI 定期把相互配套的一组标准版本"冻结"成 Freeze 套件，声明这些版本一起使用保证互操作。
- Freeze I（早期）、**Freeze II（约 0710，SOAP/XML，存量 Fab 主流、成熟稳定）**、**Freeze III（新一代，Protocol Buffers，面向高吞吐/AI，正在推广）**。

### 4. Freeze II 的服务形态（SOAP/XML over HTTP）
- 设备 EDA Server 以 Web Services 暴露一组标准服务（教学归纳）：元数据/自描述服务、会话与授权服务、采集计划管理服务（创建/激活/暂停/删除）、数据回报服务（客户端也可暴露回调服务接收数据，SOAP 的双向服务特征）。
- 消息为 SOAP 信封包裹的 XML，遵循 E138 公共组件；人可读、防火墙友好、工具链成熟，但 XML 冗长、解析重、高频大数据带宽/CPU 开销大。

### 5. Freeze III 的演进（Protocol Buffers）
- 动因：FDC/VM/AI 需要更高频、更大数据量，XML 成为瓶颈；protobuf 二进制紧凑、序列化/反序列化快、schema(.proto)强类型、跨语言代码生成成熟。
- 变化点：**编码与传输**（XML/SOAP → protobuf，传输更接近 gRPC 风格的高效 RPC/流）；**不变点**：CEM 对象模型、自描述思想、授权会话、采集计划三触发、WKN 语义——模型语义完全延续。
- 工程含义：把"领域模型/采集引擎"与"编码传输层"解耦，就能同一内核切换 XML/protobuf（今天代码即练这个）。

### 6. 与 GEM 技术栈再对照（收口本周认知）
- GEM：HSMS(TCP 长连接)+SECS-II 二进制 TLV+SxFy 消息，控制事务。
- EDA FreezeII：HTTP+SOAP/XML；FreezeIII：HTTP2/gRPC+protobuf；多客户端订阅只读采集。两套并存、端口隔离、数据源共享。
