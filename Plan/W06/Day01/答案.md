# W06 · Day01 答案与参考

## 一、自测题标准答案
1. **SV vs DV / 同一物理量能否同时是 SV 和 DV**：SV（Status Variable，状态变量）是设备当前状态的只读变量，Host 可随时查询（S1F11），反映"现在是什么"；DV（Data Variable，数据变量）是事件触发时采集的变量，随 S6F11 上报，反映"事件发生时是什么"。**同一个物理量可以同时是 SV 和 DV**，但 VID 不同——例如温度可以是 SV（随时可查当前温度，VID=100），也可以是 DV（事件发生时的温度，VID=200）。这样设计是因为查询场景和事件采集场景的需求不同，分开定义更灵活。
2. **报告 vs 事件关系 / 为何分两步**：报告(RPTID)是"一组变量的集合"，定义采集什么；事件(CEID)是"数据采集的触发器"，定义什么时候采集。分两步（S2F33 定义报告、S2F35 关联事件）是因为**解耦**——一个报告可以被多个事件关联（复用报告模板，如"温度+压力"报告可以关联 Lot Start 和 Lot End 两个事件），一个事件也可以关联多个报告（一次事件触发多份报告，如 Lot End 同时上报"工艺数据报告"和"质量数据报告"）。如果合成一步，每次定义都要重复变量列表，灵活性差。
3. **DATAID 含义 / Host 为何需要知道**：DATAID（Data Collection Definition ID）是数据收集定义 ID，标识当前这套"报告定义+事件关联"的配置版本。Host 每次重新配置（S2F33/S2F35）后 DATAID 变化，设备在 S6F11 中带回 DATAID。Host 需要知道 DATAID 是为了**确认报告是按哪套配置采集的**——如果 Host 刚改了报告定义，但收到的 S6F11 还带旧 DATAID，说明设备还在用旧配置，Host 可以判断数据是否符合预期。DATAID 也用于 S6F12 确认（Host 回 DATAID 表示收到了哪套配置的报告）。
4. **哪步定义采集什么 / 哪步定义什么时候采集**：**S2F33 定义报告**是"定义采集什么"（指定 RPTID 包含哪些 VID 变量）；**S2F35 关联事件**是"定义什么时候采集"（指定 CEID 事件触发时采集哪些 RPTID 报告）。两者配合：报告定义内容，事件定义时机。
5. **Host 怎么知道设备支持哪些 SV/事件 / 用什么消息查询**：Host 通过查询消息获取设备能力列表：
   - **SV 列表**：S1F3（Request Status Variable List）→ 设备回 S1F4（Status Variable List，含 VID 和 SV 名称）。
   - **SV 值**：S1F11（Request Status Variable Data，指定 VID 列表）→ 设备回 S1F12（Status Variable Data，含各 VID 的当前值）。
   - **事件列表**：S1F5（Request Collection Event List）→ 设备回 S1F6（Collection Event List，含 CEID 和事件名称）。
   - **报告列表**：S1F7（Request Report List）→ 设备回 S1F8（Report List，含已定义的 RPTID）。
   - 这些查询通常在建链完成后、配置数据采集前执行。
6. **一个事件能否关联多个报告 / 一个报告能否被多个事件关联 / 为何这样设计**：**都可以**。一个事件(CEID)可以关联多个报告(RPTID)——一次事件触发时，设备同时采集多份报告并一起上报（如 Lot End 事件同时上报工艺数据报告和质量数据报告，S6F11 的报告列表里有多个报告）。一个报告可以被多个事件关联——同一份变量模板可以在不同事件触发时采集（如"温度+压力"报告在 Lot Start 和 Lot End 都上报，分别反映开始和结束时的值）。这样设计是为了**复用和灵活组合**——避免重复定义相同的变量集合，也允许一次事件触发多份数据。这是 GEM 数据采集体系的核心设计思想。

## 三、7 概念速查表
| 概念 | 全称 | 含义 | 查询/定义消息 |
|---|---|---|---|
| SV | Status Variable | 状态变量，设备当前状态，只读，随时可查 | S1F3(列表)、S1F11(值) |
| DV | Data Variable | 数据变量，事件触发时采集，随 S6F11 上报 | 不能单独查询，在报告中获取 |
| VID | Variable ID | 变量 ID，变量的唯一标识（SV/DV 都有）| S1F3 查询 |
| CEID | Collection Event ID | 集合事件 ID，设备发生的事件，数据采集触发器 | S1F5(列表) |
| RPTID | Report ID | 报告 ID，报告的唯一标识，一组变量的集合 | S1F7(列表)、S2F33(定义) |
| DATAID | Data Collection Definition ID | 数据收集定义 ID，标识当前配置版本 | S6F11 中带回、S6F12 确认 |
| ECID | Equipment Constant ID | 设备常量 ID，设备可配置参数 | S2F13(查询)、S2F14(修改) |

## 五、今日易错点
1. 混淆 SV 和 DV（SV 随时可查，DV 事件时采集，同一物理量可同时是两者但 VID 不同）。
2. 以为报告和事件是一对一（一个事件可关联多个报告，一个报告可被多个事件关联）。
3. 以为 S2F33 定义报告时就指定了事件（S2F33 只定义变量集合，事件关联在 S2F35）。
4. 忽略 DATAID 的作用（DATAID 标识配置版本，Host 据此判断数据是否符合预期）。
5. 以为 DV 可以单独查询（DV 只能在事件报告中获取，不能像 SV 那样随时查询）。
6. 建链后不查询设备能力就盲目定义报告（可能引用不存在的 VID/CEID，导致 S2F34/S2F36 拒绝）。
7. 混淆 RPTID 和 VID（RPTID 是报告 ID，VID 是变量 ID，报告包含变量）。
