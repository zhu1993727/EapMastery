## 二、背景知识（先读，25 分钟）

### 1. S2F33 body 结构（必背）
```
S2F33 Define Report (Host → Equipment, W=1)
body = L,2[
  U2 RPTID,              // 报告 ID（要定义/覆盖的报告）
  L,n[                   // 该报告包含的变量 ID 列表（n 个 VID）
    U2 VID,              // 变量 ID（SV 或 DV 的 VID）
    U2 VID,
    ...
  ]
]
```
- RPTID：U2 类型，报告的唯一标识。Host 指定要定义的报告 ID。
- VID 列表：L,n[U2]，该报告包含哪些变量。n 可以为 0（空列表，表示删除该报告或定义一个空报告，具体含义见下）。
- 注意：VID 可以是 SV 的 VID，也可以是 DV 的 VID——报告里可以混合 SV 和 DV。事件触发时，设备采集报告中每个 VID 的当前值（SV 取当前值，DV 取事件时刻的值）。

### 2. S2F34 body 结构（必背）
```
S2F34 Define Report Acknowledge (Equipment → Host, W=0)
body = L,2[
  U1 ACKC5,              // 定义结果（0=成功，非0=失败）
  U2 RPTID               // 对应的报告 ID
]
```
- ACKC5 常见值：
  - **0 = 成功**（报告已定义/覆盖）
  - **1 = 拒绝**（设备不允许定义报告，如通信 OFF-LINE）
  - **2 = 报告 ID 不存在/无效**（RPTID 超出设备支持范围）
  - **3 = 变量 ID 不存在**（VID 列表中有设备不支持的 VID）
  - **4 = 其他错误**
- 具体值以设备实现为准，核心是 0=成功，非0=各种失败。

### 3. 定义报告的规则
1. **RPTID 唯一**：每个 RPTID 标识一个报告。如果 RPTID 已存在，S2F33 会**覆盖**原报告（用新的 VID 列表替换旧的）。
2. **VID 必须存在**：VID 列表中的每个 VID 必须是设备支持的变量（SV 或 DV）。如果有不存在的 VID，设备回 ACKC5=3（变量 ID 不存在），整个报告定义失败。
3. **空 VID 列表**：如果 VID 列表为空（L,0），表示**删除该报告**（或定义一个空报告，具体以设备实现为准）。标准实践是用空列表删除报告。
4. **报告数量限制**：设备通常支持有限数量的报告（如最多 256 个），超出限制会拒绝。
5. **定义顺序**：先定义报告（S2F33），再关联事件（S2F35）。如果 S2F35 引用了未定义的 RPTID，会失败。
6. **重新定义的影响**：如果报告已被事件关联，重新定义该报告（覆盖 VID 列表）后，关联关系不变，但报告内容变了——后续事件触发时按新的 VID 列表采集。

### 4. 报告的存储与查询
- 设备维护一个报告定义表：`Dictionary<RPTID, List<VID>>`。
- Host 可通过 S1F7（Request Report List）查询已定义的报告列表（返回所有 RPTID）。
- Host 可通过 S1F9（Request Report Variable List，指定 RPTID）查询某个报告包含哪些 VID。
- 报告定义通常在设备重启后丢失（除非设备支持持久化），Host 每次建链后需要重新定义报告。

### 5. 定义报告的完整流程
```
1. Host 查询 SV 列表：S1F3 → S1F4（获取所有支持的 VID）
2. Host 定义报告1：S2F33(RPTID=1, VID=[100,101,102]) → S2F34 ACKC5=0
3. Host 定义报告2：S2F33(RPTID=2, VID=[200,201]) → S2F34 ACKC5=0
4. Host 查询报告列表：S1F7 → S1F8（返回 RPTID=[1,2]）
5. Host 查询报告1内容：S1F9(RPTID=1) → S1F10（返回 VID=[100,101,102]）
```
