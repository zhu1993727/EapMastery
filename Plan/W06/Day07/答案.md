## 三、现场排障方法论（专家必会，费曼重点）

### "Host 收不到 S6F11"排查（9 步）
1. **通信状态**：设备通信 ON-LINE？控制 ONLINE？（OFF-LINE 时事件可能不上报或缓存）
2. **事件是否发生**：设备端确认事件真的发生了？（看设备日志、状态变化、操作员操作）
3. **事件是否关联了报告**：S1F7/S1F9 查询，S2F35 关联了吗？（未关联就不上报，最常见原因）
4. **报告是否定义了**：S1F7 查询报告列表，RPTID 存在吗？（报告未定义，关联会失败 ACKC6=3）
5. **报告是否包含变量**：S1F9 查询报告包含的 VID，VID 列表非空？（空报告可能不上报）
6. **S6F11 是否发出**：设备端抓包/日志，看 S6F11 是否发出？（发出了但 Host 没收到=通信问题，没发出=配置问题）
7. **S6F12 是否回了**：Host 是否回了 S6F12？（不回可能导致设备重发或停止上报）
8. **Spool 状态**：通信中断时事件是否被 Spool 缓存？（W8 细讲）
9. **DATAID**：当前 DATAID 是多少？配置是否生效？

### "S6F11 收到了，但变量值解析不对"排查
1. **报告定义是否正确**：S1F9 查询报告包含的 VID，确认 VID 列表和 Host 预期一致。
2. **变量值顺序是否正确**：S6F11 中变量值按 S2F33 定义的 VID 顺序排列，Host 按位置解析。如果 Host 记错了 VID 顺序，会解析错。
3. **变量类型是否正确**：Host 的 VID→类型映射是否正确？（从设备文档或 S1F11 推断）如果类型映射错，会把 F4 当 U2 解析。
4. **DATAID 是否匹配**：S6F11 的 DATAID 是否是 Host 期望的最新配置？如果带旧 DATAID，说明报告是按旧配置采集的，变量列表可能不同。
5. **多报告时报告顺序**：S6F11 中报告按 S2F35 关联时的 RPTID 顺序排列，Host 按报告位置解析。如果 Host 记错了报告顺序，会把报告1的值当报告2解析。
6. **变量值是否为空/异常**：设备采集变量时是否失败？（采集失败用空字符串占位，Host 解析时类型不匹配）

## 四、费曼参考脚本（对照录音）
"设备发生一个 Lot Start 事件，Host 收到温度和压力数据，前提是 Host 已经完成了数据采集配置——建链后先做能力发现：S1F3 查设备支持哪些 SV（温度 VID=100，压力 VID=101），S1F5 查设备支持哪些事件（Lot Start CEID=3001）。然后 Host 定义报告：S2F33 指定 RPTID=1 包含 VID=[100,101]，设备回 ACKC5=0，DATAID 递增。接着 Host 关联事件：S2F35 指定 CEID=3001 关联 RPTID=[1]，设备回 ACKC6=0。现在配置完成了。当设备发生 Lot Start 事件（CEID=3001），设备查关联表找到 RPTID=[1]，查报告定义找到 VID=[100,101]，采集温度的当前值（F4=25.5）和压力的当前值（U2=100），组装 S6F11 body：L,3[U4 DATAID=1, U2 CEID=3001, L,1[L,2[U2 RPTID=1, L,2[F4=25.5, U2=100]]]]]，发给 Host。Host 收到后解析，回 S6F12 确认。如果 Host 收不到 S6F11，按 9 步排查：通信状态→事件是否发生→是否关联报告→报告是否定义→报告是否有变量→S6F11 是否发出→S6F12 是否回→Spool→DATAID。核心是：先发现能力，再配置采集，最后数据上报；变量→报告→事件三层解耦。"

## 五、W7(E30 报警/远程命令/配方) 三问思考方向（先自己想，W7 揭晓）
1. **S5F1 vs S6F11 区别 / 报警需要定义报告关联事件吗**：S5F1（Alarm Report Send）是报警上报，S6F11（Event Report Send）是事件上报。区别：①报警是设备的异常状态通知（有 ALID、ALCD、ALTX），事件是设备的状态变化/操作通知；②S5F1 的 body 结构不同（L,2[U4 ALID, A ALTX] 或更复杂），不需要像 S6F11 那样先定义报告、关联事件——报警是设备主动上报的，Host 通过 S5F3 使能/禁用报警，不需要 S2F33/S2F35 配置；③报警有专门的使能/禁用机制（S5F3），事件有报告关联机制（S2F35）。简单说：报警是"异常通知"，事件是"数据采集触发器"，两者机制不同。
2. **S2F41 同步还是异步 / Host 怎么知道完成 / 失败怎么通知**：S2F41 是**异步**的。S2F42 ACKC10=0 只表示"命令已被设备接受并排队"，不是执行完成。Host 通过 **S6F11 事件上报**知道命令执行结果——设备执行完命令后触发"命令完成"或"命令失败"事件（CEID），通过 S6F11 上报，Host 回 S6F12 确认。命令执行失败时，设备也通过 S6F11 事件通知（事件中包含失败原因，或通过报警 S5F1 通知异常）。Host 也可以通过 S1F11 查询状态变量主动查询命令执行状态，但事件上报是标准方式。
3. **S7 系列消息 / 配方上传下载流程 / 配方和 R2R 关系**：S7 Stream 是"配方管理"（Process Program Management），常见消息：S7F1（配方上传请求，Host→设备，指定 PPID）、S7F2（配方上传，设备→Host，返回配方内容）、S7F3（配方下载请求，Host→设备，指定 PPID 和配方内容）、S7F4（配方下载确认，设备→Host，ACKC7）、S7F5（删除配方，Host→设备）、S7F6（删除确认）、S7F17（删除配方）、S7F18（删除确认）。配方上传流程：Host 发 S7F1（指定 PPID）→ 设备回 S7F2（返回配方内容，可能多块消息）。配方下载流程：Host 发 S7F3（指定 PPID + 配方内容）→ 设备回 S7F4（ACKC7=0 表示接受）。配方和 R2R 的关系：R2R（Run-to-Run）控制不直接修改配方主档，而是计算参数偏移（overlay），在设备执行配方时叠加偏移量。RMS（Recipe Management System）管理配方主档，R2R 管理偏移量，最终执行参数=基础配方(RMS)+R2R偏移。两者不直接互调，但要版本对齐和审计。（W7 细讲配方，M7-M9 进阶细讲 R2R）
