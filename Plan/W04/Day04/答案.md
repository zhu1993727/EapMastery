# W04 · Day04 答案与参考实现

## 一、自测题标准答案
1. **S9 的 W 位**：必须是 **0**。S9 是单向错误通知，不是请求-应答事务，不需要对端回 reply。如果 W=1，对端可能回 S9 的偶数 F reply，造成不必要的消息循环。
2. **S15F1（不支持的 Stream）回 S9F3**：Unknown Stream。Stream=15 本端不认识/不支持，回 S9F3。
3. **S1F99（Stream 认识但 Function 不支持）回 S9F5**：Unknown Function。Stream=1 认识，但 Function=99 不支持，回 S9F5。
4. **S9 body 带原始消息头的原因**：让对端知道"是哪条消息被拒绝了"。对端可能同时有多个在途事务，仅凭 S9 的 S/F 无法定位具体是哪条 primary 出错；带上原始消息头（含 SystemBytes、原始 S/F），对端就能精确匹配未决事务并触发错误回调。
5. **T3 超时是否主动发 S9F9**：**是**。本端发的 primary 在 T3 时间内没收到 reply，本端判定事务超时，此时应主动发 **S9F9** 给对端，通知"你没及时回我，我不等了"。S9F9 的 body 带那条超时 primary 的原始消息头。注意：S9F9 是"超时通知"，不是"超时本身"——超时由 T3 判定，S9F9 是把这个结果通知对端。
6. **收到 S9F7 后未决事务处理**：从 S9F7 body 中提取原始消息头，按原始 SystemBytes 在未决事务表中匹配，找到后触发该事务的 **Error 回调**（状态变为 Error），并从未决事务表移除。上层业务根据错误类型（非法数据）决定是否修正后重发、上报告警或放弃。
7. **S9F1 和 S9F3 的触发顺序**：先校验 **Device ID（S9F1）**，再校验 **Stream（S9F3）**，再校验 **Function（S9F5）**。原因：Device ID 是最外层的身份校验——如果消息根本不是发给本设备的，后面的 Stream/Function 校验没有意义；先排除"发错设备"，再逐步深入校验消息内容。这是"从粗到细"的校验顺序，也符合错误定位的逻辑。

## 二、参考实现（EapLab.Secs2/Transaction/）

### S9ErrorSender.cs
```csharp
using EapLab.Secs2.Items;
using EapLab.Transport.Hsms;

namespace EapLab.Secs2.Transaction;

public enum S9ErrorType
{
    UnknownDeviceId = 1,    // S9F1
    UnknownStream = 3,      // S9F3
    UnknownFunction = 5,    // S9F5
    IllegalData = 7,        // S9F7
    ConversationTimeout = 9,// S9F9
    DataTooLong = 11        // S9F11
}

public sealed class S9ErrorSender
{
    private readonly Action<byte, byte, bool, SecsItem?> _sendData;
    public S9ErrorSender(Action<byte, byte, bool, SecsItem?> sendData)
        => _sendData = sendData;

    /// <summary>构造并发送 S9 错误通知。originalHeader 是出错消息的 10 字节 HSMS 头。</summary>
    public void Send(S9ErrorType type, byte[] originalHeader)
    {
        // S9 body：把原始 10 字节头作为 Binary 数组
        var body = Secs.L(Secs.B(originalHeader));
        byte f = (byte)type;   // S9F1/F3/F5/F7/F9/F11
        _sendData(9, f, w: false, body);   // W=0，不需要回复
    }

    // 便捷方法
    public void UnknownDeviceId(byte[] h) => Send(S9ErrorType.UnknownDeviceId, h);
    public void UnknownStream(byte[] h) => Send(S9ErrorType.UnknownStream, h);
    public void UnknownFunction(byte[] h) => Send(S9ErrorType.UnknownFunction, h);
    public void IllegalData(byte[] h) => Send(S9ErrorType.IllegalData, h);
    public void ConversationTimeout(byte[] h) => Send(S9ErrorType.ConversationTimeout, h);
    public void DataTooLong(byte[] h) => Send(S9ErrorType.DataTooLong, h);
}
```

### 接收管线自动回 S9（在 HsmsConnection.DispatchData 中）
```csharp
private void DispatchData(HsmsHeader h, byte[] rawBody, byte[] rawHeader)
{
    // 1. 校验 Device ID（Session ID）
    if (h.SessionId != _expectedSessionId && h.Stream != 9)
    {
        _s9.UnknownDeviceId(rawHeader);
        return;
    }

    // 2. 校验 Stream 是否支持
    if (!IsStreamSupported(h.Stream))
    {
        _s9.UnknownStream(rawHeader);
        return;
    }

    // 3. 校验 Function 是否支持
    if (!IsFunctionSupported(h.Stream, h.Function))
    {
        _s9.UnknownFunction(rawHeader);
        return;
    }

    // 4. 校验数据长度
    if (rawBody.Length > _maxDataLength)
    {
        _s9.DataTooLong(rawHeader);
        return;
    }

    // 5. SECS-II 解码
    SecsItem? body = null;
    try
    {
        if (rawBody.Length > 0)
            body = SecsItem.Decode(rawBody, out int used);
    }
    catch (Exception ex)
    {
        _log.Log(LogDir.ERR, $"SECS-II 解码失败 S{h.Stream}F{h.Function}: {ex.Message}");
        _s9.IllegalData(rawHeader);
        return;
    }

    // 6. 正常分发
    if (h.Stream == 9)   // 收到 S9 错误通知
    {
        HandleS9Received(h, body);
        return;
    }
    if (h.Function % 2 == 0)
        _txMgr.TryMatchReply(h.SystemBytes, body);
    else
        OnPrimaryReceived?.Invoke(h, body);
}

private void HandleS9Received(HsmsHeader h, SecsItem? body)
{
    // 从 body 中提取原始消息头，按原始 SystemBytes 匹配事务
    uint? originalSys = ExtractOriginalSystemBytes(body);
    if (originalSys is { } sys)
    {
        _txMgr.TryMatchError(sys, body?.Encode() ?? Array.Empty<byte>());
    }
    _log.Log(LogDir.ERR, $"收到 S9F{h.Function}，原始 sys={originalSys?.ToString("X8") ?? "未知"}");
}
```

### T3 超时主动发 S9F9（在 TransactionManager 超时回调中）
```csharp
// 在 TransactionManager.ScanTimeout 中，事务超时时不仅触发回调，还通知上层发 S9F9
public event Action<SecsTransaction>? OnTransactionTimeout;

public void ScanTimeout(DateTime now, byte[]? originalHeader = null)
{
    foreach (var tx in _pending.Values)
    {
        if (tx.IsTimedOut(now))
        {
            if (_pending.TryRemove(tx.SystemBytes, out _))
            {
                tx.CompleteWithTimeout();
                OnTransactionTimeout?.Invoke(tx);   // 上层收到后发 S9F9
            }
        }
    }
}
// 上层：
_txMgr.OnTransactionTimeout += tx => _s9.ConversationTimeout(tx.OriginalHeaderBytes);
```

## 三、S9 速查卡（默写版）
| S9F | 名称 | 触发时机 | body |
|---|---|---|---|
| S9F1 | Unknown Device ID | Session/Device ID 不匹配 | 原始头 |
| S9F3 | Unknown Stream | Stream 不支持 | 原始头 |
| S9F5 | Unknown Function | Stream 支持但 Function 不支持 | 原始头 |
| S9F7 | Illegal Data | SECS-II 解码失败/数据非法 | 原始头 |
| S9F9 | Conversation Timeout | 本端 primary T3 超时 | 原始头 |
| S9F11 | Data Too Long | 数据超过本端处理上限 | 原始头 |
共性：W=0、单向通知、不要求回复、body 带原始消息头。

## 四、今日易错点
1. S9 消息置 W=1（应 W=0，单向通知）。
2. 不支持的 Stream 回 S9F5（应回 S9F3；S9F5 是 Function 不支持）。
3. S9 body 不带原始消息头（对端无法定位哪条消息出错）。
4. T3 超时只触发本地回调，不发 S9F9 通知对端（应主动发 S9F9）。
5. 收到 S9 后不匹配未决事务，事务一直 Pending（应按原始 sys 匹配并触发 Error 回调）。
6. 校验顺序错误（先校验 Function 再校验 Stream，应从粗到细：Device→Stream→Function→数据）。
7. S9F9 当成"对端超时"（是本端超时后通知对端，方向不要搞反）。
