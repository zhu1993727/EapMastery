## 二、背景知识（先读，20 分钟）

### 1. S9 是什么
- S9 是 **SECS-II 错误通知系列**，当一方收到一条无法处理的消息时，用 S9 通知对方"你的消息我处理不了，原因是 X"。
- S9 消息都是 **primary（F 奇数）**，且 **W=0**（不需要回复）——它是单向错误通知，不是事务。
- S9 不是"我出错了"，而是"你发的消息我处理不了"。

### 2. S9 系列消息表（必背）
| 消息 | 名称 | 触发时机 |
|---|---|---|
| S9F1 | Unknown Device ID | 收到的消息 Session/Device ID 与本端不匹配 |
| S9F3 | Unknown Stream | 收到的 Stream 本端不认识/不支持 |
| S9F5 | Unknown Function | 收到的 Stream 认识但 Function 不支持 |
| S9F7 | Illegal Data | 消息数据格式非法、SECS-II 解码失败、数据内容不符合预期 |
| S9F9 | Conversation/Transaction Timeout | 本端发的 primary 等 reply 超时（T3），通知对端"我不等了" |
| S9F11 | Data Too Long | 收到的消息数据太长，超过本端处理能力 |

> S9F2/F4/F6/F8/F10/F12 是对应的 reply，但 S9 通常 W=0 不要求回复，实践中几乎只见 S9F 奇数。

### 3. S9 消息的 body 结构
- S9 消息的 body 通常包含**原始出错消息的 HSMS 消息头（10 字节）**，用于标识是哪条消息出错。
- 常见表示方式：把原始 10 字节头作为 B（Binary）或 U1 数组放在 body 中。
- 具体结构以 E5 原文为准，但核心是"带上原始消息头，让对端知道哪条消息被拒了"。
- S9F9（超时）的 body 也带原始消息头，标识是哪条 primary 超时了。

### 4. S9 的触发与处理流程
**发送方（回 S9 的一方）**：
```
收到消息 → 校验 Device ID → 不匹配 → 回 S9F1
         → 校验 Stream → 不认识 → 回 S9F3
         → 校验 Function → 不支持 → 回 S9F5
         → SECS-II 解码 → 失败/非法 → 回 S9F7
         → 数据长度 → 超过上限 → 回 S9F11
         → 全部通过 → 正常业务处理
```
**接收方（收到 S9 的一方）**：
```
收到 S9Fx → 从 body 中提取原始消息头 → 按原始 SystemBytes 匹配未决事务
         → 触发事务的错误回调（Error 状态）→ 移除未决事务
         → 记日志告警
```

### 5. S9 与事务管理器的配合
- Day02 的 TransactionManager 已有 `TryMatchError(sys, s9Body)` 方法。
- 接收管线中，收到 S9F 奇数时，提取原始 sys，调用 `TryMatchError`，触发对应事务的错误回调。
- 事务状态变为 Error，上层业务可根据错误类型决定重试、上报或放弃。
