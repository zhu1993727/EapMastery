# W04 · Day03（周三）多块消息与拼接

> 建议时长：75 分钟。今天讲"一条 SECS-II 消息太大、一个 HSMS 帧装不下时怎么办"。目标：理解多块消息的概念、拼接状态机，以及实际现场中"多块"的真实形态（S7 配方分块传输）。

## 一、今日目标
1. 理解多块消息（Multi-block Message）的概念、必要性与触发条件。
2. 掌握多块消息的标识方式与拼接状态机（收集→拼接→交付）。
3. 了解实际现场中"大消息"的真实处理方式（S7 配方分块、设备实现限制）。

## 二、背景知识（先读，20 分钟）

### 1. 为什么需要多块
- HSMS 帧长度字段是 4 字节大端，理论最大 ~4GB，但**实际设备实现有缓冲区限制**（常见 1MB~8MB，老设备甚至 256KB）。
- 一条 SECS-II 消息（如大配方、大批量事件报告）可能超过单帧限制，需要分成多个 HSMS 块传输。
- 接收方收集所有块，按顺序拼接成完整 body，再交给 SECS-II 解码器。

### 2. 多块消息的标识（以 E37 原文为准）
- 所有块的 **Stream/Function 相同**，**SystemBytes 相同**（属于同一条消息）。
- 块之间通过 HSMS 头中的标志位区分"是否还有后续块"（常见实现用头中保留位作为 M-bit / More-bit；具体位定义以 E37 原文及设备实现为准）。
- 最后一个块标志"无后续块"，接收方收到后拼接完整消息。
- **W 位只在最后一个块上有意义**（是否要求 reply），中间块 W=0。

### 3. 拼接状态机（必背）
```
Idle → 收到首块(M=1) → Collecting(按 sys 缓存 body 片段)
Collecting → 收到中间块(M=1) → 追加片段，继续 Collecting
Collecting → 收到末块(M=0) → 拼接所有片段 → 交付完整消息 → Idle
Collecting → 超时(T3 内未收齐) → 丢弃缓存，记错误 → Idle
```
- 收集器按 SystemBytes 索引，同一 sys 的块归到同一收集会话。
- 块必须按顺序到达（HSMS 保证 TCP 有序，所以块顺序天然有序）。
- 收到末块后，拼接总长度 = 各块 body 长度之和，校验是否合理。

### 4. 实际现场中的"大消息"
- **很多设备不支持通用多块消息**，而是对单条消息大小做硬限制（如最大 1MB），超过就报错或截断。
- **S7 配方传输**是最常见的"大消息"场景，但它通常不用通用多块，而是用 S7 专门的分块协议：S7F3（配方上传请求）→ 设备分多块 S7F4 上传，每块带块号和"是否最后一块"标志，Host 逐块确认。这是应用层分块，不是 HSMS 多块。
- 实践中，EAP 开发者更常遇到的是**应用层分块**（S7 配方、大批量数据上传），而不是 HSMS 层多块。但理解 HSMS 多块的拼接状态机，对理解应用层分块有直接帮助。

### 5. 块收集器的工程要点
- 用 `ConcurrentDictionary<uint, MemoryStream>` 按 sys 缓存片段。
- 收到末块后，把 MemoryStream 转成 byte[]，交给 SECS-II 解码器。
- 超时清理：T3 内未收齐的收集会话必须清理，防止内存泄漏。
- 异常块（sys 不在收集中、顺序错乱）：记错误，丢弃或请求重发。
