# W04 · Day03 答案与参考实现

## 一、自测题标准答案
1. **多块消息的相同字段 / 末块标识**：所有块的 **Stream、Function、SystemBytes** 必须相同（属于同一条逻辑消息）。"是否最后一块"由 HSMS 头中的标志位（M-bit / More-bit，具体位定义以 E37 原文为准）区分：中间块标志"还有后续"，末块标志"无后续"。
2. **首块 vs 中间块处理**：首块到达时，收集器中没有该 sys 的会话，需要**新建收集会话**（创建 MemoryStream、记录首块到达时间），然后追加片段；中间块到达时，收集器中已有该 sys 的会话，直接**追加片段**即可，不需要新建。
3. **为何必须超时清理**：如果末块永远不到达（对端崩溃、网络中断、块丢失），收集会话会一直占用内存，sys 也无法复用；大量未完成的收集会话会导致内存泄漏（OOM 风险）。必须在 T3（或专门的块收集超时）内未收齐时，丢弃缓存、记错误、释放资源。
4. **HSMS 多块 vs S7 应用层分块**：HSMS 多块是**传输层**机制，对应用透明，由 HSMS 栈自动分块/拼接，所有 S/F 消息都可用；S7 配方分块是**应用层**协议，在 S7F3/F4 消息体中带块号、总块数、是否末块等字段，由业务逻辑逐块请求/确认。实际现场更常见的是**应用层分块**（尤其是 S7 配方传输），很多设备的 HSMS 栈不支持通用多块，而是限制单条消息大小。
5. **第 2 块丢失时拼接状态机**：TCP 保证可靠有序传输，正常情况下块不会丢失或乱序。但如果应用层 bug 导致块丢失（如发送方漏发一块），接收方会一直停在 Collecting 状态，等待永远不会到来的末块，直到超时清理。这就是为什么必须有超时机制——不能无限等待。
6. **W 位放在哪个块**：W 位只在**最后一个块**上有意义（表示整条消息是否要求 reply），中间块的 W 位应为 0。因为 reply 是对整条逻辑消息的回复，不是对单个块的回复。

## 二、参考实现（EapLab.Secs2/Transaction/）

### BlockCollector.cs
```csharp
using System.Collections.Concurrent;

namespace EapLab.Secs2.Transaction;

/// <summary>多块消息收集器：按 sys 收集片段，末块到达后拼接交付。</summary>
public sealed class BlockCollector
{
    private readonly ConcurrentDictionary<uint, CollectSession> _sessions = new();
    public TimeSpan Timeout { get; init; } = TimeSpan.FromSeconds(45);

    /// <summary>
    /// 收到一个块。isLast=true 表示末块。
    /// 返回：末块到达时返回拼接后的完整 body；否则返回 null（继续收集）。
    /// </summary>
    public byte[]? OnBlock(uint sys, byte[] chunk, bool isLast)
    {
        var session = _sessions.GetOrAdd(sys, _ => new CollectSession());
        lock (session)   // 同一 sys 的块可能并发到达（虽然 TCP 有序，但接收线程可能并行）
        {
            session.Buffer.Write(chunk, 0, chunk.Length);
            session.LastBlockAt = DateTime.UtcNow;
            if (!isLast) return null;

            // 末块：拼接交付
            var full = session.Buffer.ToArray();
            _sessions.TryRemove(sys, out _);
            return full;
        }
    }

    /// <summary>由统一 Tick 驱动，清理超时未收齐的会话。</summary>
    public void ScanTimeout(DateTime now)
    {
        foreach (var kv in _sessions)
        {
            if (now - kv.Value.FirstBlockAt > Timeout)
            {
                if (_sessions.TryRemove(kv.Key, out var s))
                {
                    s.Buffer.Dispose();
                    // 记日志：多块消息 sys=... 超时未收齐，已丢弃
                }
            }
        }
    }

    public int ActiveSessions => _sessions.Count;

    private sealed class CollectSession : IDisposable
    {
        public MemoryStream Buffer { get; } = new();
        public DateTime FirstBlockAt { get; } = DateTime.UtcNow;
        public DateTime LastBlockAt { get; set; }
        public void Dispose() => Buffer.Dispose();
    }
}
```

// 在 DispatchData 中，先判断是否多块
private void DispatchData(HsmsHeader h, byte[] body)
{
    bool moreBlocks = HasMoreBit(h);   // 从头中解析 M-bit（具体位以 E37 为准）
    if (moreBlocks || IsMidBlock(h))   // 中间块或首块
    {
        var full = _blockCollector.OnBlock(h.SystemBytes, body, isLast: !moreBlocks);
        if (full == null) return;       // 继续收集
        body = full;                    // 拼接完成，用完整 body 继续后续处理
    }
    // 后续：SECS-II 解码、事务匹配等
}

### 多块拼接测试
```csharp
[Fact]
public void 一条消息分3块_拼接结果与原消息一致()
{
    var collector = new BlockCollector();
    var original = Enumerable.Range(0, 300).Select(i => (byte)(i % 256)).ToArray();
    var block1 = original.Take(100).ToArray();
    var block2 = original.Skip(100).Take(100).ToArray();
    var block3 = original.Skip(200).ToArray();

    Assert.Null(collector.OnBlock(123, block1, isLast: false));
    Assert.Null(collector.OnBlock(123, block2, isLast: false));
    var full = collector.OnBlock(123, block3, isLast: true);

    Assert.NotNull(full);
    Assert.Equal(original, full);
    Assert.Equal(0, collector.ActiveSessions);
}

[Fact]
public void 超时未收齐_会话被清理()
{
    var collector = new BlockCollector { Timeout = TimeSpan.FromMilliseconds(50) };
    collector.OnBlock(456, new byte[]{1,2,3}, isLast: false);
    Assert.Equal(1, collector.ActiveSessions);
    Thread.Sleep(100);
    collector.ScanTimeout(DateTime.UtcNow);
    Assert.Equal(0, collector.ActiveSessions);
}
```

## 三、HSMS 多块 vs 应用层分块对比表
| 维度 | HSMS 多块（传输层） | 应用层分块（如 S7 配方） |
|---|---|---|
| 层级 | HSMS/E37 | 业务消息（S7F3/F4 等） |
| 透明度 | 对应用透明，HSMS 栈自动处理 | 业务逻辑显式处理 |
| 块标识 | HSMS 头 M-bit | 消息体中块号/总块数/末块标志 |
| 适用范围 | 所有 S/F 消息 | 特定消息（S7 配方、大批量数据） |
| 现场普及度 | 很多设备不支持 | 常见（尤其是配方传输） |
| 拼接位置 | HSMS 接收管线 | 业务层 |

## 四、今日易错点
1. 多块消息的 SystemBytes 各块不同（必须相同，属于同一条逻辑消息）。
2. 中间块也置 W=1（W 位只在末块有意义）。
3. 收集器不做超时清理（内存泄漏风险）。
4. 拼接时不按顺序（TCP 保证有序，但收集器仍应假设块可能乱序，至少做校验）。
5. 把 HSMS 多块和 S7 应用层分块混为一谈（两者层级不同，现场更常见应用层分块）。
6. 末块到达后不清理收集会话（sys 无法复用，内存泄漏）。
