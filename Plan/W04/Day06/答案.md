# W04 · Day06 答案与综合实验参考

## 一、自测题标准答案
1. **为何用 TaskCompletionSource 而非轮询**：TaskCompletionSource 是事件驱动的——reply 到达时立即 SetResult，调用方精准唤醒，不占用 CPU；Thread.Sleep 轮询会有延迟（轮询间隔）、浪费 CPU，且无法及时响应。TCS 是异步事务 API 的标准实现。
2. **W=0 为何不能用 SendAndWaitReply**：SendAndWaitReply 会登记未决事务并等待 reply，但 W=0 的消息对端不应回 reply，所以会永远等到超时。如果误用了，表现为"每次 W=0 消息都超时"，浪费 T3 时间和事务表资源。W=0 应用 SendOneWay，发完即返回。
3. **重发时 sys 相同还是不同**：**不同**。第一次事务已超时移除，sys 可以复用但实践中应生成新 sys——因为对端可能在超时后才迟到回第一次的 reply，如果用相同 sys，新事务可能和迟到的旧 reply 错误匹配。用新 sys 保证每次事务唯一，迟到的旧 reply 会因匹配不上而被丢弃告警。
4. **收到 S9F3 后事务状态 / API 行为**：事务状态变为 **Error**。SendAndWaitReply 应该**抛异常**（如 Secs9Exception，含 S9 错误类型和原始消息信息），而不是返回 null——因为调用方需要区分"成功但 body 为空"和"对端无法处理这条消息"。返回 null 会掩盖错误。
5. **第 2 块 sys 不同时拼接器处理**：拼接器按 sys 索引收集会话，如果第 2 块的 sys 和第 1 块不同，说明这是另一条消息的块（或发送方 bug）。拼接器应为新 sys 创建新的收集会话，不影响原有会话。但如果同一逻辑消息的块 sys 不一致，那是发送方实现错误，接收方无法拼接，最终两个会话都会超时清理。
6. **哪个场景最容易在现场出问题**：**场景3（超时重发）**。因为现场网络抖动、设备繁忙、Host 处理慢都可能导致 reply 延迟，T3 超时后重发又可能和迟到的旧 reply 冲突（sys 复用问题），重发风暴还可能加重设备负担。这是现场"偶发通信异常"的最常见原因，需要仔细处理 sys 唯一性、重发间隔、重发次数上限。

{
    public byte S9Function { get; }
    public SecsItem? S9Body { get; }
    public Secs9Exception(byte f, SecsItem? body, string msg) : base(msg)
    { S9Function = f; S9Body = body; }
}

### HsmsConnection 事务 API（在 W2 基础上扩展）
```csharp
public async Task<SecsItem?> SendAndWaitReply(byte s, byte f, SecsItem? body, TimeSpan? timeout = null)
{
    var t3 = timeout ?? _txMgr.T3;
    var tx = _txMgr.Register(s, f, body);   // 内部生成 sys 并登记

    var tcs = new TaskCompletionSource<SecsItem?>();
    tx.Completed += (t, reply, s9Body) =>
    {
        switch (t.State)
        {
            case SecsTransactionState.Replied: tcs.TrySetResult(reply); break;
            case SecsTransactionState.TimedOut: tcs.TrySetException(new TimeoutException($"S{s}F{f} T3 超时 {t3.TotalSeconds}s")); break;
            case SecsTransactionState.Error: tcs.TrySetException(new Secs9Exception(9, s9Body is null ? null : SecsItem.Decode(s9Body, out _), $"S{s}F{f} 收到 S9 错误")); break;
        }
    };

    // 用 tx.SystemBytes 构造并发送（关键：发送 sys 和登记 sys 必须一致）
    var data = body?.Encode() ?? Array.Empty<byte>();
    var head = new HsmsHeader { SessionId = _sessionId, W = true, Stream = s, Function = f, SType = HsmsSType.Data, SystemBytes = tx.SystemBytes };
    var frame = FrameWriter.Build(head.Encode(data.Length).Concat(data).ToArray());
    Send(frame);

    using var cts = new CancellationTokenSource(t3);
    var completed = tcs.Task;
    var winner = await Task.WhenAny(completed, Task.Delay(Timeout.Infinite, cts.Token));
    if (winner == completed) return await completed;
    // 理论上 TransactionManager 的超时扫描会触发 TimedOut，这里是双保险
    throw new TimeoutException($"S{s}F{f} T3 超时");
}

public void SendOneWay(byte s, byte f, SecsItem? body)
{
    var sys = _txMgr.NextSys();   // 只取 sys，不登记
    var data = body?.Encode() ?? Array.Empty<byte>();
    var head = new HsmsHeader { SessionId = _sessionId, W = false, Stream = s, Function = f, SType = HsmsSType.Data, SystemBytes = sys };
    var frame = FrameWriter.Build(head.Encode(data.Length).Concat(data).ToArray());
    Send(frame);
    // 不登记事务，发完即返回
}
```

## 五、今日验收（DoD）
- SendAndWaitReply/SendOneWay 两个 API 可正常调用。
- 5 个场景全部跑通，每个场景有抓包截图、日志、事务表状态变化记录。
- 超时重发使用新 sys，不与旧事务冲突。
- S9 错误正确抛异常，不返回 null 掩盖错误。
- 多块拼接结果与原始消息一致。

## 六、易错点
1. 发送用的 sys 和登记的 sys 不一致（必须先 Register 再用 tx.SystemBytes 发）。
2. W=0 误用 SendAndWaitReply（每次都超时）。
3. 重发复用旧 sys（和迟到的旧 reply 错误匹配）。
4. S9 错误返回 null 而非抛异常（掩盖错误，业务层无法区分）。
5. 多块拼接不做超时清理（内存泄漏）。
6. TaskCompletionSource 不在超时路径上 SetException（调用方永远挂起）。
7. 超时扫描和 TCS 超时双保险没协调好（重复触发）。
