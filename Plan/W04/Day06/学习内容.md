## 三、SendAndWaitReply API 设计
```csharp
// 同步等待 reply，超时或错误抛异常
Task<SecsItem?> SendAndWaitReply(byte s, byte f, SecsItem? body, TimeSpan timeout);

// 内部流程：
// 1. 生成 sys，构造 HsmsHeader(W=1, S, F, sys)
// 2. TransactionManager.Register(s, f, body) → tx
// 3. 发送帧
// 4. 等待 tx.Completed 事件（用 TaskCompletionSource）
// 5. 结果：Replied→返回 reply body；TimedOut→抛 TimeoutException；Error→抛 Secs9Exception
```
- W=0 的消息用 `SendOneWay(s, f, body)`，不登记事务，发完即返回。
- 超时时间默认 T3=45s，可覆盖。

## 四、5 个场景的验收标准

### 场景1：正常事务
- Host 调 `SendAndWaitReply(1, 13, body, 10s)`
- 设备收到 S1F13，回 S1F14（L,2[A MDLN, A SOFTREV]）
- Host 收到 reply，返回的 SecsItem 树与设备构造的一致
- 抓包：S1F13 W=1，S1F14 W=0，SystemBytes 相同
- 事务表：发送后 PendingCount=1，收到 reply 后 PendingCount=0

### 场景2：W=0 单向通知
- 设备调 `SendOneWay(6, 11, body)`（W=0）
- Host 收到 S6F11，不回 S6F12（因为 W=0）
- 设备端：发送后 PendingCount=0（不登记）
- 抓包：只有 S6F11，没有 S6F12；S6F11 头字节2 的 W 位=0
- Host 日志：收到 S6F11 W=0，正常处理业务，不回 reply

### 场景3：超时重发
- Host 发 S2F41，设备第一次收到后**故意不回** S2F42
- Host T3 超时（测试时设为 3s），事务状态 TimedOut，PendingCount=0
- Host 业务层决定重发：第二次调 `SendAndWaitReply(2, 41, body, 10s)`（新 sys）
- 设备第二次收到后正常回 S2F42（ACKC10=0）
- Host 第二次成功返回
- 抓包：两条 S2F41（sys 不同），第一条无 reply，第二条有 S2F42

### 场景4：S9 错误
- Host 发不支持的 S20F1（W=1）
- 设备接收管线校验 Stream=20 不支持，自动回 S9F3（body 带原始头）
- Host 收到 S9F3，从 body 提取原始 sys，匹配未决事务，触发 Error 回调
- Host `SendAndWaitReply` 抛 Secs9Exception（含 S9F3 和错误类型）
- 抓包：S20F1 W=1，随后 S9F3 W=0，S9F3 body 含 S20F1 的原始头
- 事务表：发送后 PendingCount=1，收到 S9F3 后 PendingCount=0

### 场景5：多块拼接
- 设备构造一条大 S6F11（body > 单块限制，测试时人为分成 3 块）
- 设备分 3 块发送，前两块 M-bit=1（还有后续），第三块 M-bit=0（末块）
- Host BlockCollector 按 sys 收集 3 块，第三块到达后拼接成完整 body
- Host SECS-II 解码完整 body，验证与设备构造的一致
- 抓包：3 条 HSMS 帧，Stream/Function/SystemBytes 相同，M-bit 标志不同
- 拼接后总长度 = 3 块 body 长度之和
