# W04 · Day01 答案与参考

## 一、自测题标准答案
1. **编号规律 / S6F11 的 reply**：primary 的 F 为奇数，reply 的 F = primary F + 1（偶数），Stream 相同。S6F11 的 reply 是 **S6F12**。
2. **W=0 收到 reply 怎么处理**：W=0 表示发起方明确说"不需要回复"，对端不应回 reply。如果对端仍回了，本端未决事务表里没有这个 sys（因为 W=0 没登记），应按"匹配不上的 reply"处理：记日志告警、丢弃，不触发任何业务回调。这通常意味着对端实现不符合标准。
3. **为何不能只靠 S/F 配对**：同一连接上可能同时有多个相同 S/F 的事务在途（如 Host 连续发两个 S2F33 定义不同报告，或设备连续上报两个 S6F11 不同事件）。只靠 S/F 无法区分哪个 reply 对应哪个 primary。SystemBytes 是每次事务唯一的，靠它才能精确配对。
4. **primary 的几种结局**：①**成功**——收到 sys 匹配的 reply；②**超时**——T3 时间内没收到 reply；③**错误**——收到 S9 系列错误回执（对端无法处理）；④（W=0 时）**发完即结束**，不等待。
5. **T3 vs T6**：T3 管**数据消息（SECS-II primary）**等 reply 的超时，典型 45s，业务事务较长；T6 管**控制消息**（Select/Linktest/Deselect）等应答的超时，典型 5s，连接维护事务较短。两者都靠 SystemBytes 配对，但分属不同事务类型与超时表。
6. **并发事务的线程安全**：sys 生成器必须用 `Interlocked.Increment`（原子递增，不能用 ++）；未决事务表必须用 `ConcurrentDictionary`（或加锁的 Dictionary），因为发送线程登记、接收线程匹配/移除、超时扫描线程清理，三个线程并发访问。普通 Dictionary 在并发下会损坏。

## 二、参考实现（EapLab.Secs2/Transaction/）

### SecsTransactionState.cs
```csharp
namespace EapLab.Secs2.Transaction;
public enum SecsTransactionState
{
    Pending,    // 已发送，等待 reply
    Replied,    // 收到 reply
    TimedOut,   // T3 超时
    Error       // 收到 S9 错误
}
```

### SecsTransaction.cs
```csharp
using EapLab.Secs2.Items;

namespace EapLab.Secs2.Transaction;

public sealed class SecsTransaction
{
    public uint SystemBytes { get; }
    public byte Stream { get; }
    public byte Function { get; }
    public bool W { get; }
    public SecsItem? PrimaryBody { get; }
    public DateTime SentAt { get; }
    public TimeSpan Timeout { get; }
    public SecsTransactionState State { get; private set; } = SecsTransactionState.Pending;

    /// <summary>reply 到达时触发（成功/错误/超时共用，用 State 区分）</summary>
    public event Action<SecsTransaction, SecsItem?, byte[]?>? Completed;

    public SecsTransaction(uint sys, byte s, byte f, bool w, SecsItem? body, TimeSpan t3)
    {
        SystemBytes = sys; Stream = s; Function = f; W = w;
        PrimaryBody = body; SentAt = DateTime.UtcNow; Timeout = t3;
    }

    public bool IsTimedOut(DateTime now) => State == SecsTransactionState.Pending && now - SentAt > Timeout;

    public void CompleteWithReply(SecsItem? replyBody)
    {
        if (State != SecsTransactionState.Pending) return;
        State = SecsTransactionState.Replied;
        Completed?.Invoke(this, replyBody, null);
    }
    public void CompleteWithTimeout()
    {
        if (State != SecsTransactionState.Pending) return;
        State = SecsTransactionState.TimedOut;
        Completed?.Invoke(this, null, null);
    }
    public void CompleteWithError(byte[] s9Body)
    {
        if (State != SecsTransactionState.Pending) return;
        State = SecsTransactionState.Error;
        Completed?.Invoke(this, null, s9Body);
    }

    public string Key => $"S{Stream}F{Function} sys={SystemBytes:X8}";
}
```

### 事务生命周期时序（参考画法）
```
发起方                                  接收方
  │ 构造 primary(SxFy, W=1, sys=新)
  │ 登记未决事务(sys→tx)
  │── primary ────────────────────────►│ 处理业务
  │                                     │ 构造 reply(S x F+1, sys=同)
  │◄── reply ──────────────────────────│
  │ 按 sys 匹配 tx → 触发回调(成功)
  │ 移除未决事务
  │
  │ 若 T3 内无 reply：超时回调 → 移除 → 重发/上报/Spool
  │ 若收到 S9F x：错误回调 → 移除
```

## 三、今日易错点
1. 以为 reply 的 F 可以任意（必须是 primary F+1）。
2. W=0 也登记未决事务等 reply（应发完即忘）。
3. 靠 S/F 配对而忽略 SystemBytes（并发下错乱）。
4. T3 和 T6 混用（数据事务用 T3，控制事务用 T6）。
5. 未决事务表用普通 Dictionary 并发访问（必须 ConcurrentDictionary 或加锁）。
6. 超时后不从事务表移除（内存泄漏，sys 被复用后错乱）。
