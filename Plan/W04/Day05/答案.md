# W04 · Day05 答案与参考

## 一、自测题标准答案
1. **S1F1 vs S1F13**：S1F1（Are You There）是轻量级的"你在吗"探测，body 为空，设备回 S1F2 带身份信息，用于快速确认设备在线；S1F13（Establish Communications）是正式的建立通信请求，Host 带自己的 MDLN/SOFTREV，设备回 S1F14 也带身份，双方交换身份信息后进入通信状态，是 GEM 通信建立的正式流程。S1F1 可以随时发，S1F13 通常在连接建立后、正式通信前发。
2. **S2F33 vs S2F35 的关系**：S2F33（Define Report）定义"报告里包含哪些变量（VID）"，即报告的内容模板；S2F35（Link Event Report）把"事件（CEID）"和"报告（RPTID）"关联起来，即"当这个事件发生时，上报这些报告"。分两步是因为：一个报告可以被多个事件关联（复用报告模板），一个事件也可以关联多个报告（一次事件触发多份报告），解耦后更灵活。
3. **S6F11 body L,3 三个元素**：①U4 DATAID（数据收集定义 ID，标识这套报告-变量关联关系是哪次 S2F33 定义的）；②U2 CEID（集合事件 ID，标识触发本次上报的具体设备事件）；③L,n 报告列表（每个报告是 L,2[U2 RPTID, L,m 变量值]）。
4. **S5F1 ALCD 含义**：ALCD（Alarm Code）表示报警的状态/类型，常见值：1=报警设置（Alarm Set，报警发生），2=报警清除（Alarm Clear，报警恢复），0=未知/无效。ALID 是报警 ID，ALTXT 是报警文本描述。
5. **S7 用应用层分块而非 HSMS 多块**：①很多设备的 HSMS 栈不支持通用多块消息，但 S7 应用层分块是标准定义的，所有 GEM 设备都支持；②应用层分块在消息体中带块号、总块数、末块标志，业务逻辑可以逐块确认、断点续传，更灵活；③配方数据可能很大（几 MB 到几十 MB），应用层分块可以控制每块大小，避免单条 HSMS 消息超过设备缓冲区限制。
6. **设备主动发的消息 W 位**：通常 W=1。S6F11（事件上报）、S5F1（报警上报）都是设备主动发给 Host 的 primary，W=1 表示要求 Host 回 reply（S6F12/S5F2）确认收到。这样设备可以确认 Host 收到了事件/报警，如果 T3 超时没收到 reply，设备可以重发或进入 Spool（W5/W8 细讲）。W=0 的话设备发完即忘，Host 收没收到设备不知道，不可靠。
7. **ACKCx 确认码**：0=接受/成功（命令被接受、报告定义成功、关联成功等）；非 0=各种拒绝原因（如 1=命令不被接受、2=参数错误、3=设备忙、4=资源不足等，具体含义因 ACKC 类型而异）。ACKC 是设备对 Host 请求的应答，Host 根据 ACKC 判断请求是否成功。

## 二、3 条重点消息 body 构造代码

### S1F13（Establish Communications Request）
```csharp
// Host 发：L,2[A MDLN, A SOFTREV]
var s1f13 = Secs.L(Secs.A("HOST-MDLN"), Secs.A("1.0.0"));
// Encode: 20 02 40 09 48 4F 53 54 2D 4D 44 4C 4E 40 05 31 2E 30 2E 30
// 设备回 S1F14：同样 L,2[A MDLN, A SOFTREV]，带设备身份
```

### S2F41（Host Command Send）
```csharp
// Host 发：L,2[A RCMD, L,n[L,2[A CPNAME, <CPVALUE>]]]
var s2f41 = Secs.L(
    Secs.A("START"),
    Secs.L(
        Secs.L(Secs.A("LOTID"), Secs.A("LOT001")),
        Secs.L(Secs.A("RECIPE"), Secs.A("RCP_A")),
        Secs.L(Secs.A("QUANTITY"), Secs.U2(25))
    )
);
// 设备回 S2F42：L,2[U1 ACKC10, A ERRMSG?]，ACKC10=0 表示命令被接受
```

### S6F11（Event Report Send）
```csharp
// 设备发：L,3[U4 DATAID, U2 CEID, L,n[L,2[U2 RPTID, L,m[变量值...]]]]
var s6f11 = Secs.L(
    Secs.U4(1),                                    // DATAID
    Secs.U2(2001),                                 // CEID
    Secs.L(                                         // 报告列表 L,1
        Secs.L(                                     // 单个报告 L,2
            Secs.U2(1),                             // RPTID
            Secs.L(Secs.U1(100), Secs.A("RUN"), Secs.F4(1.5))  // 变量值列表
        )
    )
);
// Host 回 S6F12：U4 DATAID（确认收到哪份数据收集的报告）
```

## 三、Host↔设备典型交互时序图
```
Host(上位机)                              Equipment(设备)
  │── S1F13 建立通信(MDLN,SOFTREV) ──────►│
  │◄─ S1F14 设备身份 ─────────────────────│  进入 COMMUNICATING
  │                                          │
  │── S2F33 定义报告(RPTID=1, [VID=100,101]) ►│
  │◄─ S2F34 ACKC5=0 ──────────────────────│
  │── S2F35 关联事件(CEID=2001→RPTID=1) ──►│
  │◄─ S2F36 ACKC6=0 ──────────────────────│
  │                                          │
  │          设备事件发生(CEID=2001)         │
  │◄─ S6F11 事件上报(DATAID,CEID,报告数据) ─│
  │── S6F12 ACK(DATAID) ──────────────────►│
  │                                          │
  │── S2F41 远程命令(START, [LOTID,RECIPE]) ►│
  │◄─ S2F42 ACKC10=0 ─────────────────────│
  │                                          │
  │          设备报警(ALID=100, Set)         │
  │◄─ S5F1 报警上报(ALCD=1,ALID,ALTXT) ────│
  │── S5F2 ACK(ALID) ─────────────────────►│
```

## 四、ACKC 确认码速查（常见）
| ACKC 类型 | 0 | 非 0 常见值 |
|---|---|---|
| ACKC1 (S1F16/F18) | 接受在线/离线 | 1=拒绝，2=不支持 |
| ACKC5 (S2F34/S5F4/S7F4/F18) | 接受 | 1=拒绝，2=参数错，3=忙，4=资源不足 |
| ACKC6 (S2F36/F38) | 接受 | 1=拒绝，2=CEID 不存在，3=RPTID 不存在 |
| ACKC10 (S2F42) | 命令被接受 | 1=命令不被接受，2=参数错，3=设备忙，4=拒绝 |
> 具体值以 E30 原文及设备实现为准，核心是"0=成功，非0=各种失败原因"。

## 五、今日易错点
1. S1F1 和 S1F13 混淆（一个是探测，一个是正式建链）。
2. S2F33 和 S2F35 顺序搞反（应先定义报告，再关联事件）。
3. S6F11 body 第一层元素顺序记错（DATAID→CEID→报告列表）。
4. ALCD 值记错（1=Set，2=Clear，不是反过来）。
5. 设备主动发的 S6F11/S5F1 置 W=0（应 W=1，要求 Host 确认）。
6. ACKC 非 0 当成成功（0 才是成功）。
7. S7 配方用单条大消息不分块（应应用层分块，避免超设备缓冲）。
