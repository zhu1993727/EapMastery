## 二、背景知识（先读，15 分钟）

### 1. S5 消息处理管线集成架构
```
HSMS 接收消息 → Stream 分发
  ├─ Stream=1 → S1Handler（W5/W6 已实现）
  ├─ Stream=2 → S2Handler（S2F33/S2F35/S2F37/S2F41，W6/W5 已实现）
  ├─ Stream=5 → S5Handler（今天实现）
  │    ├─ Function=1 → S5F1 是设备主动发的，不是 Host 发的（Host 发 S5F2 确认）
  │    ├─ Function=2 → 收到 Host 的 S5F2 确认（处理超时/重发逻辑）
  │    ├─ Function=3 → S5F3Handler（使能/禁用）
  │    ├─ Function=5 → S5F5Handler（查询列表）
  │    └─ 其他 → 回 S9F5（Unknown Function）
  ├─ Stream=6 → S6Handler（S6F11 设备主动发，S6F12 Host 确认，W6 已实现）
  └─ Stream=7 → S7Handler（明天实现，配方管理）
```

### 2. 设备主动发消息的机制（S5F1/S6F11）
- S5F1 和 S6F11 是设备**主动**发给 Host 的（W=1，需要 Host 回确认）。
- 设备端需要一个"主动消息发送器"：当报警状态变化（AlarmStore.OnAlarmChanged）或事件触发（EventReportEngine.TriggerEvent）时，组装消息 body，通过 HsmsConnection 发送，等待 Host 回确认（S5F2/S6F12）。
- 超时处理：如果 Host 在 T3 时间内没回确认，设备可能重发（取决于设备实现和 Spool 配置，W8 细讲）。
- 今天实现简化版：发送后不强制等待确认（异步发送），记录日志；T3 超时重发在 W8 综合实验中完善。

### 3. S5F1 body 的两种实现
- **简化版**（今天实现）：`L,2[U4 ALID, A ALTX]`，只带报警 ID 和文本。
- **完整版**（部分设备实现）：`L,3[U4 ALID, U1 ALCD, A ALTX]`，带报警 ID、报警代码、文本。
- 今天实现简化版，ALCD 可以通过扩展加入（在 Alarm 模型中已有 ALCD，S5F1 body 可以选择是否包含）。
- Host 区分 SET/CLEAR 靠维护 ALID→状态映射表，不依赖 body 中的字段。

### 4. 报警状态变化触发 S5F1 的流程
```
1. 设备内部检测到异常（如温度超过阈值）
2. 调用 AlarmStore.Set(ALID)
3. AlarmStore 检查：报警存在？状态不是 SET？→ 状态变 SET
4. AlarmStore 检查：报警已使能？→ 触发 OnAlarmChanged 事件
5. S5F1Handler 订阅 OnAlarmChanged 事件
6. S5F1Handler 组装 S5F1 body = L,2[U4 ALID, A ALTX]
7. S5F1Handler 通过 HsmsConnection 发送 S5F1（W=1，SystemBytes 由连接分配）
8. Host 收到 S5F1，回 S5F2（U4 ALID）
9. 设备收到 S5F2，确认上报完成（清除重发定时器）
```
