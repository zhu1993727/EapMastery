# W09 · Day03 答案

## 一、自测题标准答案
1. **为什么叫元数据查询 / 查类型还是实例 / 没实例时能用吗**："元数据"是"描述数据的数据"——S14 查询的不是某个对象当前的属性值（那是实例数据，用 S15F5 查），而是"这类对象有哪些属性、方法、事件、各自什么类型"的**类型定义**，所以叫元数据查询。它查询的是 ObjectType（类型层），不是 ObjectInstance（实例层）。设备当前没有任何实例时 S14 完全能用——类型定义在设备启动时就注册在 ObjectRegistry 的 TypeRegistry 中，与实例是否存在无关。这正像 C# 反射：不 new 任何对象，也能 typeof(ProcessJob).GetProperties()。
2. **四对消息查什么 / reply 顶层结构**：
   - S14F1/F2：查**对象类型名列表**。F2 顶层=L,2[U1 ACKC, L,n[ L,3[A ObjType, U1 AttrCount, A Comment] ]]。
   - S14F3/F4：查指定类型的**属性定义**。F3=L,1[A ObjType]；F4 顶层=L,2[U1 ACKC, L,n[ L,5[A AttrId,U1 DataType,U1 AccessMode,Boolean Required,A AttrName] ]]。
   - S14F5/F6：查指定类型的**方法定义**。F5=L,1[A ObjType]；F6 顶层=L,2[U1 ACKC, L,n[ L,4[A MethodId, L,k 输入参数, L,m 输出参数, L,p 前置状态] ]]。
   - S14F7/F8：查指定类型的**事件定义**。F7=L,1[A ObjType]；F8 顶层=L,2[U1 ACKC, L,n[ L,4[U4 CEID, A EventName, L,q 快照属性, A TriggerState] ]]。
   - 共同规律：所有 reply 都是 L,2[ACKC, 列表]，ACKC=0 成功，列表元素是同构的定义子 List。
3. **首次连接类型发现顺序 / 为什么先发现再操作**：顺序：①GEM 基础建链（HSMS Select→S1F13→S1F17 在线）；②S14F1 拿全部类型名列表；③对每个类型依次 S14F3 拿属性、S14F5 拿方法、S14F7 拿事件；④Host 在本地构建"类型→属性/方法/事件"模型缓存；⑤之后才能用 S15 创建/操作实例、用缓存解析 S16 事件。原因：S15/S16 消息体里只有 ATTRID/METHODID/CEID 这些标识，Host 必须先知道每个标识对应的数据类型、访问模式、参数定义、语义，才能正确编码 S15 请求（比如设置 LotID 要知道它是 A 类型、必填）和解析 S15 reply / S16 事件（比如 CEID=4101 要知道它是 ProcessJob.Started、快照里有哪些属性）。没有类型发现，Host 拿到一堆 ID 无法解释。
4. **AccessMode 三个值 / Required=true 的含义**：AccessMode：0=ReadOnly（只读，Host 只能 S15F5 查询，不能 S15F7 设置，对应设备内部决定的状态量如 ProcessState）；1=ReadWrite（读写，Host 可在允许状态下设置，对应配置量如 LotID/Priority）；2=WriteOnly（只写，少见，如某些触发型控制字段）。Required=true 表示**创建对象实例（S15F1）时必须提供该属性的初始值**，缺失则设备拒绝创建并回错误；Required=false 的属性创建时可省略，设备用 DefaultValue 填充默认值。
5. **RequiredStates 的作用 / Host 拿到有什么用**：RequiredStates 是方法定义中声明的"允许调用该方法的对象状态集合"（如 Start 只允许 QUEUED/PAUSED）。设备端用它做服务端校验（错误状态调用拒绝）。Host 拿到它的用途：①**客户端预判**——Host 界面/调度逻辑在调用方法前先判断对象当前状态是否在允许集合内，避免发了必被拒绝的无效请求，减少通信往返；②**状态机建模**——Host 用"方法+允许状态+事件触发状态"重建对象状态机模型，知道 Start 后对象会转到 EXECUTING、什么状态能 Abort；③**操作使能**——Host UI 根据状态灰化/点亮操作按钮（EXECUTING 时 Start 按钮灰、Abort 按钮亮）。
6. **类型发现要不要缓存 / SOFTREV 升级为什么重新发现**：要缓存。同一型号设备的对象类型定义是静态的，Host 为每台设备（或每个设备型号）缓存一份类型模型即可，不必每次连接都全量 S14 查询，减少建链时间和通信量；实例数据（S15F5）每次实时查，但类型定义（S14）走缓存。设备 SOFTREV（软件版本，S1F13/F14 交换）升级后，厂商可能新增/删除/修改了对象类型、属性、方法、事件（如新增属性、改了数据类型、CEID 重新编号），旧缓存与新设备不匹配会导致解析错误或操作失败，因此 Host 检测到 SOFTREV 变化时必须使缓存失效、重新执行完整 S14 类型发现。
7. **查询不存在的类型怎么回**：设备不崩溃、不断连。S14F4/F6/F8 回 ACKC 非 0（表示请求的类型不存在），列表为空 List（L,0），可在附加字段中带错误描述（如 "Unknown ObjType: xxx"，具体以设备实现为准）。Host 收到后记录日志、检查自己请求的类型名是否拼写错误或设备是否支持该 GEM300 标准。原则：对端请求的资源不存在是正常业务情况，用业务错误码回答，不是协议异常。

## 四、用 Day02 的模型构造 S14F4 reply 的代码片段（Day04 完整实现的预览）
```csharp
// 从 ObjectType 生成 S14F4 body
public static SecsItem BuildAttrsReply(ObjectType type)
{
    var attrItems = new List<SecsItem>();
    foreach (var a in type.Attributes)
    {
        attrItems.Add(SecsItem.L(
            SecsItem.A(a.AttrId),
            SecsItem.U1((byte)a.DataType),       // 类型码映射，实际应用字典转换
            SecsItem.U1((byte)a.Access),
            SecsItem.Boolean(a.Required),
            SecsItem.A(a.Name)
        ));
    }
    return SecsItem.L(SecsItem.U1(0), SecsItem.L(attrItems.ToArray()));
}
```

## 五、今日易错点
1. 混淆 S14（查类型定义）和 S15F5（查实例属性值）——S14 是元数据，S15F5 是运行时数据。
2. reply 顶层结构漏掉 ACKC（所有 S14 reply 都是 L,2[ACKC, 列表]）。
3. CEID 类型用错（事件 ID 用 U4，属性/方法 ID 用 A 字符串，注意区分）。
4. AccessMode/Required 含义混淆（AccessMode 是读写权限，Required 是创建时是否必填）。
5. 以为没实例就不能 S14 查询（类型定义独立于实例存在，随时可查）。
6. 查询不存在类型时抛异常断连（应回 ACKC 非 0 + 空列表，正常业务错误）。
7. Host 不缓存类型模型，每次操作前都全量 S14（应缓存，SOFTREV 变化才重新发现）。
8. 忽略 RequiredStates，Host 在错误状态盲目发方法调用（应客户端预判，减少无效请求）。
9. 手算 Item 树时 List 子项个数写错（L,n 的 n 必须等于实际子项数，List 长度是子项个数不是字节数）。
