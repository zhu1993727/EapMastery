# W09 · Day05 答案

## 一、自测题标准答案
1. **S15 六个操作及 Function 号**：
   - 创建对象：S15F1（请求）/S15F2（回复）
   - 删除对象：S15F3/F4
   - 查询属性值：S15F5/F6
   - 设置属性值：S15F7/F8
   - 调用方法：S15F9/F10
   - 存在性查询（批量）：S15F11/F12
   规律：奇数 F 是 Host→设备 primary，偶数 F 是设备→Host reply，全部 W=1。所有操作都携带或返回 OBJSPEC。

2. **S15F1 创建对象的校验和顺序**：①对象类型存在（ObjType 在 TypeRegistry 注册，否则 ACKC=1）；②ObjectID 合法（非空、字符集/长度合规）；③OBJSPEC 不重复（同 Type:ID 不存在，否则 ACKC=3）；④初始属性中的 ATTRID 都在类型定义中（未知属性 ACKC=4）；⑤必填属性齐全（Required=true 且无默认值的必须提供，否则 ACKC=6）；⑥每个初始值类型与 AttributeDefinition.DataType 匹配（否则 ACKC=7）；⑦ReadOnly 属性允许创建时给初值；⑧该类型实例数未超上限；⑨业务前置条件（如依赖对象已存在）。顺序原则：先校验"能不能找到类型和对象"（存在性），再校验"内容对不对"（属性/类型/必填），最后校验"业务允不允许"（上限/前置），这样错误码最精确、排查最快。

3. **S15F5 请求 AttrId 顺序与返回列表顺序的关系**：**一一对应、同序返回**。请求 L,n 里第 i 个 AttrId，返回 L,n 里第 i 项就是它的值，Host 直接按下标匹配，不依赖返回项里是否重复带 AttrId。这样设计的好处：①Host 不必做名称查找，O(n) 顺序读取性能高；②即使两个同名（理论上不会）也能靠位置区分；③编码紧凑。设备端实现时必须严格按请求顺序组装返回，不能用字典枚举打乱顺序（字典无序），应当遍历请求 AttrId 列表逐个取值。请求空列表表示查全部属性，此时返回顺序按类型定义中属性的注册顺序。

4. **批量设置推荐整批原子还是部分成功 / 为什么**：**推荐整批原子（all-or-nothing）**——先对整批属性做完所有校验（存在性、只读、状态、类型），全部通过才一次性写入，任一不合法则整批拒绝、对象状态完全不变，回第一个错误码。原因：①对象属性之间常有耦合（如设置工艺窗口要同时改上限和下限，只改一个会产生非法组合），部分成功会让对象进入半更新的不一致状态；②Host 难以从"部分成功"的结果中恢复（哪些改了哪些没改需要逐项核对、补偿）；③原子语义清晰、可重放（失败后修正参数整批重试即可，结果确定）。部分成功只在属性彼此完全独立、且 Host 明确需要"尽力而为"的场景用，且必须在 reply 中逐项返回成功/失败标志。GEM300 工艺对象（Job/Carrier）建议一律原子。

5. **为什么 S15F10 ACKC=0 不代表方法完成 / Host 怎么知道完成**：S15F10 是方法**请求的同步应答**，ACKC=0 只表示"请求格式合法、对象存在、方法存在、当前状态允许调用、方法已被设备接受（排队或开始执行）"，这一刻方法的业务逻辑可能刚开始甚至还在排队，尚未完成。方法执行通常需要时间（如 ProcessJob.Start 后要加工几分钟到几小时），不可能在 SECS 消息的同步应答窗口（T3 约 45 秒）内完成。Host 知道真正完成靠**对象事件 S16F1**：方法驱动对象状态机转换，每次转换触发对应事件（Start→QUEUED/PAUSED→EXECUTING 触发 Started；加工结束→COMPLETED 触发 Completed；异常→ABORTED 触发 Aborted），Host 收到终态事件（Completed/Aborted）才知道方法对应的业务流程结束。这和 GEM 的"S2F42 ACKC10=0 只接受、完成靠 S6F11"是完全一致的异步设计。

6. **EXECUTING 的 ProcessJob 能直接 S15F3 删除吗 / 应该怎么做**：不能直接删。EXECUTING 表示 Job 正在加工，直接删除会导致：设备内部加工任务失去对象记录、正在执行的工艺无人管理、Host 状态与设备不一致、可能产生孤儿工艺和硬件风险。正确流程：①先调用 Abort 方法（S15F9 METHODID=Abort，当前状态 EXECUTING 在 Abort 的 RequiredStates 内）安全中止工艺（停气体/停射频/腔体回安全态）；②状态机转到 ABORTED（终态），触发 S16F1 Aborted 事件通知 Host；③确认对象处于终态（ABORTED/COMPLETED）后，再 S15F3 删除。删除方法的业务校验就是"只允许在终态删除"，EXECUTING 时删除请求回 ACKC=8（状态非法）。

7. **S15F11/F12 存在性查询的典型场景**：①**重连状态同步**——Host 与设备断连期间，设备端对象可能被操作员删除或因工艺结束被清理，Host 重连后用 S15F11 批量查询自己缓存的所有 OBJSPEC 是否还存在，清理本地失效对象，避免对已删除对象发操作（会反复收到 ACKC=2）；②**批量操作前校验**——Host 准备对一批 Job/Carrier 操作前，先批量确认它们都存在；③**模型对账**——周期性比对 Host 对象缓存和设备实际对象集合（配合 S15 列举实例能力），发现漂移。相比逐个 S15F5 查询，S15F11 一次请求批量返回，通信开销小。

8. **对 ReadOnly 属性发 S15F7 会怎样 / 错误码**：设备在设置校验的 AccessMode 检查环节拒绝该操作——找到属性定义后发现 Access=ReadOnly，不写入、对象状态不变，S15F8 回 ACKC=5（只读属性拒绝写），并记录日志（OBJSPEC、ATTRID、当前值、试图写入的值）。如果是整批原子设置，其中含一个只读属性，则整批拒绝、其他合法属性也不写入。原因：只读属性（如 ProcessState、StartTime、WaferCount）是设备内部真实状态，只能由设备内部状态机/工艺逻辑改变，Host 直接改写会破坏"设备是状态权威来源"原则。

## 三、方法调用异步时序图（手绘参考）
```
Host(EAP)                    ObjectInstance(PJ001)              设备工艺执行器
   │                                │                                  │
   │── S15F9 Start ────────────────►│                                  │
   │                                │ 校验:对象/方法存在?               │
   │                                │ 状态 QUEUED∈RequiredStates?      │
   │                                │ 接受, 投递执行 ──────────────────►│
   │◄─ S15F10 ACKC=0(已接受) ───────│                                  │
   │                                │                                  │ 开始加工
   │                                │◄──────── 状态 QUEUED→EXECUTING ──│
   │                                │ 触发 Started 事件                 │
   │◄─ S16F1[CEID=4101 Started] ────│                                  │
   │── S16F2 ACK ──────────────────►│                                  │
   │                                │                                  │ 加工中(分钟~小时)
   │                                │◄──────── 状态 EXECUTING→COMPLETED │
   │                                │ 触发 Completed 事件               │
   │◄─ S16F1[CEID=4102 Completed] ──│                                  │
   │── S16F2 ACK ──────────────────►│                                  │
   │                                │                                  │
   │  此刻 Host 才知道方法业务完成   │                                  │
```
要点：S15F10 是"收到"的同步回执（毫秒级），S16F1 终态事件才是"做完"的异步通知（可能数小时后），两者之间是工艺执行时间。

## 四、S15 校验顺序速查（设备端处理流水线）
```
收到 S15 请求
 → 解析 body 格式（格式错→对应请求错误码）
 → 定位对象类型/实例（类型不存在→1；实例不存在→2；重复创建→3）
 → 定位成员（属性不存在→4；方法不存在→9）
 → 权限校验（只读写→5）
 → 必填校验（创建缺必填→6；调用缺参数→10）
 → 类型校验（类型不匹配→7）
 → 状态机校验（当前状态不允许→8）
 → 执行业务（创建/删除/读写/调用）
 → 组装 reply（成功 ACKC=0 + 数据）
```

## 五、今日易错点
1. 把 S15F10 ACKC=0 当成方法执行完成（只是接受，完成靠 S16F1 终态事件）。
2. S15F5 返回列表不按请求顺序（必须同序，遍历请求列表逐个取值，不能用无序字典枚举）。
3. 批量设置用部分成功导致对象半更新（工艺对象推荐整批原子）。
4. EXECUTING 中直接删除对象（必须先 Abort 到终态再删）。
5. OBJSPEC 只传 ID 不传 Type（标准是 "Type:ID"）。
6. ReadOnly 属性允许 S15F7 写入（应回 ACKC=5，只读状态只能设备内部改）。
7. 创建对象时不校验必填属性和类型（残缺对象后续操作必出问题，创建时就要拦住）。
8. 错误码混用（要建立统一 ACKC 表，设备和 Host 一致，排查时一眼定位是哪类问题）。
9. S15F11 逐个对象查（它是批量接口，一次传 OBJSPEC 列表，减少往返）。
10. 忽略"空列表查全部属性"的约定（S15F5 空 AttrId 列表=查全部，返回按类型注册顺序）。
