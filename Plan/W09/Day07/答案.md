# W09 · Day07 答案

## 一、W9 自测题（10 题）标准答案

### 1. GEM 和 OSS 的关系 / GEM300 为什么基于 OSS
GEM（E30）提供基础通信地基——HSMS 连接、通信/控制状态机、数据采集、报警、远程命令、Spool；OSS（E39）在地基上提供对象级抽象层，把设备内部实体建模为"类型→实例→属性/方法/事件"，用 S14 查类型、S15 操作实例、S16 上报对象事件。OSS 不替代 GEM，而是扩展它。GEM300 标准（E40 ProcessJob、E87 Carrier、E90 Substrate、E94 ControlJob）基于 OSS 的原因：它们管理的都是"多实例、有生命周期、有状态机、彼此有层级关系"的对象（多个 Job、多个 FOUP、多片 Wafer），GEM 扁平 ID 模型无法优雅表达，而 OSS 的类型/实例/OBJSPEC/对象树天然支持多实例和生命周期，且所有标准复用同一套 S14/S15/S16 接口，学习和实现成本低、跨厂商一致性好。

### 2. OSS 两层模型
- **元数据层（类型层，静态）**：ObjectType + AttributeDefinition/MethodDefinition/EventDefinition，描述"这类对象长什么样"，设备启动注册一次、运行期基本不变，**S14 查询这一层**（相当于反射查 Type/PropertyInfo/MethodInfo/EventInfo）。
- **实例层（动态）**：ObjectInstance，持有 OBJSPEC、当前属性值、状态机，运行期动态创建/删除，**S15 操作、S16 上报这一层**（相当于 new 出来的对象）。
- ObjectRegistry 分两个字典管理：TypeRegistry（类型名→ObjectType）和 InstanceStore（OBJSPEC→ObjectInstance）。分层的意义：无实例也能查类型定义；类型定义全局一份不重复存储；实例只存运行期数据，结构清晰。

### 3. OBJSPEC 格式和作用
格式 "Type:ID"（如 ProcessJob:PJ001），层级对象用路径 "ControlJob:CJ001/ProcessJob:PJ001"（W10 详解）。作用：唯一标识对象实例。S15 中 Host 用 OBJSPEC 指定操作目标（创建时由 Type+ID 拼成，删除/查询/设置/调方法都带 OBJSPEC 定位实例）；S16 中设备上报事件带 OBJSPEC，告诉 Host 是哪个实例触发的。没有 OBJSPEC 就无法区分同类型的多个实例。

### 4. S14 四对消息及 reply 顶层结构
- S14F1/F2 类型列表：F2=L,2[U1 ACKC, L,n[L,3[A TypeName,U1 AttrCount,A Comment]]]
- S14F3/F4 属性定义：F3=L,1[A TypeName]；F4=L,2[U1 ACKC, L,n[L,5[A AttrId,U1 DataType,U1 AccessMode,Boolean Required,A Name]]]
- S14F5/F6 方法定义：F5=L,1[A TypeName]；F6=L,2[U1 ACKC, L,n[L,4[A MethodId,L,k 输入参数,L,m 输出参数,L,p 允许状态]]]
- S14F7/F8 事件定义：F7=L,1[A TypeName]；F8=L,2[U1 ACKC, L,n[L,4[U4 CEID,A Name,L,q 快照属性,A TriggerState]]]
- 共同规律：reply 都是 L,2[ACKC, 同构定义列表]，空集合回 L,0。

### 5. 首次连接类型发现顺序 / SOFTREV 变化为何重新发现
顺序：GEM 建链（Select→S1F13→S1F17）→S14F1 拿类型名列表→对每个类型 S14F3 属性、S14F5 方法、S14F7 事件→Host 本地构建类型模型缓存→之后 S15 操作/S16 解析都用缓存。SOFTREV（设备软件版本，S1F13/F14 交换）升级后，厂商可能增删改对象类型、属性、方法、事件（新增字段、改数据类型、CEID 重编号），旧缓存与新设备不匹配会导致编码/解析错误或操作非法，因此检测到 SOFTREV 变化必须让缓存失效、重新完整发现。

### 6. S15F1 创建对象校验链（按顺序）
①类型存在（不存在→ACKC=1）；②ObjectID 合法（非空、符合字符集/长度）；③OBJSPEC 不重复（重复→3）；④初始属性的 ATTRID 都已定义（未知属性→4）；⑤必填属性齐全且无默认值的必须提供（缺→6）；⑥每个初始值类型匹配（不匹配→7）；⑦ReadOnly 属性允许创建时给初值；⑧实例数未超类型上限；⑨业务前置（依赖对象存在等）。原则：先存在性、再内容合法性、最后业务允许，错误码最精确。

### 7. S15F7 两阶段原子设置
阶段一"校验"（不写入）：遍历整批，检查属性存在、非只读、状态允许写、类型匹配，任一失败立即回错误码且不做任何修改；阶段二"提交"：全部通过后循环 SetAttribute 真正写入。校验阶段不能写入，是为了避免"前几个已写、后面校验失败"导致半更新不一致（属性间常有耦合，部分更新会产生非法组合），先全量校验后统一提交天然实现 all-or-nothing，无需回滚。

### 8. S15F9/F10 与 S16F1 的异步关系
S15F9 是 Host 调方法请求；S15F10 是设备**同步应答**，在"对象/方法存在、状态允许、参数合法、请求被接受"后立即（毫秒级）返回，ACKC=0 只代表**接受执行**，不代表执行完成；方法执行驱动对象状态机转换，每次转换触发事件，ObjectEventService 发 **S16F1**（Start→转 EXECUTING 发 Started；工艺结束→转 COMPLETED 发 Completed；异常→ABORTED 发 Aborted）。Host 判断方法业务真正完成，必须等 S16F1 的终态事件（Completed/Aborted），而不是看 F10。这与 GEM"S2F42 只接受、完成靠 S6F11"是同一异步思想。

### 9. ObjectEventService 订阅时机 / 泄漏与幽灵事件
订阅：实例创建成功后（S15F1 成功路径或设备内部创建处）Subscribe，挂 instance.EventRaised；取消：实例删除前/时 Unsubscribe，用 -= 精确摘除委托（需保存委托引用）。不取消的后果：①内存泄漏——事件委托持有实例引用，对象从 Registry 删除后 GC 仍无法回收，长期运行内存持续增长；②幽灵事件——已删除对象若内部仍触发状态变化，残留订阅会把事件发给 Host，Host 收到不存在对象的 S16F1，状态错乱。

### 10. S15 ACKC 错误码 1-10
0 成功；1 对象类型不存在；2 对象实例不存在；3 对象已存在；4 属性不存在；5 只读属性拒绝写；6 缺少必填属性；7 数据类型不匹配；8 状态非法（当前对象状态不允许该操作）；9 方法不存在；10 参数错误（缺必填参数/参数非法）；99 内部错误。

## 四、W10 预热补充：对象树与事件订阅要点
1. **对象树关系**：ControlJob 1—N ProcessJob，ProcessJob 1—N Substrate，Carrier 1—N Substrate（槽位）。父对象状态由子对象聚合（E94 级联状态机核心，W21 详解），删除父对象前要先处理子对象。
2. **嵌套 OBJSPEC**：路径式表达父子归属，解析时从左到右逐级定位，每级都要校验存在性和类型。
3. **事件订阅两种策略**：设备全发 Host 过滤（设备实现简单、网络流量大）vs Host 订阅设备过滤（省带宽、设备要维护订阅表）；重连后订阅关系和 S2F35 一样要重建（易失）。
4. **OSS 与 GEM 数据双通**：同一工艺状态既可以作为 GEM SV 通过 S6F11 上报（兼容老 Host），也可以作为 OSS 属性通过 S16F1 上报（新接口），内部应是同一份状态源、两个出口，避免双份状态不一致。

## 五、今日易错点（W9 全周高频错误汇总）
1. 混淆类型层和实例层、S14 和 S15F5。
2. OBJSPEC 漏 Type 只写 ID。
3. S15F10 当完成信号（完成靠 S16F1 终态事件）。
4. S15F5 返回不按请求顺序（字典无序，必须按请求列表）。
5. S15F7 边校验边写（两阶段原子）。
6. ReadOnly 属性被 Host 写入（ACKC=5 拒绝）。
7. 执行中对象直接删除（先 Abort 到终态）。
8. 创建后不订阅、删除后不取消（内存泄漏+幽灵事件）。
9. S16F1 不走 Spool（断连丢事件）。
10. 错误码靠异常文本匹配（应结构化错误码）。
11. 类型模型不缓存或 SOFTREV 变了不重新发现。
12. 状态转换绕过 TransitionTo 直接改字段（事件不触发、非法边不拦截）。
