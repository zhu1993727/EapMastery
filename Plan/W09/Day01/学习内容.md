## 二、背景知识（先读，30 分钟）

### 1. 为什么需要 OSS？GEM 的局限性

回顾 E30 GEM 的通信方式：
- Host 发 **S2F41 远程命令**（如 START，带 LOTID/RECIPE 参数）→ 设备回 S2F42（ACKC10=0 接受）→ 设备异步执行 → 完成时发 **S6F11 事件**通知。
- Host 发 **S1F3** 查询设备有哪些状态变量（SV）→ 设备回 S1F4 列表。
- Host 发 **S2F33** 定义报告（选哪些 SV）→ **S2F35** 关联事件 → 事件触发时 **S6F11** 上报。

GEM 的问题：
1. **扁平、无结构**：所有变量、事件、命令都是扁平的 ID（VID/CEID/RCMD），Host 不知道它们属于哪个实体。比如"温度=100"是哪个腔体的温度？"LotStart=3001"是哪个 Lot 的开始？GEM 无法表达。
2. **多实例困难**：设备有多个腔体、多个 FOUP、多个 Job 时，GEM 只能用不同的 VID/CEID 区分（如腔体1温度=100、腔体2温度=200），ID 空间爆炸，Host 配置复杂。
3. **生命周期不可见**：Host 不知道设备内部有哪些 Job、每个 Job 处于什么状态、什么时候创建/删除。GEM 只能通过事件间接推断。
4. **扩展性差**：新增一种设备实体（如双腔体设备的 Chamber），需要新增一整套 VID/CEID/RCMD，没有统一的操作接口。

OSS 的解决方案：
- 把设备内部实体建模为**对象**（Object），每个对象有**属性**（Attribute，如状态、配方）、**方法**（Method，如 Start、Abort）、**事件**（Event，如 Started、Completed）。
- Host 通过 **S14** 查询设备支持哪些对象类型、每种类型有哪些属性/方法/事件（类似反射）。
- Host 通过 **S15** 对具体对象实例进行操作（创建、删除、查询属性、设置属性、调用方法）。
- 设备通过 **S16** 通知 Host 对象状态变化事件。
- 这样，多实例、生命周期、结构化、扩展性问题都解决了。

### 2. OSS 的 6 个核心概念

#### 概念1：Object Type（对象类型）
- 定义：一类对象的模板，类似面向对象编程中的 **Class（类）**。
- 作用：定义该类型对象有哪些属性（Attribute）、方法（Method）、事件（Event）。
- 示例："ProcessJob"、"ControlJob"、"Carrier"、"Substrate"、"Chamber"、"Recipe"、"Alarm"。
- 每种 Object Type 有唯一的类型名（如 "ProcessJob"），Host 通过 S14 查询设备支持哪些类型。

#### 概念2：Object Instance（对象实例）
- 定义：对象类型的具体实例，类似面向对象编程中的 **Object（对象）**。
- 作用：代表设备内部的一个具体实体。
- 示例：设备同时有 3 个 ProcessJob 实例（PJ001、PJ002、PJ003），2 个 Carrier 实例（FOUP_A、FOUP_B）。
- 每个实例有唯一的 **OBJSPEC**（对象说明符），格式为 "Type:ID"，如 "ProcessJob:PJ001"、"Carrier:FOUP_A"。
- 实例有生命周期：创建（S15F1）→ 存在（可操作）→ 删除（S15F3）。

#### 概念3：Attribute（属性）
- 定义：对象的状态变量，类似类的 **Field/Property（字段/属性）**。
- 作用：描述对象的当前状态。
- 示例：ProcessJob 的属性：Status（状态）、Recipe（配方）、LotID（批次号）、Quantity（数量）、StartTime（开始时间）。
- 每个属性有 ATTRID（属性 ID）和数据类型（A/B/I/U/F/List 等 SECS-II 类型）。
- Host 通过 S15F5/F6 查询属性值，通过 S15F7/F8 设置属性值（部分属性只读）。
- 与 GEM 的 SV（状态变量）对比：SV 是设备级的扁平变量，Attribute 是对象级的结构化变量，属于某个对象实例。

#### 概念4：Method（方法）
- 定义：对象可以执行的操作，类似类的 **Method（方法）**。
- 作用：让对象执行某个动作。
- 示例：ProcessJob 的方法：Start（开始）、Abort（中止）、Pause（暂停）、Resume（恢复）。
- 每个方法有 METHODID（方法 ID）、输入参数列表、输出参数列表。
- Host 通过 S15F9/F10 调用对象方法，传入参数，设备执行后回结果。
- 与 GEM 的 RCMD（远程命令）对比：RCMD 是设备级的扁平命令，Method 是对象级的结构化操作，属于某个对象实例。调用 ProcessJob:PJ001.Start() 和直接发 START 命令的区别是：前者明确指定对哪个 Job 操作，后者设备自己决定对哪个 Job 操作（通常是当前 Job）。

#### 概念5：Event（事件）
- 定义：对象状态变化时触发的通知，类似类的 **Event（事件）**。
- 作用：通知 Host 对象发生了什么变化。
- 示例：ProcessJob 的事件：Started（已开始）、Completed（已完成）、Aborted（已中止）、Paused（已暂停）。
- 每个事件有 CEID（事件 ID）和关联的报告（Report，包含事件发生时的属性值快照）。
- 设备通过 S16F1/F2 上报对象事件，Host 回 S16F2 确认。
- 与 GEM 的 CEID（收集事件）对比：GEM 的事件是设备级的，OSS 的事件是对象级的，属于某个对象实例。S16F1 中会携带 OBJSPEC，明确是哪个对象触发的事件。

#### 概念6：OBJSPEC（对象说明符）
- 定义：对象实例的唯一标识，格式为 "Type:ID"（或更复杂的嵌套格式）。
- 作用：Host 通过 OBJSPEC 指定要操作哪个对象实例。
- 示例："ProcessJob:PJ001"、"Carrier:FOUP_A"、"Substrate:WAFER_001"。
- OBJSPEC 在 S15（实例操作）和 S16（事件通知）中都使用：
  - S15F1 创建对象时，Host 提供 OBJSPEC（或设备自动分配）。
  - S15F3 删除对象、S15F5 查询属性、S15F7 设置属性、S15F9 调用方法时，Host 提供 OBJSPEC 指定目标对象。
  - S16F1 事件上报时，设备携带 OBJSPEC，告诉 Host 是哪个对象触发的事件。
- OBJSPEC 是 OSS 的核心——没有 OBJSPEC，就无法区分同类型的不同实例。

### 3. OSS 的 3 个消息族

#### S14：对象类型查询（Object Type Query）
- 作用：Host 查询设备支持哪些对象类型，每种类型有哪些属性/方法/事件。类似面向对象的**反射（Reflection）**。
- 典型消息：
  - S14F1/F2：查询对象类型列表（设备支持哪些类型）
  - S14F3/F4：查询指定类型的属性列表（有哪些 Attribute，ATTRID 和类型）
  - S14F5/F6：查询指定类型的方法列表（有哪些 Method，METHODID 和参数）
  - S14F7/F8：查询指定类型的事件列表（有哪些 Event，CEID 和关联报告）
- 特点：S14 是"元数据查询"——查询的是类型定义，不是具体实例的数据。Host 在首次连接设备时，通过 S14 了解设备的对象模型，然后才能进行 S15 操作。

#### S15：对象实例操作（Object Instance Operation）
- 作用：Host 对具体对象实例进行操作（创建、删除、查询、设置、调用方法）。
- 典型消息：
  - S15F1/F2：创建对象（Create Object）——Host 提供 OBJSPEC 和初始属性值，设备创建实例
  - S15F3/F4：删除对象（Delete Object）——Host 提供 OBJSPEC，设备删除实例
  - S15F5/F6：查询属性值（Get Attribute Value）——Host 提供 OBJSPEC 和 ATTRID 列表，设备回属性值
  - S15F7/F8：设置属性值（Set Attribute Value）——Host 提供 OBJSPEC 和属性值，设备设置
  - S15F9/F10：调用方法（Invoke Method）——Host 提供 OBJSPEC、METHODID 和参数，设备执行后回结果
  - S15F11/F12：查询对象存在性（Object Existence）——Host 提供 OBJSPEC，设备回对象是否存在
- 特点：S15 是"实例操作"——针对具体对象实例，所有消息都携带 OBJSPEC。

#### S16：对象事件通知（Object Event Notification）
- 作用：设备向 Host 通知对象状态变化事件。类似 GEM 的 S6F11，但针对对象。
- 典型消息：
  - S16F1/F2：对象事件上报（Object Event Report）——设备携带 OBJSPEC、CEID、报告数据（属性值快照），Host 回 S16F2 确认
  - S16F3/F4：事件确认/订阅管理（部分实现）
- 特点：S16 是"设备主动上报"——对象状态变化时，设备主动发 S16F1 给 Host，不需要 Host 轮询。S16F1 中携带 OBJSPEC，明确是哪个对象的事件。

### 4. OSS 与 GEM 的关系（关键！不要混淆）

| 维度 | GEM（E30） | OSS（E39） |
|---|---|---|
| 抽象级别 | 消息级（Message-level） | 对象级（Object-level） |
| 核心概念 | SV/CEID/RCMD/Report | Object Type/Instance/Attribute/Method/Event |
| 标识 | 扁平 ID（VID/CEID/RCMD） | OBJSPEC（Type:ID）+ ATTRID/METHODID/CEID |
| 多实例 | 困难（用不同 ID 区分） | 原生支持（同类型多个实例，OBJSPEC 区分） |
| 生命周期 | 不可见（通过事件推断） | 可见（创建/删除/状态查询） |
| 类型查询 | S1F3/F5/F7（扁平列表） | S14（结构化类型定义） |
| 实例操作 | S2F41（远程命令，设备级） | S15（对象操作，实例级） |
| 事件通知 | S6F11（设备级事件） | S16F1（对象级事件，带 OBJSPEC） |
| 关系 | 基础（提供通信/状态/数据采集） | 扩展（在 GEM 之上提供对象抽象） |

**关键结论**：
1. OSS **不是替代** GEM，而是**扩展** GEM。GEM 提供基础通信（连接/建链/状态/数据采集/报警/Spool），OSS 在 GEM 之上提供对象级抽象。
2. GEM300 标准（E40 ProcessJob、E87 Carrier、E90 Substrate、E94 ControlJob）都**基于 OSS**——它们定义了特定的对象类型和这些对象的属性/方法/事件。
3. 学习路径：GEM（W2-W8）→ OSS（W9-W10）→ GEM300 基于 OSS 的标准（E40/E87/E90/E94，W11-W23）。
4. 设备可以同时支持 GEM 和 OSS——Host 可以用 GEM 消息（S2F41/S6F11）也可以用 OSS 消息（S15/S16），但通常 GEM300 设备以 OSS 为主，GEM 用于基础通信和兼容老系统。
