# W28 · Day03 答案与参考实现

## 一、自测题标准答案
1. **为何不能每计划一线程/集中调度**：每计划一个 Timer/线程，在多客户端×多计划×高频下会产生大量线程与定时器，引发频繁上下文切换、锁竞争、线程唤醒抖动，CPU 随订阅数线性膨胀，最坏拖垮设备。集中调度用一个基础节拍循环（如 10ms）运行，把计划按采样周期换算成"每几个 tick 采一次"（100Hz 每 tick、50Hz 每 2 tick、10Hz 每 10 tick），一次 tick 内遍历到期计划统一采样；多个客户端订同一变量时这一 tick 只读一次值、打同一时间戳再分发给各计划。线程数恒定、与订阅数无关、同源同戳、节拍可预测。
2. **单调时钟/跨系统对齐**：节拍与时间间隔必须用单调时钟（只增不减，如 Stopwatch/高精度计时器），因为墙上时钟会被 NTP 校时/手动改时回拨或跳变，导致采样间隔为负、波形时间轴错乱、环形缓冲时序混乱（W24 EPT 同原则）。做法是内部节拍、间隔、缓冲排序全用单调时间；同时在数据包里附 UTC 墙上时间戳供与 MES/FDC/历史库等跨系统对齐，即"内部单调保真、对外 UTC 对齐"，两者可建立映射。
3. **环形缓冲优势**：固定容量数组+读写指针，入队/出队 O(1)、写满按策略覆盖最旧、绝不动态扩容，因此内存严格有界、无扩容抖动、几乎无 GC 分配，适合定速高频写入。普通 Queue/List 会随数据增长不断分配/扩容（内存无界、GC 压力大），List 还涉及搬移；在高频实时流里无界增长会内存失控，频繁扩容造成延迟尖峰。环形缓冲用固定空间承载持续流，是实时通道的标准结构。
4. **trace 覆盖 vs 事件不可覆盖**：周期 trace 是连续时间序列，实时性优先、消费者慢时宁可丢最旧点保最新波形并标 Gap，因此环形缓冲可覆盖最旧；事件(ECV)/异常(EXV)快照是离散但业务关键的节点证据（Step 切换、报警现场），每一条都不可替代、不能被后续周期点覆盖丢失，否则 FDC 无法定位工艺节点/故障，因此用独立不覆盖队列（满则阻塞/单独扩容策略或上报失败重试），与周期 trace 分通道对待。
5. **低 GC 手段**：①采样点用 readonly struct 值类型，避免 class 堆分配与装箱；②缓冲数组用 ArrayPool<T>.Shared.Rent/Return 复用，批量写入而不是每点 new 数组/List；③热路径不拼字符串、不 ToString 装箱、不用 LINQ/闭包/lambda 捕获（这些都会分配）；④字典/集合在初始化时按容量建好、复用，不在 tick 内增删；⑤读值返回只读快照/span，避免拷贝与分配；⑥序列化与字符串化延迟到上报线程批量做。目标是热路径每 tick 接近零分配，消除 Gen0/Gen1 GC 暂停带来的采样抖动。
6. **采样/上报分开/阻塞后果**：采样线程必须极轻（读值+拷贝进缓冲、临界区极短）以保证高频节拍稳定；序列化、编码、网络发送是慢且不确定的操作，放上报线程。若慢发送阻塞采样线程，网络一抖或某客户端变慢就会让采样节拍停顿/丢拍，所有客户端的波形都被拖垮，甚至影响共享数据源读取的实时性。通过有界环形缓冲把两者解耦（生产消费），上报慢只影响自己的缓冲（覆盖/背压），采样线程始终按节拍前进，这也是 Day04 隔离与背压在引擎层的落地。
7. **性能预算/保护**：先估算每秒采样操作数=Σ(每计划点数×采样频率)，结合单次读值/拷贝成本估 CPU、内存带宽与网络发送量，给出设备可承受的全局总预算与单客户端频率/点数上限（授权配额）。运行时调度器统计实际负载，订阅请求若使总量超预算则降频到允许值或拒绝；发送/缓冲超水位触发背压（覆盖+Gap）；EDA 采样线程优先级与资源与 GEM 控制隔离、设 CPU 上限，保证最坏情况下控制面（HSMS/状态机）不被数据面挤占。

## 二、参考实现（net8.0）

```csharp
namespace EapLab.Eda.Engine;
// 值类型采样点, 零堆分配
public readonly struct Pt{public readonly double At;public readonly double V;public readonly Quality Q;
    public Pt(double at,double v,Quality q){At=at;V=v;Q=q;}}

// 有界环形缓冲: O(1), 覆盖最旧, 统计溢出, 线程安全
public sealed class RingBuffer
{
    readonly Pt[] _a;int _w,_count;readonly object _lk=new();public long Overwritten{get;private set;}
    public RingBuffer(int cap){_a=new Pt[cap];}
    public void Write(Pt p){lock(_lk){ if(_count==_a.Length){_w=(_w+1)%_a.Length;Overwritten++;}
        _a[_w]=p;_w=(_w+1)%_a.Length;_count=Math.Min(_count+1,_a.Length);} }
    public Pt[] Drain(){lock(_lk){var n=_count;var outA=new Pt[n];var r=(_w-_count+_a.Length)%_a.Length;
        for(int i=0;i<n;i++)outA[i]=_a[(r+i)%_a.Length];_count=0;_w=0;return outA;}}
    public int Count{get{lock(_lk)return _count;}}
}

// 集中采样调度: 基础tick, 计划按周期分级, 一次tick服务多计划
public sealed class SamplePlan{public string Id{get;}public string Tag{get;}public int EveryTicks{get;}
    public RingBuffer Buf{get;}public SamplePlan(string id,string tag,int every,int cap){Id=id;Tag=tag;EveryTicks=every;Buf=new RingBuffer(cap);}}

public sealed class SampleScheduler
{
    readonly List<SamplePlan> _plans=new();readonly EquipmentDataBus _bus;long _tick;
    public SampleScheduler(EquipmentDataBus bus){_bus=bus;}
    public SamplePlan Add(string id,string tag,double planHz,double baseHz,int cap)
    { var every=Math.Max(1,(int)Math.Round(baseHz/planHz));
        var p=new SamplePlan(id,tag,every,cap);_plans.Add(p);return p; }
    // 每基础节拍调用一次; 到期的计划采样, 同一tick同时间戳
    public void Tick(double monoAt,Func<string,Quality> q)
    { _tick++;
        foreach(var p in _plans)
            if(_tick%p.EveryTicks==0)
                p.Buf.Write(new Pt(monoAt,_bus.Read(p.Tag),q(p.Tag))); }
    public long Ticks=>_tick;
}
```

## 三、采样管线（手绘参考）
```
数据源更新线程(唯一权威)
      │只读快照(极短临界)
      ▼
采样线程: 一个基础节拍tick ──按EveryTicks分级──▶ 到期计划(同tick同单调时间戳)
      │ struct点写入
      ▼
各计划有界环形缓冲(周期trace可覆盖最旧+Overwritten/Gap; 事件/异常独立不覆盖队列)
      │Drain批量
      ▼
上报线程: 批量取→序列化(XML/PB)→网络发送(慢操作在此, 不阻塞采样)
低GC: struct点/ArrayPool复用/热路径零LINQ零字符串零闭包; 单调时钟内部, UTC对外
保护: Σ点数×Hz 预算+每客户端配额, 超限降频/拒绝; 与GEM资源隔离
```

## 四、今日易错点
1. 每计划开 Timer/线程，订阅一多 CPU/抖动失控（应集中调度）。
2. 用墙上时钟定节拍，NTP 回拨导致间隔为负（用单调时钟）。
3. 用无界 Queue/List 承载高频流，内存失控、GC 抖动（用环形缓冲）。
4. 事件/异常快照也用覆盖式缓冲，关键节点证据被周期点覆盖丢。
5. 热路径每点 new class/数组、拼字符串、用 LINQ，GC 暂停造成采样抖动。
6. 慢网络发送放在采样线程，一堵全丢拍（采样/上报必须解耦）。
7. 多客户端订同一变量重复读值、时间戳不一致（一次读、同 tick 同戳共享）。
8. 不做性能预算与全局上限，极端订阅挤占 GEM 控制面资源。
