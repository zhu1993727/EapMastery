# W28 · Day05（周五）数据上报服务：Freeze II/III 编码与推送通道

> 建议时长：95 分钟。运行时产出 Packet 后，要按 Freeze 版本编码并推送给各客户端。今天实现数据上报服务：传输抽象、Freeze II XML 回报与 Freeze III protobuf 流、内容协商、发送队列/断连处理、订阅生命周期，形成"采集→打包→编码→推送"完整链路。

## 一、今日目标
1. 理解两种数据回报形态：Freeze II 设备调用客户端回调 Web Service（SOAP/XML）；Freeze III 服务端流推送（protobuf，近 gRPC streaming）。
2. 实现传输抽象 ITransport + 编码器可插拔（XML/PB），按会话协商选择。
3. 掌握每客户端独立发送队列、异步发送、断连缓冲/重连策略、发送失败不影响他人。
4. 打通订阅生命周期：建立→数据流→暂停/恢复→取消，取消即停发并释放。
5. 用 C# 实现 ReportService（编码选择、按会话路由、发送队列、断连处理、生命周期）+ 模拟客户端；xUnit 验证。

## 二、背景知识（先读，35 分钟）

### 1. Freeze II 的回报方式
- SOAP 架构里客户端也暴露一个回调 Web Service（数据接收端点），设备 EDA Server 在有数据时**主动调用客户端的回报方法**，把 XML 数据包 POST 过去（双向 Web Services）。
- XML 数据包遵循 E138 公共组件结构，人可读、易调试；高频时报文大、解析重。

### 2. Freeze III 的回报方式
- 采用 Protocol Buffers 编码，传输更接近 gRPC 的**服务端流（server streaming）**：建立订阅后设备沿流持续推送二进制数据包，连接复用、报文紧凑、延迟低，适合高频大数据。
- 语义与 Freeze II 完全一致（同一个 Packet 模型），只是编码与传输机制不同。

### 3. 传输抽象与内容协商
- 定义与编码无关的 ITransport（Send(sessionId, bytes)），上层只给中性 Packet；XmlEncoder/ProtoEncoder 可插拔。
- 会话建立时协商 Freeze 版本/编码（客户端声明支持 II 还是 III），ReportService 按会话选编码器，同设备可同时服务 II 老客户端与 III 新客户端（向后兼容）。

### 4. 发送队列与故障隔离
- 每会话独立发送队列与发送任务（Day04 隔离）：某客户端网络慢/断，只堆积/挂起它自己的队列，不阻塞设备采样与其他客户端。
- 断连处理：短暂断连可有限缓冲（实时流缓冲有界，超限按 Day04 策略丢周期保事件+Gap）；重连后继续推新数据（实时流一般不补历史，历史由 EDC/历史库负责，W34）；明确区分"实时通道不补"与"GEM 事务可靠不丢"。
- 发送失败计数、最后错误可观测；连续失败达阈值判会话死亡，触发 Day04 级联撤销。

### 5. 订阅生命周期在上报侧的体现
- Create：建发送队列与编码上下文；Pause：停止取该计划 Packet（保留注册）；Resume：恢复；Cancel/会话关闭：停发、清队列、释放编码上下文、退订。
- 保证"取消后绝不再发出该计划数据"（无泄漏、无错发）。

### 6. 与 ASP.NET Core 的对应（W29 真做 HTTP）
- 今天先用内存抽象把链路逻辑做对；W29 用 ASP.NET Core 最小 API/gRPC 把 ITransport 换成真实 HTTP(S)/HTTP2，逻辑层不变——这正是 Day06 内核与传输分离的回报。
