# W23 · Day02 答案与参考实现

## 一、自测题标准答案
1. **只看静态优先级的饥饿 / 只看 FIFO 的问题**：只看静态优先级，若高优先级批次持续到来，低优先级任务永远排在它们后面、长期得不到资源，即饥饿（可能饿死某些返工片/实验批）。只看 FIFO（严格先来先服务）则无法响应生产中的紧急情况——hot lot（急件）、工程批、交期临近批次无法插队，关键订单被普通批次堵在后面。正确做法是以静态优先级体现紧急度、以等待老化保证公平兜底、以确定性 tie-break 保证可复现。
2. **有效优先级构成 / 完整排序**：有效分 effective=静态优先级 Prio + 老化增益 floor(等待时长/agingInterval)（可封顶但封顶值要足以最终超过静态差）。完整排序次序：①有效分降序；②就绪时间升序（同有效分先来先服务）；③工艺/腔体亲和（同 recipe、同腔切换代价小者优先）；④CjId/PjId 字典序（确定性 tie-break，保证唯一顺序、可复现）。即先比"谁更该做"、再比"谁更早等"、再比"谁更省切换"、最后用 ID 消除并列。
3. **老化如何数学保证无饥饿**：设静态优先级范围 [0,Pmax]，某低优任务静态分=0，只要老化增益随等待时间无上界增长（或封顶 ≥Pmax），则它等待到 agingInterval×Pmax 之后，有效分就 ≥ 任何新到达的最高静态优先级任务（后者老化≈0、有效分≤Pmax），此后它必然排在就绪队首被调度。即"等待时间可以兑换成任意高的优先级"，于是任意任务的等待时间都有上界，不存在无限等待，数学上消除饥饿；同时可用 maxWait 监控这个上界、超时告警。
4. **优先级反转 / 不可抢占设备的治理**：反转指高优先级 H 要用的资源正被低优先级 L 持有，而 L 又被一连串中优先级任务持续插队、迟迟得不到调度释放资源，导致 H 被比自己低的任务间接阻塞。设备加工不可中途抢占（中途让腔会报废在制品），治理：①优先级继承——L 一旦持有 H 等待的资源，就在持有期间继承 H 的高有效分，保证 L 不会被中优先级插队、尽快跑完释放；②有序预留——预留资源时就按有效优先级排序分配，避免低优任务过早占住高优马上要用的关键资源；③不做工艺中途抢占。这样 H 的实际等待只等于 L 剩余加工时间，有上界、不会被中优任务无限拉长。
5. **亲和为何次级 / 何时让位**：亲和（同 recipe 连做减少换气清腔、同腔减少差异）是效率优化，只影响"同等该做的任务里谁更省成本"，不改变"谁更该做"。当它与有效优先级/防饥饿冲突时必须让位：一个等待已久（老化后有效分更高）的不同 recipe 批次，应优先于刚到的同 recipe 批次，否则用亲和做首要规则会让"配方不同"的任务被反复推迟、形成另一种饥饿。所以排序里亲和排在有效分、就绪时间之后，只做 tie-break 级优化。
6. **DecisionRecord 字段 / 解决问题**：字段应含决策时刻、被选中任务（CjId/PjId）、其有效分构成（静态分+老化增益+等待时长）、同刻竞争者列表及各自有效分、未选原因（等哪个资源、该资源被谁占到何时、预计自己最早可用时刻）、本次预计开始/结束、是否触发老化提权/优先级继承。它解决现场"黑盒调度说不清"的问题：Host/工程师问"为什么这批还没开始""为什么先做那批"，能直接给出规则化、可核对的理由，并能在排产异常（某批等待超 maxWait）时追溯是被谁、按什么规则挡住。
7. **低优等待久反超新高优是不是 bug**：不是 bug，正是老化防饥饿机制按设计生效。新高优先级批次静态分高但刚到、老化增益≈0；低优批次等待很久、累积老化增益后有效分反超，于是先调度它，以保证任何批次等待有上界、不被持续到来的高优流饿死。若业务上某急件确实必须绝对优先，应通过更高的静态优先级 + 明确的抢占/预留策略表达，而不是靠取消老化；老化反超可被 DecisionRecord 解释（记录了两者有效分构成），是可预期、可审计的公平行为。

## 二、参考实现（net8.0）

```csharp
namespace EapLab.E94.Sched;
public sealed class SchedJob
{
    public string CjId="",PjId="",Recipe=""; public int StaticPrio; public double ReadyAt;
    public double AgingInterval=10; public int AgingCap=100;
    public double EffectivePrio(double now)=>
        StaticPrio + Math.Min(AgingCap,(int)Math.Floor((now-ReadyAt)/AgingInterval));
    public double Wait(double now)=>now-ReadyAt;
}
public sealed record DecisionRecord(double At,string Chosen,double ChosenScore,
    List<(string id,double score,string reason)> Candidates,double EstStart,double EstEnd,bool Aged);

public sealed class PriorityPolicy
{
    public List<SchedJob> Order(IEnumerable<SchedJob> jobs,double now,string? currentRecipe)=>
        jobs.OrderByDescending(j=>j.EffectivePrio(now))
             .ThenBy(j=>j.ReadyAt)
             .ThenBy(j=>j.Recipe==currentRecipe?0:1)   // 亲和次级
             .ThenBy(j=>j.CjId).ThenBy(j=>j.PjId).ToList();
}

public sealed class AgingScheduler
{
    private readonly PriorityPolicy _policy=new(); private readonly GlobalResourceCalendar _cal;
    public double MaxWait{get;init;}=100; public List<string> StarvationAlerts{get;}=new();
    public AgingScheduler(GlobalResourceCalendar cal){_cal=cal;}

    public DecisionRecord? Decide(List<SchedJob> ready,ResId[] res,double dur,double now,string? recipe)
    {
        foreach(var j in ready) if(j.Wait(now)>MaxWait) StarvationAlerts.Add($"{j.CjId}/{j.PjId}等待超{MaxWait}");
        var ordered=_policy.Order(ready,now,recipe); if(ordered.Count==0)return null;
        var chosen=ordered[0];
        var cands=ordered.Select(j=>
        { double s=j.EffectivePrio(now);
          string reason=ReferenceEquals(j,chosen)?"选中":
              (_cal.Overlaps(res[0],now,now+dur)?"等待资源":"有效分较低");
          return (j.CjId+"/"+j.PjId,s,reason); }).ToList();
        double est=_cal.EarliestCommon(res,dur,Math.Max(now,chosen.ReadyAt))!.Value;
        bool aged=chosen.EffectivePrio(now)>chosen.StaticPrio;
        return new DecisionRecord(now,chosen.CjId+"/"+chosen.PjId,chosen.EffectivePrio(now),cands,est,est+dur,aged);
    }
}
```

### 优先级继承（持有高优所需资源时提级）
```csharp
public sealed class PriorityInheritance
{   // holder当前持有资源; waiters是等待该资源的任务, 取最高有效分作为继承分
    public double InheritedScore(SchedJob holder,IEnumerable<SchedJob> waiters,double now)
    =>Math.Max(holder.EffectivePrio(now),waiters.DefaultIfEmpty().Max(w=>w?.EffectivePrio(now)??double.MinValue));
}
```

public class PriorityTests
{
    static SchedJob J(string id,int prio,double ready,string recipe="R")=>
        new(){CjId=id,PjId="P",StaticPrio=prio,ReadyAt=ready,Recipe=recipe,AgingInterval:10};

      var o=p.Order(new[]{high,low},100,null);
      Assert.Equal("L",o[0].CjId); }                 // low老化分=10 > 5
    [Fact] public void 同有效分_FIFO再亲和再ID()
    { var p=new PriorityPolicy();
      var o=p.Order(new[]{J("B",1,0,"X"),J("A",1,0,"X")},0,null);

    { var p=new PriorityPolicy();
      var aged=J("OLD",0,100,"X"); var fresh=J("NEW",3,0,"X"); // 当前recipe=X, fresh同配方
      var o=p.Order(new[]{fresh,aged},100,"X");
      Assert.Equal("OLD",o[0].CjId); }

## 三、调度优先级（手绘参考）
```
排序键: 有效分(静态Prio + 老化floor(wait/interval), 可封顶)降序
      → 就绪时间升序(FIFO) → 配方/腔体亲和(省切换) → CjId/PjId字典序(确定)
无饥饿: 老化可兑换任意优先级 → 等待有上界; MaxWait监控告警
反转治理: 工艺不可抢占; 持有者继承等待者最高分(不被中优插队) + 有序预留
亲和: 仅次级tie-break, 与老化/优先级冲突时让位
可解释: DecisionRecord(选中/有效分构成/竞争者/未选原因=等谁占的哪个资源到何时/预计起止/老化标记)
```

## 四、今日易错点
1. 只按静态优先级（低优饥饿）或只按 FIFO（急件无法优先）。
2. 老化封顶过低，最终仍超不过最高静态分（封顶须 ≥静态极差，保证无饥饿）。
3. 并列时无固定 tie-break（排程不可复现）。
4. 试图工艺中途抢占腔体（会报废在制品，应非抢占+优先级继承）。
5. 把配方亲和当首要规则（制造新饥饿，亲和只能次级）。
6. 调度是黑盒、给不出"为什么先做它"（必须 DecisionRecord 可解释）。
7. 不监控最大等待，饥饿发生了无告警。
8. 优先级继承只在 CPU 场景用（设备资源持有者同样要继承，防中优插队拖死高优）。
